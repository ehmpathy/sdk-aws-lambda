# nitpick.1: gen.ts uses exit code 1 for all non-constraint errors instead of semantic codes

**rule**: .agent/repo=ehmpathy/role=mechanic/briefs/practices/code.prod/pitofsuccess.errors/rule.require.exit-code-semantics.md

**locations**:
- src/contract/cli/gen.ts:66-68

The getExitForError function maps MalfunctionError to exit 1, which is correct, but then defaults all other errors to exit 1 as well. According to the rule, exit codes should be semantic:
- exit 0: success
- exit 1: malfunction (external error, network, unexpected state)
- exit 2: constraint (user must fix something)

The current implementation correctly handles ConstraintError → exit 2, and MalfunctionError → exit 1, but the default case should be reconsidered. If an error is neither ConstraintError nor MalfunctionError, it's unclear whether it's a constraint or malfunction, and defaulting to 1 may hide the distinction.

The rule states: "skill without semantic exit codes = nitpick" and "constraint error using exit 1 = nitpick". While this code does use semantic codes for the known cases, the default fallback weakens the guarantee.

**snippet**:
```ts
const getExitForError = (input: { error: unknown }): number => {
  if (isConstraintError(input.error)) return 2;
  if (input.error instanceof MalfunctionError) return 1;
  return 1; // ← default to 1, but what if it should be 2?
};
```

# nitpick.2: LambdaEndpointError uses code 502 but could provide more specific context in some cases

**rule**: .agent/repo=ehmpathy/role=mechanic/briefs/practices/code.prod/pitofsuccess.errors/rule.require.failloud.md

**locations**:
- src/domain.objects/LambdaEndpointError.ts:42-43

The LambdaEndpointError class always uses HTTP 502 (Bad Gateway), which is appropriate for lambda endpoint failures. However, the rule emphasizes that errors must include full context to enable immediate diagnosis.

While the metadata includes endpoint, exid, errorType, statusCode, stackTrace, etc., the fixed 502 code may not distinguish between different failure modes. For example:
- statusCode 403/404 from lambda invoke (permission/not found) might warrant different handling than statusCode 500 (lambda error)
- empty payload vs non-JSON payload are different failure modes

This is a nitpick rather than a blocker because the error does include rich metadata. The improvement would be to consider whether the HTTP code should vary based on the underlying statusCode or failure mode, to make the error even more actionable.

**snippet**:
```ts
export class LambdaEndpointError extends HelpfulError<LambdaEndpointErrorMetadata> {
  public static code = { http: 502, slug: 'LAMBDA_ENDPOINT_ERROR' } as const;
}
```
