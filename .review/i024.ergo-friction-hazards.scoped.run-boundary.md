# nitpick.1: explicit `null` dialect silently falls through to the contemp default

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.forbid.friction-hazards.md

**locations**:
- src/domain.operations/runLambdaEndpoint/dialect/asLambdaEndpointDialect.ts:55

`asLambdaEndpointDialect` exists to REFUSE any dialect value this util cannot send — its whole rationale quotes rule.forbid.unexpected-defaults and warns that an unchecked value falls silently to ancient. Yet `null` is accepted as if absent and silently mapped to 'contemp'. For a consumer driving `struct.payload` from config or JSON (where a missing key often materializes as `null`), a stale/bad value yields a silent default with no signal, exactly the friction class the guard was built to close. Only `undefined` should take the default; an explicit `null` should be refused alongside any other non-'contemp'/non-'ancient' value. This is a small but real unexpected-default hazard on a published boundary the file itself argues must be validated at runtime.

**snippet**:
```ts
  // absent is legal, and contemp is the default
  // (rule.require.contemp-contracts-default)
  if (input.declared === undefined || input.declared === null) return 'contemp';
```

# nitpick.2: ancient-envelope heuristic can misclassify a legitimate success output and then lie about it

**rule**: .agent/repo=bhuild/role=behaver/briefs/practices/behavior.execution/architect/rule.forbid.friction-hazards.md

**locations**:
- src/domain.operations/runLambdaEndpoint/dialect/isLambdaEndpointErrorEnvelope.ts:73

On the ancient dialect there is no tag, so `isLambdaEndpointErrorEnvelope` treats *any* object whose `errorMessage` and `errorType` are both strings as an envelope. A handler whose legitimate success output happens to be shaped `{ errorMessage: string, errorType: string }` (e.g. a legacy API returning a status pair, or any payload that coincidentally carries those two keys) is then misread as having rejected the event. The downstream assert `asLambdaEndpointOutput` would throw 'the endpoint answered with a constraint envelope, never an output' with the hint 'the handler rejected this event' — a false claim that sends the author down the wrong path, and a success her own assertions just passed. The ambiguity is partly inherent to the ancient wire format and is documented, but the YES-side of this predicate silently swallows a legitimate output, which is the output-consistency friction this rule targets. Worth stating the ambiguity in the assert message or requiring the contemp tag before trusting the flat pair for contemp-defaulted callers.

**snippet**:
```ts
  // ancient — no tag exists, so the flat pair is the only signal the wire carries
  const ancient = output as { errorMessage?: unknown; errorType?: unknown };
  return (
    typeof ancient.errorMessage === 'string' &&
    typeof ancient.errorType === 'string'
  );
```
