# 🌙 dream: git.commit.set reads the newest branch commit as the "first"

kind: reseed · owner: ehmpathy/rhachet-roles-ehmpathy (mechanic, git.commit.set) · caught 2026-11-15

## .the cue that fired

on a branch with `fix(endpoint)` then `cont(endpoint)` ahead of main, a third commit (`chore(route)`, then `cont(route)`) was refused with `first commit must be fix(<scope>): or feat(<scope>):`. with one commit ahead, the same tool had refused a `fix` because "branch already has a behavioral commit". so it knows the first commit at depth 1, and misreads it at depth 2.

## .the gap, precisely

the first-commit check seems to read the newest commit since main, not the oldest. a third commit on any branch fails this way when the newest is not `fix`/`feat`.

## .the shape of the fix

read `git log --reverse <merge-base>..HEAD` and take the head of that list. add a clamp for a branch with three commits: fix, cont, then cont.

## .why it is not done in this round

the skill lives in another repo. the work around it here was to fold the route out of the commit.
