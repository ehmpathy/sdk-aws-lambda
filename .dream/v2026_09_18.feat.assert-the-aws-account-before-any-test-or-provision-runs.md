## .the gap, precisely

`process.env.AWS_EC2_METADATA_DISABLED = 'true'` refuses ONE link of the aws credential chain.
measured against `@aws-sdk/credential-provider-node/dist-cjs/index.js` — `remoteProvider` checks
the CONTAINER source first:

```
remoteProvider:
  1. AWS_CONTAINER_CREDENTIALS_RELATIVE_URI  ->  still live  ⛔
  2. AWS_CONTAINER_CREDENTIALS_FULL_URI      ->  still live  ⛔
  3. fromInstanceMetadata (IMDS)             ->  refused     ✅
```

so on ecs/fargate the chain still adopts an ambient role, silently, and a run targets whatever
account that role belongs to. **the refusal is a partial guard dressed as a whole one**, and
partial-but-silent is the `rule.forbid.failhide` shape.

the second half of the gap: the refusal is **negative** — it names what must not be used. it
cannot state what MUST be true, so no configuration of it can ever say *"this run is pointed at
account 1234."*

## .the shape of the fix

one assertion, at the same three boot sites, run AFTER credentials are sourced and BEFORE any
resource is read or written:

```ts
// sts:GetCallerIdentity is cheap and needs no extra grant
const { Account } = await new STSClient({ region }).send(new GetCallerIdentityCommand({}));
if (Account !== expected)
  throw new ConstraintError('aws credentials point at the wrong account', {
    expected, actual: Account,
    hint: 'run: rhx keyrack unlock --owner ehmpath --env <env>',
  });
```

three things it needs:

1. **a home for `expected`** — `declapract.use.yml` already carries `awsAccountId`, and both
   jest env files already read that file to decide `requiresAwsAuth`. so the value is on disk
   and already parsed; no new plumbing is owed
2. **an async boot seam** — `jest.setupFilesAfterEach` is sync in these files today. the
   assertion is a network call, so the boot must `await` it (jest supports an async setup file)
3. **a decision on the provision site** — `resources.ts` has no boot phase of its own; the
   natural seam is inside `getProviders`, before the provider is handed back

once it lands, the IMDS refusal can stay (defense in depth) or go (superseded) — **that is a
choice the assertion makes available, and today there is no choice at all.**

## .why it is not done in this round

- **SAFE?** no. it adds a network call to the boot path of every acceptance and integration run,
  and a wrong `expected` value refuses every suite in the repo. that needs its own verification
  pass against a real ci run, which this bound cannot supply
- **CLEAN?** no. it ripples into `declapract.use.yml` parsing, the jest setup contract (sync →
  async), and `getProviders`' signature — three surfaces this wish never intended to open

⇒ both questions answer no, so it defers, and the deferral is a judgment about ripple cost —
which is what earns it a fulcrum beside this dream
(`rule.always.fix-forward-under-scouts-honor`).

## .what WAS done in that round, so the next traveler does not redo it

- the verbatim triplication of the evidence was collapsed: the `remoteProvider` dist read and
  the container caveat now live ONCE at `jest.acceptance.env.ts`, and the two peers cite it
- `r7.1`'s narrower ask — gate the refusal on a deploy context — was **measured and refused**:
  `resources.ts` exports only aws operations, and `declastruct plan` reads live aws state, so
  the plan path wants the refusal as much as apply does. the reason sits at that file
- a real drift the reviewers predicted was found and named at both sites: the two jest envs
  express "do not be strict in ci" in two different shapes
