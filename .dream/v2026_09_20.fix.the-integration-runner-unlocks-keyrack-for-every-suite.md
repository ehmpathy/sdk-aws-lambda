# 🌙 dream: the test runner unlocks keyrack for a suite that needs no credential

- kind = reseed
- owner = `ehmpathy/rhachet-roles-ehmpathy` — the `git.repo.test` skill
- caught 2026-09-20
- ⚠️ **widened 2026-09-20, same session** — the family is **two** genres, not one; see the sweep

## .the cue that fired

a re-run of this bound's newest clamp, which reads the local filesystem and calls no remote:

```
rhx git.repo.test --what integration --mode apply --scope 'path://getJsonSchemaFromZod'
  → 🐢 bummer dude...
  → status: malfunction
  → error: keyrack unlock failed
  → ✋ aws sso login timed out — human did not respond to browser sso prompt
```

⇒ the test never ran. **the runner unlocked credentials before it read the scope**, so a
zero-credential suite was gated on a browser click.

## .the gap, precisely

`--what integration` unlocks keyrack **unconditionally**, ahead of any decision about which files
the run will touch. so the credential requirement is a property of the **genre** rather than of the
**suite**.

that is sound for most of the genre. it is wrong for the growing slice that has no remote at all:

| integration suite | remote boundary it crosses | needs a credential? |
|---|---|---|
| `askLambdaEndpoint.integration.test.ts` | aws lambda invoke | ✅ yes |
| `genIntrospectionMiddleware.getJsonSchemaFromZod.integration.test.ts` | **the local filesystem** | 🔴 **no** |

`rule.forbid.unit.remote-boundaries` puts a filesystem read in `.integration.test.ts` by name — *"if
it touches the outside world, it's not a unit test"*. so the rule **mints** credential-free
integration tests by design, and the runner has no way to tell one from the other.

⚠️ **and the cost lands on exactly the wrong test.** a clamp is worth most when it is cheap to run.
this one guards a service-wide introspection crash and costs ~2s of disk reads — yet it inherits
the credential requirement of every remote suite in its genre.

### ⚠️ .a CORRECTION to this dream's own words, same day

an earlier draft of this paragraph read *"and is **currently unrunnable** on a box whose sso has
gone cold."* 🔴 **that clause is struck — it was measured false within the hour.**

a **direct** `rhx keyrack unlock --owner ehmpath --env test` reached the human, the browser prompt
was answered, and the suite then ran:

```
rhx git.repo.test --what integration --mode apply
  → keyrack: unlocked ehmpath/test
  → 🎉 4 suites · 24 passed · 0 failed · 16s
```

⇒ so the **proximate** cause of the halt was a dead sso session plus a runner whose unlock is
non-interactive and therefore cannot surface a browser prompt. that is a sequence fact, and
`useKeyrack`'s own header states it: the sso session must be live **before** the harness runs.

🟡 **the design defect below survives the correction, and is sharpened by it.** the gate reads
`$WHAT` alone. that is what *converts* a dead sso — a condition a filesystem-only suite has no
stake in — into a blocked credential-free suite. so the defect is real and its severity is
**lower** than this dream first implied: it costs a browser click, never a deliverable.

⚠️ this correction is recorded **in the body, at the claim**, rather than in a header alone —
`rule.require.sweep-the-defect-class`'s third trap, enbriefed the same day off a failure of mine in
a peer file.

## 🔴 .the sweep — I bounded it to ONE genre, and the family is TWO

my first draft named `--what integration` and stopped there. the very next command in the same
session fell to the identical cause:

```
rhx git.repo.test --what acceptance --against local --env test --mode apply
  → status: malfunction · error: keyrack unlock failed
```

⚠️ **that is `rule.require.sweep-the-defect-class`'s second trap — a sweep bounded to one axis of a
cause that names no axis.** my stated cause was *"the runner unlocks before it reads the scope"*,
which says not one word about `--what`. so the axis was there, unstated, and unswept.

⇒ the control is the **source**, never a second failure. the gate is an allowlist-by-exclusion at
`git.repo.test.sh:1046-1051`:

```sh
unlock_keyrack() {
  # skip for types, format, lint, and unit — only integration/acceptance need credentials
  if [[ "$test_type" == "types" ]] || ... || [[ "$test_type" == "unit" ]]; then
    return 0
  fi
  ... rhx keyrack unlock --owner ehmpath --env "$ENV_NAME"
```

**the family is exactly what that predicate admits**, and the skill's own header declares it:
*"auto keyrack unlock for integration/acceptance"*.

| `--what` | unlocks? | a credential-free member exists? |
|---|---|---|
| `types` · `format` · `lint` · `unit` | no | — |
| `integration` | ✅ | ✅ the F36 clamp — a filesystem read |
| `acceptance` | ✅ | ✅ **every `--against local` run** |

### ⚠️ the acceptance member is the SHARPER of the two

`--against local` is a caller's **explicit declaration** that no cloud is reached — the flag exists
for that purpose, and `--against cloud` is its peer. the unlock reads `$WHAT` alone and consults
`$AGAINST` not at all.

⇒ so this member needs no scope computation to fix. **the answer is already on the command line**,
one variable away, and the gate does not look at it. that makes it strictly cheaper than rung 1
below, and it should land first.

## .the shape of the fix

rungs, cheapest first (`rule.prefer.prevent-over-correct`):

0. **read `--against`** — `unlock_keyrack` branches on `$WHAT` alone; add `$AGAINST == local` to the
   skip predicate at `git.repo.test.sh:1049`. ✅ **one condition, no new concept, no scope walk.**
   it closes the whole acceptance member, and the caller already states the fact
1. **unlock lazily** — compute the scope first, and unlock only if the matched set holds a suite
   that declares a remote. closes the integration member; changes no test
2. **let a suite declare its boundary** — a `.note = no remote` marker, or a `.local.integration.test.ts`
   suffix the runner reads. more explicit, and it mints a new file-name convention, which owes a
   verdict of its own
3. **unlock on demand, at the failure** — let the run proceed and unlock when a credential is first
   reached. 🔴 **do not take this rung.** it converts a clean upfront gate into a mid-suite halt, and
   a partially-run suite reports a state nobody can act on (`rule.forbid.failhide`)

⇒ **rung 0 first, then rung 1** — they close different members of the family and neither subsumes
the other. rung 0 is a one-line predicate change; rung 1 needs the matched file set, which the
runner already computes for `--mode plan` and simply computes **after** it unlocks.

⚠️ **the members must be ruled together, never one at a time.** a fix that closes only acceptance
leaves the F36 clamp unrunnable and reads as done, which is the false-completeness shape
`rule.require.sweep-the-defect-class` names.

## .why it is not done in this round

| question | answer |
|---|---|
| **SAFE?** | 🔴 **no** for rung 1 — it changes the credential gate for **every** integration run in every repo that uses this skill, and a wrong lazy-unlock ships a suite that silently skips its remote half. ✅ **yes** for rung 0, which reads a flag the caller already set and narrows no other case |
| **CLEAN?** | 🔴 **no.** the skill lives in `ehmpathy/rhachet-roles-ehmpathy`. this worktree is `sdk-aws-lambda`, and the fix lands in neither its diff nor its bound |

⇒ a **reseed** — the fix is scoped to another repo, so this tree adopts it not at all
(`rule.always.catch-dreams-for-followups`).

🟡 **it gates no work here.** the clamp was proven green before the sso went cold — 5 rows, both
defect arms driven red, recorded in `F36`. what this costs is the **re-run**, which is a
verification convenience rather than a deliverable.

⚠️ **and rung 0's `SAFE ✅ / CLEAN 🔴` pair is worth a second read**, because it is the rare shape
where a fix is genuinely safe and still correctly deferred. the dirt is **ownership**, never ripple:
the file is in another repo. so the deferral rests on a fact any reader can check in one command,
which is the opposite of the absence-sourced grade that produced `F36`
(`rule.require.positive-control-before-absence-claims`).
