# 🌙 dream: a deployed suite's hook budget loses on a cold run

- kind = fix
- owner = `ehmpathy/sdk-aws-lambda`
- caught 2026-09-18

## .the cue that fired

self review `r1.has-zero-test-skips` at stone `5.3.verification` swept the axes its stated cause
left unstated. one of them was **`--changedSince=origin/main`** — a default that runs only the
test files a branch touched, which is a scope narrow rather than a `.skip`, and therefore
invisible to every grep for the word.

widened to the full suite, the acceptance run went red:

```
deployed.introspection.acceptance.test.ts   7 failed
  thrown: "Exceeded timeout of 360000 ms for a hook."
```

⚠️ **no gate raised it.** the narrow run was green, the warm re-run is green, and the same suite
alone is **7 passed in 25s**. it took one cold full run to see it once.

### 🔴 .a REPRODUCTION was claimed here on 2026-09-20, and it is RETRACTED

⚠️ **read this whole section. the claim it replaces was struck the same hour it was written, and a
header stamp alone would leave the false table live beneath it**
(`rule.require.sweep-the-defect-class`, the third trap).

**what was claimed:** a `[t1]` run on 2026-09-20 returned `267 passed · 7 failed` — the same file,
the same 7, the same `Exceeded timeout of 360000 ms for a hook`, the same `useBeforeAll` frame. I
called it *"one deterministic breach"* and treated this dream's weakest line — *"it took one cold
full run to see it once"* — as repaired.

🔴 **it is not.** that run had a **concurrent peer I started myself**: a backgrounded run of the
identical command, inflight for the whole 559s the foreground one ran. both deploy the same lambda
functions into the same aws account, and aws blocks a concurrent update rather than queues it.

| the 2026-09-20 pair | wall | result |
|---|---|---|
| foreground, with a concurrent peer | 559s | 267 ✅ · **7 ✗** |
| background, allowed to finish | 1197s | ✅ **274 ✅ · 0 ✗** |

⇒ **the 7 measured contention, never the cold path.** so `[t0]` remains this dream's **only**
observation, and its own caution stands unrepaired: one cold full run saw it once.

🟡 **`[t0]` is untouched by this.** its evidence is the absent `⏱ setLambda upsert took Nms` line,
read from its own log, with no concurrent writer in play. the `180s` figure still derives from one
truncated sample, and the arithmetic in `.the shape of the fix` is unchanged.

🟡 **one result the retracted run did leave behind, and it holds:** the warm control was re-run at
that instant and returned **7 passed, 0 failed, 39s** — 25s at `[t0]`, 39s now. that is a second
measurement of the *warm* arm, against a **360s** budget, and it is not confounded: the control ran
alone.

⚠️ **the lesson, for whoever next measures this:** run the suite **once**. a second concurrent run
against a shared aws account does not double the sample — it manufactures a failure that wears the
same error string as the defect you came to observe.

## .the gap, precisely

the hook budget is composed in `blackbox/__test_assets__/setLambdaLive.ts`:

```
LAMBDA_DEPLOY_HOOK_BUDGET_MS  =  PREFLIGHT (30s)  +  LAMBDA_DEPLOY_BUDGET_MS (330s)   = 360s
LAMBDA_DEPLOY_BUDGET_MS       =  IAM backoff (30s) + LAMBDA_UPSERT_BUDGET_MS (180s) + waiters (120s)
```

**the phase that overran is located by what the log does NOT hold** — the same method the file's
own `.which term ACTUALLY squeezed` block used one level up:

| the line, for `svc-seaturtle-prep-checkContract` | present? | what its absence rules out |
|---|---|---|
| `⏱ … bundle + zip took 332ms` | ✅ | — |
| `⏱ … iam role upsert took 1879ms` | ✅ | — |
| `⏱ … setLambda upsert took Nms` | 🔴 **absent** | the upsert **never returned** |
| `⏳ … iam propagation, retry` | absent | `withRetry` saw no retryable error — ONE attempt |
| `⏳ … await State=Active...` | absent | neither waiter ran |

⇒ preflight was **2.2s**, so **≥357s** sat in one `setLambda` attempt against a **180s** budget.
that is a breach by more than 2x, and it is still a floor — jest truncated it, exactly as it
truncated the 157s sample the 180s was derived from.

🟡 **the same run holds both arms of the spread.** six peer functions reported
`4425 · 5043 · 5104 · 4608 · 4975 · 4598 ms` warm. ~70x, and the warm arm is what every green
run publishes.

### 🔴 and CI meets the same path — this is not a local curiosity

traced at review `r2.has-zero-test-skips`:

| fact | evidence |
|---|---|
| CI runs the **whole** acceptance suite, deployed suites included | `.github/workflows/.test.yml:212` — `THOROUGH=true npm run test:acceptance` |
| with real aws creds | `.test.yml:199-203`, gated on `inputs.creds-aws-role-arn` |
| against **the same account** as a local run | `test.yml:24` → `arn:aws:iam::805192865516:role/ehmpathy-demo-oidc`, and the local run's function arn is `arn:aws:lambda:us-east-1:805192865516:…` |

⇒ **CI and every developer share one set of deployed functions**, so whichever ran last leaves
them warm for the next. that is precisely why the breach reads as a flake: the cold path is only
reached by whoever moves the code hash first, and everyone after them is warm.

⚠️ **so a PR that changes a handler fixture is the one most likely to fail CI on this**, and it
will fail with a hook timeout that names no product defect — the worst possible signal to hand a
contributor.

### why this is a budget defect and not a product defect

| control | result |
|---|---|
| the suite alone, warm | 7 passed, 0 failed, **25s** |
| the full suite re-run, warm | 274 passed, 0 failed, **117s** |

no assertion ever failed. the suite is correct.

## .the shape of the fix

🔴 **the obvious repair is ruled out by arithmetic, and so is the fallback.** to cover 357s puts
`LAMBDA_DEPLOY_BUDGET_MS` at `30 + 357 + 120` ≈ **507s**, and `deployed.codegen.refs`' four-lambda
bound at `30 + 507 × 4` ≈ **34 min** — past the 30-min bound that already rejected a `240s` raise.

so what is left are three options, best first, and each is a change this bound did not open:

1. **take the cold path off the critical path** — split the `deployed.*` suites out of the default
   acceptance gate into a command of their own, so a cold deploy is a deliberate run with a budget
   of its own. cheapest, and it stops the arithmetic from having to serve two populations at once
2. **a per-suite budget** — admit that a four-lambda suite and a one-lambda suite need different
   arithmetic. `deployed.codegen.refs` is the only member of the first class
3. **serialize the deployed suites and warm them** — a jest-config change, named and rejected in
   `F34`'s original fork for being outside this bound. the measurement raises its case, not lowers it

⚠️ **do not simply raise the number.** the 180s came from one truncated sample and the next number
would come from another truncated sample. whoever takes this should measure with a budget large
enough to let `setLambda` **complete**, so the run yields a real ceiling rather than a third floor.

## .why it is not done in this round

| question | answer |
|---|---|
| **SAFE?** | ✅ yes — every option touches test infrastructure alone, no prod behavior |
| **CLEAN?** | 🔴 **no.** option 1 changes the `package.json` test contract and the CI workflow that names it; option 2 changes an arithmetic four call sites read; option 3 is a jest-config change |

⇒ a **dirt** call rather than a size call, so it is paired with a fulcrum
(`rule.always.fix-forward-under-scouts-honor`). and the open question is no longer a number —
it is *"which population does the acceptance gate serve?"*, which is a wisher call.

⚠️ **and it is NOT an unmet acceptance line.** every behavior the wish and the vision asked for is
covered and green. what fails is the harness that deploys the fixtures, on its cold path only.
