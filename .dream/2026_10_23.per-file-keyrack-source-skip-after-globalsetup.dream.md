# 🌙 dream: skip the per-file keyrack.source once jest's global setup has sourced the keys

kind: fix · owner: sdk-aws-lambda (test harness) · caught 2026-10-23

## .the cue that fired

the first thorough acceptance run on 2026-10-23 at 23:12Z (`.log/role=mechanic/skill=git.repo.test/what=acceptance/2026-10-23T23-12-54Z.stderr.log`) died on the keyrack daemon, not on a test:

      at Object.<anonymous> (jest.acceptance.env.ts:65:11)

a retry passed (18 files, 410 tests). the same daemon fault hit a lone `rhx keyrack unlock` that night, so the daemon is flaky on its own; each extra call is one more draw.

## .the gap, precisely

`jest.keyrack.globalsetup.ts` runs `useKeyrack` once in the parent, so every worker inherits every key. yet each test file's `useKeyrack` (via `jest.integration.env.ts` and `jest.acceptance.env.ts`) still calls `keyrack.source` (`useKeyrack.ts`, the `source({ env, owner, mode })` line) before its `AWS_ACCESS_KEY_ID` skip. a thorough acceptance run makes 18 daemon GETs where one would do; integration makes 23.

## .the shape of the fix

- the global setup marks the env once its source ran, e.g. `KEYRACK_SOURCED_BY_GLOBALSETUP=true`
- `useKeyrack` returns before `source(...)` when that mark is set and `AWS_ACCESS_KEY_ID` is present
- the per-file call stays the backstop for a run that bypasses the global setup (mark absent)
- clamp in `useKeyrack.integration.test.ts`: with the mark set, 22 per-file calls make 0 `source` calls; with it absent, 1 each. revert the early return → red
- a keyrack daemon that can call `process.exit(2)` inside a jest worker is its own defect; consider a `reseed` dream to rhachet for a thrown error in place of the exit

safe, but not clean for this round: the commander froze the tree after the 23:09–23:35Z full-suite green, so an edit now would void that green before the 20:00 CT commit. ruled by the director: catch it as a dream.
