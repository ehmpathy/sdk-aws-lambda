## ⛔ .why it is REJECTED — and it is a PROOF, never a preference

> **the measurement that vindicates the sdk's behavior also refutes this dream's own recommendation.
> the two follow from ONE fact, so no later round can take the first and re-open the second.**

measured through a real wired handler, four candidates on one schema, each driven with a bad value:

| what the schema does | what the caller meets |
|---|---|
| `.transform()` + a bare `throw` | 🔴 a server fault |
| `.transform()` + a genuine null-deref | 🔴 a server fault |
| `.refine()` | ✅ a caller fault |
| `.transform()` + `ctx.addIssue()` + `return z.NEVER` | ✅ a caller fault, **reshape intact** |

**1. there is no defect.** rows 1 and 2 reach `getValidatedInput` as the same plain `Error` out of
the same `inst._zod.parse` frame, with no property that parts them. a guard-throw and a broken
transform are **indistinguishable by construction**, so the server-fault default is the only honest
read — and it is the safe direction to be wrong in.

**2. there is no absent affordance.** rows 3 and 4 are both zod's own documented api. a consumer who
wants a caller fault has two forms already, and row 4 guards **and** reshapes in one pass — the
mechanism `X.contract()` itself uses internally. this dream's premise, and F35's, was that no such
vocabulary exists. it exists, and it is not ours.

**3. 🔴 and the recommendation CANNOT be built correctly.** rung 4 asked for a hint that names
`ctx.addIssue` *"when the throw arrives from a transform frame"*. **both** rows 1 and 2 arrive from
a transform frame. so that hint would tell a consumer whose transform holds a genuine null-deref to
reach for `ctx.addIssue` — which would have them **disguise a server defect as a caller fault**. a
hint that is right half the time, and whose wrong half steers toward a `failhide`, is worse than
silence.

⇒ **the one fact under all three is the SAME indistinguishability.** it is what makes the behavior
correct (1), what makes the two forms a consumer's own choice rather than our gap (2), and what
makes the hint unbuildable (3). ⇒ **to re-open this dream, that fact must fall — and it is clamped
at `[case13][t3]` and `[case20][t3]`, both proven by revert.**

## .the gap, precisely

a consumer who wants a custom validation reaches for the natural thing:

```ts
schema: {
  input: z.object({
    spot: z.string().transform((v) => {
      if (!KNOWN_SPOTS.includes(v)) throw new Error(`unknown spot: ${v}`);  // 👎 the trap
      return v;
    }),
  }),
  output: z.null(),
}
```

that throw is a **caller** fault by intent and a **server** fault on the wire:

| family | what the caller meets |
|---|---|
| `forApiGateway` | a **500** |
| `forAskEndpoint` | a **FAILED invocation** — `FunctionError`, retried, alarmed |

there are **two** correct forms, and no signal points at either. the nearer is one word different:

```ts
      spot: z.string().refine((v) => KNOWN_SPOTS.includes(v), 'unknown spot'),  // 👍
```

⚠️ **AMENDED 2026-09-21 — `.refine()` is the WEAKER of the two, and this dream named only it.**
measured through a real `forAskEndpoint` handler, four candidates driven with the same bad input:

| what the schema does | what the caller meets |
|---|---|
| `.transform()` + a bare `throw` | 🔴 REJECTED — a plain `Error`, reported as a server fault |
| `.transform()` + a genuine null-deref | 🔴 REJECTED — a `TypeError`, reported as a server fault |
| `.refine()` | ✅ `BadRequestError` |
| `.transform()` + `ctx.addIssue()` + `return z.NEVER` | ✅ `BadRequestError` |

```ts
      spot: z.string().transform((v, ctx) => {
        if (!KNOWN_SPOTS.includes(v)) {
          ctx.addIssue({ code: 'custom', message: `unknown spot: ${v}` });
          return z.NEVER;
        }
        return asSurfSpot(v);     // 👍 guards AND reshapes, in one pass
      }),
```

⇒ **`.refine()` cannot reshape**, so it is no substitute for a consumer whose transform genuinely
converts — it forces them to write the guard and the conversion as two chained steps. `ctx.addIssue`
does both at once, and it is the mechanism **`X.contract()` itself uses** (`5.1` yield `:583`). so
the sdk's headline feature already rides this path, and not one record ever said a consumer may too.

⚠️ **and rows 1 and 2 are indistinguishable by construction.** a guard-throw and a broken-transform
throw both reach `getValidatedInput` as a plain `Error` out of the same `inst._zod.parse` frame — no
property parts them. so the server-fault default is no mis-report; it is the only honest read of an
ambiguous signal, and the safe direction to be wrong in.

⇒ **the gap is DISCOVERABILITY, never behavior.** that narrows what this dream and F35 both owe: a
consumer must learn that a bare `throw` means *"I malfunctioned"* and `ctx.addIssue` means *"you sent
me a bad value"*. no code change is owed to make the second one work — it already does.

**a consumer meets ZERO signal today.** `[case4]`/`[case13]`/`[case20]` clamp the behavior, and a
clamp reaches a traveler who reads the suite rather than a consumer who writes a schema. not one of
them fires at the keystroke, at the compile, or at the lint.

⚠️ **AMENDED 2026-09-20 — the readme is no longer a signal either, and that is deliberate.** it
carried the trap and the `.refine()` workaround for a while, and that section was cut: a readme
states how to use the sdk, so a defect written into one is a defect documented rather than
repaired — the workaround reads as the contract, and the repair stops being owed.

⇒ so the original framing of this dream was **too kind to the readme rung**. the readme was always
the weakest instrument for THIS trap, because the trap is what a consumer reaches for when they
have not read the readme — that is what makes it a trap rather than a documented choice. the cut
removed no protection a consumer held; it removed the appearance of one, and it raises what a real
signal is worth.

## .the shape of the fix

the rungs, best first (`rule.prefer.prevent-over-correct`):

1. **make it impossible** — 🔴 ruled out, measured. a type cannot part a `.transform()` that
   **coerces** (the headline usecase — `X.contract()` is one) from a `.transform()` that **guards**.
   both are `ZodType`, both carry the same `_zod.def.type`. so any type-level refusal would refuse
   the feature this sdk exists to publish
2. **make it hard** — a lint rule that flags a `throw` inside a `.transform()` callback within a
   `schema:` position, and names **`ctx.addIssue` + `z.NEVER`** in its message (with `.refine()` as
   the simpler form where no reshape is wanted). the same rung F36 named and the same config-scope
   question it raised — so **these two should be ruled together**, since one lint-config decision
   buys both
3. **make it detectable at runtime** — a `.transform()`-throw could be re-tagged at the boundary as
   a caller fault. 🔴 **this is `rule.forbid.failhide` outright**: an unknown throw from consumer
   code would be absorbed as a caller fault, so a genuine server defect inside a transform would
   report as a 400. **do not take this rung** — it is recorded here so the next traveler meets the
   refutation rather than re-derives the idea
4. **make it loud in the error** — the 500/FunctionError body could name **`ctx.addIssue`** in its
   hint when the throw arrives from a transform frame. cheapest real rung, and it is the one worth a
   measurement: `rule.require.errors-name-the-fix` asks exactly this

⇒ **rung 4 is the recommendation.** it fails no differently, it hides no fault, and it converts a
readme a consumer did not read into a hint they cannot miss — at the one moment they are certain to
look.

⚠️ **the 2026-09-21 measurement makes rung 4 a STRICTLY better hint than it was.** its message used
to offer `.refine()`, which drops the consumer's reshape — so a consumer who took the hint traded
one defect for a rewrite. it can now offer `ctx.addIssue`, which keeps their transform whole. **the
hint becomes a one-line repair rather than a redesign**, which is the difference between a hint a
consumer takes and one they argue with.
