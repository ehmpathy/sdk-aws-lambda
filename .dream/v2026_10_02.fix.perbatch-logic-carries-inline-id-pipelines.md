## .the gap, precisely

`logic` in `genLambdaEndpoint.forSqs.perBatch.ts` is an orchestrator, yet holds six inline
map/filter/Set pipelines (`rule.forbid.inline-decode-friction`):

- `idsClaimable` — `new Set(recordsValidated.map((record) => record.id))`
- `refsMalformed` — `successes.map((success, index) => …).filter(…typeof success?.id !== 'string')`
- `idsUnclaimable` — `successes.map(…id).filter((id) => !idsClaimable.has(id))`
- `idsSucceeded` — `new Set(successes.map(…id))`
- `idsFailed` — `[...new Set(records.map(…id).filter((id) => !idsSucceeded.has(id)))]`
- `batchItemFailures` — `idsFailed.map((id) => ({ itemIdentifier: id }))`

## .the shape of the fix

named transformers in `genLambdaEndpoint.forSqs/`, each with a data-driven unit test:
`getAllSqsIdsClaimable({ records })`, `getAllSqsSuccessesMalformed({ successes })`,
`getAllSqsIdsUnclaimable({ successes, idsClaimable })`, `getAllSqsIdsFailed({ records, successes })`,
`asSqsBatchResponse({ idsFailed })`. the `logic` body then reads as the three refusals and the
answer. `perBatch`'s extant `[case4]`/`[case9]`/`[case11]`/`[case16]` clamp the behavior through
the refactor unchanged.
