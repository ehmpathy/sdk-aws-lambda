# 🌙 dream: verify the stack field name the cloud wire carries — `trace` or `stackTrace`

- kind: fix
- owner: ehmpathy/sdk-aws-lambda
- caught 2026-10-22, in route `v2026_10_22.fix-local-locus-reads-error-name`

## .the cue that fired

the aws node runtime's `toRapidResponse` (`aws-lambda-nodejs-runtime-interface-client`, `src/Errors.js`) emits `{ errorType, errorMessage, trace }`. the local locus (`asWireFunctionErrorPayload`) emits `stackTrace`, and the client (`getParsedResponse.ts:109`, `getIsLambdaErrorResponse.ts:24`) reads `stackTrace`, with a note that "aws sends it on the wire".

## .the gap, precisely

unverified whether the Invoke api (or the runtime api) renames `trace` → `stackTrace` before the caller sees it. if it does not, a cloud error carries no stack in the parsed metadata while a local one does — a local/cloud divergence of the same class as #73, smaller in harm (diagnosis only, never classification).

## .the shape of the fix

1. invoke a deployed demo lambda that throws; capture the raw `Payload` (`howto.provision-demo-infra`)
2. if the field is `trace`: read `trace ?? stackTrace` in `getIsLambdaErrorResponse` / `getParsedResponse`, and emit `trace` from `asWireFunctionErrorPayload`; clamp both
3. if it is `stackTrace`: record the measured payload in `getIsLambdaErrorResponse.ts` so the note cites evidence

## .why it is not done in this round

it needs a live cloud invoke to measure, and it changes a field the client already reads — not small, and not part of the errorType fix this route owns.
