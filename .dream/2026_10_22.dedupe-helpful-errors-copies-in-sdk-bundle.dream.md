# 🌙 dream: one helpful-errors copy in the sdk's production tree

kind: fix · owner: sdk-aws-lambda · caught 2026-10-22

## .the cue that fired

`blackbox/deployed.faultLabel.acceptance.test.ts` bundles a raw handler with esbuild. the deployed message read `✋ ConstraintError2: order id malformed` and `💥 MalfunctionError2: upstream down`. a peer reviewer (5.3 i002, `ergo-snapshot-visual-blemishes`) flagged the `2` as a class no caller can find.

## .the gap, precisely

- `pnpm why helpful-errors`: the sdk's production deps pull `helpful-errors@1.7.3` (direct, plus `domain-objects`, `sdk-environment`, `sdk-logs`, `type-fns`), and `with-simple-cache@0.15.3` pulls `helpful-errors@1.5.3`
- so a bundle of the sdk holds two `ConstraintError` classes, and esbuild renames one by module order. a caller's message, and any `constructor.name` read, then names `ConstraintError2`
- the branch for sdk-aws-lambda#73 never touched `with-simple-cache`, so this holds on main too
- the caller-fault gate is not known to break: `getIsConstraintError` tries `instanceof` first, and a handler and the sdk that share the 1.7.3 copy pass it. a throw from the 1.5.3 copy, if any path makes one, reads by its own `.name` or prototype names, and a renamed constructor may fail the latter. unmeasured

## .the shape of the fix

1. bump `with-simple-cache` to a release that depends on `helpful-errors@1.7.x` (the lockfile already holds `with-simple-cache@0.17.3` for a dev peer); pin exact
2. assert one copy: `pnpm why helpful-errors` shows a single version under `dependencies`
3. drop `asHeadlineUnsuffixed` from `blackbox/deployed.faultLabel.acceptance.test.ts`, rerun with `--resnap`, and expect the snapshot to stay unchanged

## .why it is not done in the #73 fix

safe but not clean: a production dependency bump ripples into every consumer's tree, beyond a patch that fixes a label and an sqs disposition. fulcrum F22.
