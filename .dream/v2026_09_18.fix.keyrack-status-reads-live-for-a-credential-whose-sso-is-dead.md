# 🌙 dream: `keyrack status` reads `expires in: 28m` for a credential that cannot authenticate

- kind = reseed
- owner = `ehmpathy/rhachet` (the keyrack surface), **not** `ehmpathy/sdk-aws-lambda`
- caught 2026-09-18

## .the cue that fired

self review `r3.has-all-tests-passed` at stone `5.3.verification` re-ran every gate to satisfy the
guide's demand for verbatim proof. two of them — `integration` and `acceptance` — failed at the
keyrack unlock step. per `rule.require.retry-before-you-escalate` i took a fresh read before i
called it a wall:

```
$ rhx keyrack status --owner ehmpath
   ├─ ehmpathy.test.AWS_PROFILE
   │  ├─ env: test
   │  ├─ org: ehmpathy
   │  └─ expires in: 28m          ← reads LIVE
```

⇒ **so i retried, on the strength of that line.** it failed identically:

```
$ rhx git.repo.test --what integration --mode apply --thorough
   ├─ status: malfunction
   └─ error: keyrack unlock failed
      └─ CredentialsProviderError — Token is expired. To refresh this SSO session
         run 'aws sso login' with the profile it names.
```

## .the gap, precisely

**`status` reports the lifetime of the keyrack LEASE. it does not report the lifetime of the aws
SSO token that lease depends on.** the two are independent clocks, and only one of them is on the
page.

| clock | who holds it | shown by `status`? |
|---|---|---|
| the keyrack lease | keyrack | ✅ `expires in: 28m` |
| 🔴 the aws sso token behind it | aws | **no** |

so a credential in this state reads **green** on the one surface built to answer *"is this
usable?"*, and is **dead** the moment a caller uses it.

### 🔴 the two clocks, MEASURED rather than argued

the section above was a diagnosis. one hour later, at self review `r5`, a second read was taken per
`rule.require.retry-before-you-escalate` — and it settles the claim:

| read | `ehmpathy.test.AWS_PROFILE` | the credential | does `status` tell the truth? |
|---|---|---|---|
| `[t0]` at the gate failure | `expires in: 28m` | dead (sso expired) | 🔴 **no** |
| `[t1]` ~1 hour later | `expires in: 1m` | dead — unchanged | 🔴 **no** |
| `[t2]` a few minutes later | **the row is ABSENT** | dead — unchanged | ✅ yes — *by coincidence* |

⇒ **the lease clock ticked down normally, by the wall time elapsed, across an hour in which the
credential authenticated not once.** that is the two clocks, observed rather than inferred: one
counts, the other is already stopped, and only the counter is on the page.

### ✅ `[t2]` is a PREDICTION this dream made, and then met

the paragraph below was written at `[t1]` and said the false green would heal *"within about a
minute"*. `[t2]` is that prediction, measured — and the unlock attempt at the same instant reports
the second clock in plain words for the first time:

```
🔓 keyrack unlock ehmpathy.test.AWS_PROFILE
   ├─ with sso prior?
   │  └─ ✗ clear, no prior session
```

⇒ 🔴 **`unlock` knows. `status` does not ask.** the sso state was legible to the toolchain at every
one of the three reads; only the surface built to answer *"is this usable?"* omitted it. that moves
rung 1 from *"add a clock we would have to compute"* to *"print a fact a peer command already
holds"*, which is a materially cheaper fix than this dream first supposed.

⚠️ **and it sharpens the defect rather than softens it — the false green is TRANSIENT.** within
about a minute the lease reads expired and `status` will agree with reality *by coincidence*. so the
window in which the surface lies is bounded and unpredictable: a robot that arrives inside it burns
a retry and writes a false claim, and one that arrives a minute later sees a correct row and cannot
reproduce the report. **a defect that heals itself is a defect nobody reproduces**, which is why
rung 1 (show the sso clock) is worth more than its one line of output suggests.

### why it is failhide-shaped

`rule.forbid.failhide` (mechanic) names the class: a green signal that verified none. that is
precisely this — `status` renders a healthy row, and the health it measured is not the health the
reader wants.

and the cost is measurable in exactly the way this branch measured it:

- a robot takes the fresh read, sees `28m`, and **retries** — one wasted run
- `rule.require.retry-before-you-escalate` mandates that read, so the rule and the surface
  disagree: the surface tells the robot to retry, and the retry cannot succeed
- ⇒ **the one discipline built to prevent a false escalation is fed a false input by the tool it
  is told to trust**

⚠️ and the inverse is worse: a robot that reads `28m` and reports *"credentials are live"* into a
review artifact ships a claim that is false at the moment it is written.

## 🔴 .the axis nobody had seen — the surface fails in BOTH directions

`rule.require.retry-before-you-escalate` was **born** from an incident on a peer branch where this
same surface was read and was **correct**:

> `.behavior/v2026_08_03.feat-apigateway-wire-response/5.1.execution.from_vision.yield.md:348`
> *"the human corrected me: `rhx keyrack status --owner ehmpath` reads … **live.** … the run, once
> I simply retried: **242 passed**"*

⇒ so the rule's whole remedy — *"take a fresh read"* — was validated against a case where the read
told the truth. swept across all three known directions:

| axis | what `status` says | the truth | known before now? |
|---|---|---|---|
| a read without `--owner ehmpath` | **locked** | live | ✅ `howto.keyrack` names it a trap |
| the peer branch's incident | **live** | live | ✅ the rule's founding case |
| 🔴 **this incident** | **live** | **dead — sso expired** | **no** |

⚠️ **row 3 was measured a fourth time on 2026-09-20 — see `[t3]` below — and it widened.** the false
green reaches every `aws.params`-backed credential, at an independent clock each, and one of them
read **339m**.

⚠️ **a fresh read of a surface that lies green is still a lie.** so the rule is sound for rows 1–2
and silent on row 3 — and row 3 is the one where an obedient robot burns a retry, then may write
*"credentials are live"* into an artifact on the strength of it.

⇒ **the fix below closes the gap in the rule as well as in the tool**, which is why the rung-1
recommendation is a display change rather than a doc change: give the reader the second clock and
row 3 stops to exist.

## 🔴 .`[t3]`, 2026-09-20 — a FOURTH read, days later, and it WIDENS the defect

taken on a fresh session while stone `5.1` was halted. `[t0]`–`[t2]` all measured **`AWS_PROFILE`**,
so the report read as a defect of one credential. it is not.

| what `status` printed | what an unlock of it returned |
|---|---|
| `ehmpathy.test.FIREWORKS_API_KEY` — `expires in: **339m**` | 💥 `errored` — `CredentialsProviderError — Token is expired` |
| `ahbode.test.FIREWORKS_API_KEY` — `expires in: **255m**` | (same dead sso behind it) |
| `ehmpathy.test.AWS_PROFILE` — **absent** | 🚫 `✗ clear, no prior session` |

⇒ **the false green is not confined to `AWS_PROFILE`.** every credential keyrack resolves through
`aws.params` inherits that dead sso, and each renders **its own independent lease clock** — so the
surface showed **two** healthy rows, one at 339m, for secrets that could not be fetched.

⚠️ **and `339m` is a far worse lie than `28m` was.** the earlier window healed within a minute
(`[t2]`), which bounded the damage. a five-and-a-half-hour lease on a dead credential does not heal
— a robot that reads it is told *"live, and live for the rest of your session."*

⇒ so rung 1 (**print the sso clock**) must show it **once, at the top**, never per row. the sso
token is one shared dependency, and a per-row lease renders it N times as N different healthy
numbers, which is precisely the shape that produced this read.

🟡 **the tell that this is one dependency, not N:** `status` names `daemon: active ✨` at the top
already. the sso clock belongs in that same block, beside it.

## .the shape of the fix

three rungs, cheapest first:

1. **surface the sso clock beside the lease clock** — one extra line per aws-backed row.
   `sso: expired` / `sso: 43m` is the whole fix, and it makes the two clocks visibly distinct
2. **fail the row loud** — where the sso token is expired, render the row `🔴 expired` regardless
   of the lease, since the lease is worthless without it
3. **verify on read** — `status` performs a cheap `sts:GetCallerIdentity` per aws profile. the
   strongest, and it costs a network call per row

⇒ **rung 1 is the recommended first move.** it adds information and removes no other, so it cannot
regress a reader who today relies on the lease number.
