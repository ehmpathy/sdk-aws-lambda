# 🌙 dream: the `sqs.record.refused` line names whether the schema or the handler refused

- kind: feature
- owner: sdk-aws-lambda
- caught: 2026-10-22, route `v2026_10_22.fix-local-locus-reads-error-name`, stone 5.1

## .the cue that fired

`enroll-impl-arch-defects` (5.1, i004, nitpick.1): a `ConstraintError` from our own handler — a downstream 4xx caused by our own bad request — writes the same `sqs.record.refused` line as a producer's schema refusal, and the message is deleted with no alarm.

## .the gap, precisely

- `logSqsRecordRefused` writes `{ id, class, errorMessage, consequence }`. no field says who refused
- `perRecord`'s one `try` wraps validate, freeze, and invoke, so its catch cannot tell the two apart today
- `setSqsRecordsValidated` (perBatch) only ever sees schema refusals, so its origin is always `schema`

## .the shape of the fix

1. `logSqsRecordRefused` takes `origin: 'schema' | 'handler'` and writes it on the line
2. `perRecord` splits its `try`: validation in one, the invoke in another, each catch composes `asCallerFault` and passes its own origin
3. `setSqsRecordsValidated` passes `origin: 'schema'`
4. readme: an alarm on `origin: 'handler'` catches a handler that refuses messages it should have retried
5. clamps: `logSqsRecordRefused.test.ts` pins both origins; perRecord `[case4]` asserts `schema`, `[case10][t1]` asserts `handler`

## .why it is not done in this round

safe, but not clean: it splits perRecord's catch, which this round's reviewers already graded twice, and it adds a field to a log contract that operators alarm on. the human's ruled policy stands without it; it is an observability gain, so it earns its own change.
