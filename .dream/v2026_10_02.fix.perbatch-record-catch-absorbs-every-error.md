# 🌙 dream: perBatch's per-record catch absorbs every Error, not only a validation refusal

kind: fix · owner: sdk-aws-lambda · caught 2026-10-02

## .the cue that fired

peer review `mech-failhides` on route `v2026_10_01.fix-frozen-deep-branded-primitives`, stone 5.1,
raised it as a blocker. that branch touched `genLambdaEndpoint.forSqs.perBatch.ts` only at its import
line, so the catch is pre-extant (shipped in 0.7.0, #46).

## .the gap, precisely

`genLambdaEndpoint.forSqs.perBatch.ts`, the validation loop:

```ts
} catch (error) {
  if (!(error instanceof Error)) throw error;
  log.warn('sqs.record.invalid', { id: record.id, errorMessage: error.message });
}
```

- the validator (`setSqsRecordValidated` → `getValidatedInput`) throws a `ConstraintError` from
  `getValidationError` for a schema refusal — that is the one population this catch exists for
- any other `Error` thrown inside the parse — a throw from inside an author's zod `.transform` (a dobj
  constructor via `.contract()`, a bug), which zod rethrows rather than collects — is labeled
  `sqs.record.invalid` at `warn` and the record is retried alone. the label is false, and a defect
  reads as caller fault (`rule.forbid.failhide`: the catch holds no allowlist)

## .the shape of the fix

```ts
} catch (error) {
  if (!(error instanceof ConstraintError)) throw error;   // only a validation refusal is absorbed
  log.warn('sqs.record.invalid', { ... });
}
```

plus a clamp: a schema whose `.transform` throws a plain `Error` → the invoke throws (red under the
current catch, green under the allowlist).

## .why it is not done in that round

**not SAFE for a patch.** the allowlist changes run-time behavior: today a non-validation throw fails
ONE record; under the fix it escapes `logic`, so the whole batch fails and sqs redelivers every
record — siblings the handler already processed included. for a handler with non-idempotent effects
that is duplicate work. that is a behavior change a consumer should meet in a release note, not
inside a types-only 0.7.1 whose wish is #48. a judged deferral, so it carries fulcrum F5 on that
route.

the alternative worth a look when this is picked up: keep the record-level disposition but log a
non-validation throw at `error` with its class, rather than escalate to the whole batch.
