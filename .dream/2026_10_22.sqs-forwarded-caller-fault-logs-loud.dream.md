# 🌙 dream: a perBatch handler's forwarded ConstraintError logs loud

kind · fix · owner sdk-aws-lambda · caught 2026-10-22

## .the cue that fired

`enroll-impl-arch-defects` (5.1, i005, nitpick.1): a `ConstraintError` a `perBatch` handler throws redrives the whole batch (F8), yet the sdk writes no `handler.error` line for it.

## .the gap, precisely

- `genInternalServiceErrorMiddleware.ts` returns early on `getIsConstraintError`. that is right for `forAsk` and `forApiGateway`, where `genConstraintErrorMiddleware` answers the fault
- the sqs chain (`genSqsEndpointMiddlewares.ts`) registers no constraint middleware, so the throw escapes unlogged by the sdk. aws still records the invoke error in cloudwatch
- `forAsk` also passes `asOutputAfter: false`, so that flag cannot stand in for "no one answers a caller fault"
- true on main too: the chain is unchanged by this route

## .the shape of the fix

- an explicit opt on `genInternalServiceErrorMiddleware`, e.g. `callerFault: 'answered-downstream' | 'log-and-rethrow'`, set by each family. sqs passes `'log-and-rethrow'`
- or `perBatch` wraps its `invoke` call: log `sqs.batch.forwarded` at error, then rethrow
- clamp: perBatch `[case7][t1]` spies on `console.error` and asserts the line

## .why it is not done in this round

safe but not clean: it adds a field to a middleware contract three families share, in a route whose wish is the wire label. the fault is not hidden — the invoke fails, aws logs it, sqs redrives.
