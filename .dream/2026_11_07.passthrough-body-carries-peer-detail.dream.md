# 🌙 dream: decide whether a pass-through 400 body should carry the peer's url and headers

- kind: decision, then a small feat
- owner: the commander of sdk-aws-lambda
- caught 2026-11-07

## .the cue that fired

a peer review of `local.askApiGateway [case3][t1]` saw the pass-through 400 body carry the peer's `url`, `status`, and `connection` / `keep-alive` / `date` headers. the default 500 body holds none of them (inventory row 16).

## .the gap, precisely

under `refusal: { as: 'ConstraintError' }`, the consumer rethrows the peer's `ConstraintError` with its metadata whole, byte for byte as before #77. an api-gateway consumer then answers its own caller 400 with that metadata in `error.details`. so an end caller sees an internal peer url and the peer's response headers.

this is the old behavior, held on purpose: pass-through restores it. whether "old behavior" should include detail an end caller has no use for is a scope call the wish did not make.

## .the shape of the fix

if trimmed: `asErrorFromPeerRefusal` pass-through arm builds the `ConstraintError` with metadata minus `url`, `headers`, `status`. it retains `exid`, `correlationId`, and the peer's own `issues` / `hint`. one file, plus the snapshots of `local.askApiGateway [case3][t1]`, `getParsedResponse [case1..9]`, and the `asErrorFromHttpResponse` pass-through rows.

## .why it is not done in this round

pass-through is defined as the old class with the old message and metadata, byte for byte. a trim would move pass-through away from the old behavior, which is the commander's call, not the driver's.
