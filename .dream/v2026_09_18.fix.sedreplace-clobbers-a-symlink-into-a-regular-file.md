# 🌙 dream: `sedreplace` clobbers a symlink into a regular file

- **kind** = reseed → `ehmpathy/rhachet-roles-ehmpathy` (the mechanic skill `sedreplace`)
- **owner** = unclaimed
- **caught** = 2026-09-18, at stone `5.3.verification`, self-review `r7.has-ergonomics-validated`

## .the cue that fired

`sedreplace` reported **success** on two paths that were symlinks. a grep of the link targets then
showed the old text still present.

> 🔴 **the report and the state disagreed, and the report was the confident one.** that gap is the
> whole defect — a tool that says `updated` while the file it names is untouched.

## .the gap, precisely

`sedreplace` does not follow a symlink. it **writes through it as a new regular file**, so:

1. the link is destroyed and replaced by a copy of the target's content
2. the replacement is applied to that copy
3. **the real target is never touched**
4. the tool reports `updated`

### checkable evidence — measured on this branch

```
$ rhx sedreplace --old 'r6.has-ergonomics-validated' --new 'r7.has-ergonomics-validated' \
      --glob '.behavior/**/*.md' --mode apply
   ├─ files: 3
   ├─ matches: 6
   └─ updated
      ├─ .../5.3.verification.yield.md (2)
      ├─ .../dreams/v2026_09_18.fix.genservicesdk-takes-a-log-and-emits-no-status.md (2)   ← a symlink
      └─ .../dreams/v2026_09_18.fix.the-error-payload-carries-its-metadata-twice.md (2)    ← a symlink
```

then, against the link targets:

```
$ rhx grepsafe --pattern 'r6.has-ergonomics' --path .
  .dream/v2026_09_18.fix.the-error-payload-carries-its-metadata-twice.md:5:   ... `r6.has-ergonomics-validated`
  .dream/v2026_09_18.fix.the-error-payload-carries-its-metadata-twice.md:104: ... r6.has-ergonomics-validated.md
  .dream/v2026_09_18.fix.genservicesdk-takes-a-log-and-emits-no-status.md:5:   ... `r6.has-ergonomics-validated`
  .dream/v2026_09_18.fix.genservicesdk-takes-a-log-and-emits-no-status.md:87:  ... r6.has-ergonomics-validated.md
```

and the link check, with a **positive control** — an untouched peer in the same directory:

```
$ file .../dreams/v2026_09_18.fix.the-error-payload-carries-its-metadata-twice.md \
       .../dreams/v2026_09_18.fix.genservicesdk-takes-a-log-and-emits-no-status.md \
       .../dreams/v2026_09_18.fix.the-blackbox-suite-imports-src-never-dist.md

  ...the-error-payload-carries-its-metadata-twice.md:  Unicode text, UTF-8 text, with very long lines (429)
  ...genservicesdk-takes-a-log-and-emits-no-status.md: Unicode text, UTF-8 text
  ...the-blackbox-suite-imports-src-never-dist.md:     symbolic link to ../../../.dream/...
```

⇒ **the two `sedreplace` touched are regular files; the one it did not is still a link.** the
control is what makes this a measurement rather than a guess — the three sit in one directory, were
created by the same `rhx symlink` command, and differ only in whether `sedreplace` ran over them.

## .why it matters beyond a stale string

`rule.always.catch-dreams-for-followups` makes the symlink **the provenance**:

> *"its location IS the provenance — no prose citation to drift."*

so a clobbered link is not a cosmetic loss. it silently converts a live reference into a **frozen
copy**: the route still shows a dream, the `.dream/` queue still holds one, and the two now drift
apart with no signal. a reader of either would never learn the other exists.

🔴 **and `--mode plan` cannot warn you.** the plan output is byte-identical for a symlink and a
regular file, so the preview a driver is forced to run offers no tell at all.

## .the shape of the fix

in the skill, before the write — expand the link to its real target:

```sh
# expand a symlink to its target, so the edit lands on the real file
target="$(readlink -f "$file")"
```

plus a **loud** line in the output when a path expanded elsewhere, since a silent follow is its own
surprise:

```
├─ .../dreams/v2026_09_18.fix....md (2)   ↪ followed to .dream/v2026_09_18.fix....md
```

⚠️ the alternative — **refuse** a symlink and name it — is also defensible and may be safer:
a bulk find-and-replace that quietly reaches outside its stated glob is a surprise of a different
kind. either verdict is better than the current one, which is to destroy the link and report
success.

**the sweep this owes** (`rule.require.sweep-the-defect-class`): the cause is *"a mechanic file
skill that writes a path without a symlink check"*, so grep the **subject** — every skill that
writes to a path — never the form of `sedreplace`'s write. `teesafe`, `cpsafe`, and `mvsafe` are
the peers and each should be checked, not assumed.

## .why it is not done in this round

- 🔴 **it is ANOTHER REPO.** the skill lives in `ehmpathy/rhachet-roles-ehmpathy`; a tree adopts
  only what is scoped to itself. this is a `reseed`, and **caught is not dispatched** — `.dream/` is
  the local queue
- the damage on this branch **is already repaired**: both links were deleted, the targets corrected
  by hand, and the links re-created with `rhx symlink --idem findsert`, then verified with `file`
