# 🌙 dream: lift `x-trail-exid` out of sqs/sns message attributes

kind: feat · owner: sdk-aws-lambda · caught 2026-10-15

## .the cue that fired

the #51 vision moves the http opt-in onto the `x-trail-exid` header. the foreman's design scoped
`forSqs.*` as "build now if the read is one codepath with api gateway; else record as next". it is
not one codepath (F3).

## .the gap, precisely

- `asSqsRecordDecoded.ts` reads no `exid`; `genTrailMiddleware` matches the wrapper only. a producer
  that sets `x-trail-exid` on an sqs message is ignored, and the trace breaks at the queue
- `trail.md` lists the sqs lift as unbuilt

## .the shape of the fix

🔴 the send side comes first — the wisher: *"we should first decide how we would even slap trail
exids onto those messages to begin with"*. open questions, in order:

1. who sends: this sdk has no sqs/sns sender today. a producer calls the aws sdk itself. does this
   sdk ship a sender (`sendSqsMessage`-like) that sets the attribute, or only a cast that a
   producer spreads into its own `MessageAttributes`?
2. which exid: the producer's `context.log.trail.exid` at send time — one per message, or one per
   `SendMessageBatch` call?
3. then the receive side, below

receive side, once the send side is settled:

- read `messageAttributes['x-trail-exid'].stringValue` from the reconciled per-record headers
- trail only — no dialect branch (`invariant.ancient-vs-contemp-callers.md`)
- decide the batch grain: one invoke, one trail. `perBatch` needs a rule for ten records with ten
  exids (first? a fresh one plus a log of each?); `perRecord` may scope a child log per record
- a send-side cast per bag, peer of `asTrailExidHeaders`: e.g. `asSqsMessageAttributes`, which
  emits `{ 'x-trail-exid': { DataType: 'String', StringValue } }`
- sns the same, via `MessageAttributes`; kinesis has no bag

## .why it is not done in this round

not clean: the batch-grain rule is a new decision, and #51 is an api gateway defect that needs none
of it.
