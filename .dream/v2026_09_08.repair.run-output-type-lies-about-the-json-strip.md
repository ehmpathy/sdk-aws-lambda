# 🌙 dream: `LambdaEndpointRunOutput` must model the JSON strip it performs

- **kind** = repair
- **owner** = `ehmpathy/sdk-aws-lambda`
- **caught** 2026-09-08, at self-review r6 of `v2026_09_03.feat-absorb-handler-invoke-test-util`

## .the cue that fired

I added `asLambdaEndpointOutput` — the success-side narrow — and wrote a clamp to prove it infers
the output type rather than collapses to `unknown`. the annotation I reached for was the one the
demo taught:

```ts
const out: { scheduledAt: string } = asLambdaEndpointOutput(res);
```

the gate rejected it:

```
error TS2322: Type '{ scheduledAt: Date; }' is not assignable to type '{ scheduledAt: string; }'.
  Types of property 'scheduledAt' are incompatible.
    Type 'Date' is not assignable to type 'string'.
```

**both sides are right, and that is the defect.** the handler declares `Date`; the util JSON-strips
its output, so the value is a `string`.

## .the gap, precisely

`LambdaEndpointRunOutput<TOutput, TDialect> = TOutput | LambdaEndpointErrorEnvelope<TDialect>`
carries `TOutput` **as the handler declares it**. but `runLambdaEndpoint.onReferenced` returns
`asWireStripped(output)` — `JSON.parse(JSON.stringify(x))` — so every `Date` becomes a `string`,
every `undefined` field vanishes, and every class instance flattens to a plain object.

⇒ **the return type describes a value the util never returns.**

checkable evidence:

| | what the type says | what the value is |
|---|---|---|
| `Date` | `Date` | `string` (iso) |
| an `undefined` field | present, optional | **absent from the object** |
| a class instance | the class | a plain object, methods gone |

and the consumer-visible failure:

```ts
const out = asLambdaEndpointOutput(res);
out.scheduledAt.toISOString();   // ✅ compiles · 💥 "toISOString is not a function"
```

🔴 **this contradicts the very lesson `case=4` exists to teach.** that demo's whole point is *"the
strip runs on the way out too"* — and the type tells the reader otherwise. so the artifact that
teaches the strip and the type that models it disagree.

🟡 **it is a prior defect, and my narrow is what made it REACHABLE.** before `asLambdaEndpointOutput`
a consumer could not read a field off the union at all, so the unsoundness had no expression.

🔴 **and it applies to `onSerialized` too — verified, rather than assumed.** this paragraph asserted
that in its first draft with no read behind it, which is the defect this dream exists to record,
committed in the artifact that records it. traced:

| locus | where the jsonify happens |
|---|---|
| `local` | `runLambdaEndpoint.onSerialized.ts` — `JSON.stringify(output ?? null)`, then `getParsedResponse` parses it |
| `cloud` | `askLambdaEndpoint` → the real wire → `getParsedResponse` (`:41` parse, `:116` return) |

⇒ `onSerialized`'s `Promise<TOutput>` is unsound for the same reason, and **a second example
surfaced in that read**: a handler typed `void` yields a value that is `null`. so the defect holds
on two independent shapes, not one.

## .the shape of the fix

a `Jsonified<T>` mapped type, applied where `TOutput` enters the run output:

```ts
type Jsonified<T> =
  T extends Date                    ? string
  : T extends (infer U)[]           ? Jsonified<U>[]
  : T extends object                ? { [K in keyof T as undefined extends T[K] ? never : K]: Jsonified<T[K]> }
  : T;

export type LambdaEndpointRunOutput<TOutput, TDialect extends LambdaEndpointDialect> =
  Jsonified<TOutput> | LambdaEndpointErrorEnvelope<TDialect>;
```

⚠️ **the optional-key clause is the hard half, and it should be settled before the rest is written.**
`JSON.stringify` drops a key whose value is `undefined`, so a strictly faithful model removes
optional keys entirely — which is correct and hostile, since `{ a?: string }` becomes `{}`. a
kinder model keeps the key optional and is then unfaithful under `exactOptionalPropertyTypes`.
**pick one deliberately; do not let the first draft decide it.**

also settle: `Map`/`Set` (→ `{}`), `bigint` (→ throws), and a `toJSON()` method (→ its return type,
which a mapped type cannot reach).

## .why it is not done in this round

**it fails CLEAN** (`rule.always.fix-forward-under-scouts-honor`):

- it changes the public return type of BOTH boundary operations
- it ripples into every test that names an output type, and into the two case demos that show one
- the `Date` case is one line; the optional-key semantics is a design decision that wants its own
  review, not a ride-along in a self-review round

it passes SAFE — types only, no runtime change — which is exactly why it is tempting, and why the
deferral needed a fulcrum rather than only this dream.

## .what was done instead

1. the discrepancy is **clamped, not merely noted** — `advertisedExamples.test.ts` `[case8][t2]`
   asserts `typeof out.scheduledAt === 'string'` under an annotation that says `Date`, so the lie is
   pinned and cannot drift unnoticed
2. `asLambdaEndpointOutput`'s docblock carries the ⚠️, the failing call, and a pointer here
3. raised as **fulcrum F13**, so the deferral is reviewable rather than only recorded
