### 🐛 a latent bug the conformance exposed

the handler's declared input was `APIGatewayProxyEvent` — **v1 only** — while the family accepts
v1 **or** v2. that is exactly what `genApiGatewayEventNormalizationMiddleware` exists to unify, so
the outer type understated what the handler takes: a v2 caller was accepted at run time and
**rejected at compile time** by anyone who typed against the returned handler.

`ApiGatewayRequestPayload` is the union, so the declaration now matches the behavior. tsc confirmed
the mismatch was real rather than cosmetic — the first attempt failed with

```
Type 'APIGatewayProxyEventV2' is not assignable to type 'APIGatewayProxyEventBase<...>'
```

which is the v2 case the old signature could not express.

**the vision had this wrong too** — it declared `ApiGatewayRequestPayload` as `inputBefore` and then
typed the handler `MiddyfiedHandler<APIGatewayProxyEvent, …>` in the same code block. a name that
does not reach the boundary it describes buys no one anything; corrected in both places.

the `as unknown as` cast at the middy construction **stays** — the chain translates both ends and
tsc cannot track a transform across `.use`. it is now documented with `.as` / `.removal` per
`rule.forbid.as-cast`, and it names the two outer shapes rather than AWS's raw types.

### 🐛 the vision's `body: ''` row, falsified

the vision said a body-less 204 emits `body: ''` "since `APIGatewayProxyResult.body` is a required
string". that rested on the AWS type alone, never on a run. a probe of the real chain shows
`body: ''` becomes **`'""'`** — the serializer `JSON.stringify`s it — unless a `Content-Type` is
already set, and a 204 must not carry one.

so the body must be **omitted**, which makes `ApiGatewayResponsePayload.body` genuinely optional.
declaring it so rather than leaving the cast to hide it (`rule.require.shapefit`) forced 24
`JSON.parse(result.body)` sites to reckon with absence — resolved with one named test reader,
`asParsedResponseBody`, which fails loud rather than let each site assert a non-null
(`rule.require.named-transformers`). that also deleted a `result.body!` which predated this work.

corrected in the yield's edgecase table, in its surface block, in `ApiGatewayResponse.body`'s note,
and in the appendix's coverage table. probe recorded in `appendix/verification.md`.

### 🚧 the blocked fulcrum — where does `inputAfter` live?

**the constraint the vision did not account for:** `@middy/http-cors` reads the **request** off
`request.event` in its `after` hook — `request.event.headers` at line 83, and the http method
derived from `request.event` at lines 38 and 106 (`@middy/http-cors/index.js`, v5.5.1). so
`request.event` must stay **http-shaped** for the whole chain.

⚠️ **a first draft of this note said `@middy/http-security-headers` reads it too. it does not** —
that package touches only `request.response` (`index.js:237,239,246,251`). the claim was inferred
from the two packages' shared role rather than read, and it reached two code comments before a
grep of the dist caught it. the constraint stands on cors alone; one vendor reader is enough to
make the slot untouchable. enbriefed as `rule.require.read-the-slot-a-dependency-reads`.

the vision's model says the input translator turns `inputBefore` into `inputAfter`, and the
natural middy seam for that is `request.event = translate(request.event)`. that seam **starves
both middlewares**: with `request.event` overwritten by the bare body, cors emits no headers at
all. found by a real test, never by inspection — `[case3]`'s cors assertions went undefined the
moment the translate middleware ran.

so the api-gateway family carries `inputAfter` at `event.body` while the ask-endpoint family
carries it at `event` itself. that asymmetry is the root of two live defects, each now marked in
code with a `.removal` / `.note` that cites this section:

| site | the smell |
|---|---|
| `genLambdaEndpoint.forApiGateway.ts` — the logic fn | `event.body as TInput` — an `as`-cast that asserts the relation the translator should derive |
| `genIntrospectionMiddleware.ts` | `opts.apiGateway ? request.event?.body : request.event` — a config fork, i.e. a `rule.forbid.parallel-codepaths` violation |

**three candidate homes, none a defensible best-guess:**

1. **`request.internal.eventAfter`** — middy's own sanctioned side-channel. keeps `request.event`
   http-shaped. but `internal` is middy-specific, so the ask-endpoint family would either adopt
   middy's idiom for no reason or the two families diverge again.
2. **`context.eventAfter`, uniform across both families** — one home, both chains, and the
   introspection fork collapses. but it re-purposes `context` (a dependency bag) to carry data,
   which reads against `rule.require.input-context-pattern`.
3. **a symmetric overwrite/restore inside the translate middleware** — set `request.event` to
   `inputAfter` in `before`, restore the http shape in `after` before cors runs. one home, no new
   channel — but it depends on where middy runs its `after` hook relative to two third-party
   middlewares, and a dependence on hook order is exactly what breaks silently on a dependency
   bump.

**why this is a block and not a best-guess** (per `rule.always.defer-fulcrums-to-last`): the
rework is **not clean**. whichever channel wins is read by 4 middlewares across 2 families and
is baked into the public `Translate` contract, so a wrong guess forces a teardown rather than a
rename. and the wish's `.acceptance` has **no line** that this serves — the response work is
complete and green without it.

**what this costs on the wire today: zero.** every acceptance line is met. the `Translate` type
ships as vocabulary (phase 4), the output translator ships registered, and the input translator
is the one piece deferred.

### 🚩 a repo-wide defect for the wisher — NO snapshot in this repo clamps

found while r8 verified the clamp above, and **not fixed, deliberately**.

unset, `$RESNAP` leaves `[ -n ]` — a single-argument `test`, which POSIX evaluates as *"is the string

#### the defect

`isApiGatewayResponse` validated **cardinality only** — `'status' in input || 'headers' in input ||
