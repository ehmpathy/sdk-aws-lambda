# case=3 — a stale name fails at compile, loudly

**cell** `A2·B3·D2·E1` · **feel** sharp · **care** 🔴 critipath · **density** 1

## the narrative

squirt migrates a service off `simple-lambda-handlers`. the org's migration guide says, in as many
words:

> `declapract-typescript-ehmpathy/…/simple-lambda-handlers/.declapract.readme.md:35`
> *"thread headers via `rawEvent.headers`"*

so squirt writes exactly that, upgrades the sdk, and:

```
error TS2339: Property 'rawEvent' does not exist on type
  '{ headers: Record<string, string | undefined>; payload: TInput; event: UnifiedApiGatewayEvent }'.
```

**this is the good outcome.** squirt reads the type, sees `headers` right there in the error, and
the fix is *shorter* than the broken line:

```ts
- const sig = rawEvent.headers['x-sig'];
+ const sig = headers['x-sig'];
```

**the failure mode this avoids** is the one a both-fields deprecation release would create: both
names compile, squirt keeps the stale one, the deprecation note goes unread, and the break merely
moves to a later release where nobody remembers the reason. a clean break spends the surprise once,
at compile time, with the fix on screen.

## 🔴 the SECOND stale name — `event`, which keeps its word and changes its type

⚠️ **this case originally claimed a `{ event }`-only handler compiles UNCHANGED. that is now
false**, and what made it false is the whole verdict: `event` no longer denotes the body.

| the handler writes | before | after | the compiler |
|---|---|---|---|
| `{ rawEvent }` | ✅ | ⛔ absent key | 🔴 **loud at the destructure** |
| `{ event }`, then `event.jobUuid` | the body | the envelope | 🔴 **loud at the use** — the envelope has no `.jobUuid` |
| `{ event }`, then `body: event` | the body | the envelope | 🔴 **loud**, if the receiver types its param |
| `{ event }`, then `event.path` | the body | the envelope | ⚠️ **silent** — both shapes have `path`. see below |

⇒ so the break is **two** renames under one diff, and only the first announces itself at the
destructure. the second is the one that owed a measurement.

### the measurement — 0 silent collisions

a silent break needs a field name present on **both** the old body and the new envelope. measured
against the real consumer, each with the positive control `rawEvent.headers` → **129**:

| the collision candidate | consumer reads |
|---|---|
| `event.path` | **0** |
| `event.httpMethod` | **0** |
| `event.queryStringParameters` | **0** |
| `event.pathParameters` | **0** |
| `event.isBase64Encoded` | **0** |
| `event.headers` ×5, `event.requestContext` ×1 | ✅ **false positives** — raw-signature handlers that never call `invoke` |

⇒ **zero real collisions.** every stale `event.<x>` site fails to compile.

and the receiver check holds too: the real consumer types its body param
(`sendQuote.ts:34-39` — `body: { jobUuid: string; providerUuid: string; … }`), so a stale
`body: event` is a compile error rather than a runtime surprise.

## the bdd sketch

```
given [case3] a handler written against the prior shape

  when  [t0] it destructures `{ rawEvent }`
  then  typescript refuses it
  and   the error names the three keys that DO exist
  and   `headers` is among them, so the fix is visible in the error itself

  when  [t1] the handler is corrected to `{ headers }`
  then  it compiles
  and   the read is one hop shorter than the line it replaced

  when  [t2] a handler destructures `{ event }` and reads a BODY field off it
  then  🔴 typescript refuses it — `event` is now the envelope
  and   the error names the envelope's own fields, so the reader meets the new sense
  ⇒ the rename is LOUD at the use site, not merely at the destructure

  when  [t3] the handler is corrected to `{ payload }`
  then  it compiles
  and   the read is the same length it always was

  when  [t4] a handler destructures `{ event }` and reads an ENVELOPE field off it
  then  it compiles — and it is now CORRECT rather than accidentally correct
  ⇒ the positive control: measured 0 such sites in production, so this arm
     is a clamp against a future silent read, never a migration path
```

⚠️ `[t2]` is the assertion that carries the weight, and it **replaces** an earlier `[t2]` that
claimed the opposite. a rename that changes a type under an unchanged word is the one shape a
compiler can miss, so it owes a clamp rather than a confidence.

## what makes it a critipath

- it is the **only** sharp-feel cell a real consumer will meet, and the wish's chosen deprecation
  path (clean break) is what puts them there
- the quality of that moment is entirely decided by the shape: `{ headers, payload, event }` puts
  the fix **inside the error message** for both renames at once — squirt reads the three keys and
  the sense of each is its own name
- 🔴 it is the one case that could have shipped a **silent** migration, and the measurement above is
  what proves it does not. a claim of loudness with no count is exactly the drive's repeated defect
  class (`rule.require.positive-control-before-absence-claims`)
- it is the case that justifies question 4's answer, so if this experience is bad, the clean break
  is wrong
