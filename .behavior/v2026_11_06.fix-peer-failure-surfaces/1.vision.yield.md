# 1.vision — a peer failure surfaces, at cause

## .the outcome world

on-call filters svc-gateway logs to `level >= warn`. every failure the middleware chain observes shows: a caller fault at warn, a server fault at error. a success stays at debug. a killed invocation (timeout, out of memory) is aws's to report, and it already fails the invocation.

when svc-notifications refuses a request svc-gateway composed, svc-gateway does not answer its browser 400. it throws `LambdaEndpointRefusedError`, its chain answers 500 with a correlationId, and an error line names the peer and its message. the alarm fires on the first one, not the twenty-fourth.

**before → after**

| moment | before | after |
|---|---|---|
| host's own caller fault | `handler.output` at debug | `handler.output` at **warn** |
| host's server fault | `handler.output` at debug + `handler.error` at error | both at **error** |
| peer refuses a request the consumer composed | consumer throws its own `ConstraintError` → 400 to the http caller, Errors = 0 | consumer throws `LambdaEndpointRefusedError` → 500 + correlationId, error line |
| consumer forwards the caller's payload verbatim | (same as above) | opts in: `refusal: { as: 'ConstraintError' }` → 400, as today |
| test author runs `runLambdaEndpoint.onSerialized` on a refusal | `ConstraintError` | `ConstraintError` (unchanged) |

**aha**: a `ConstraintError` means "*my* caller must fix this". a peer's refusal of a request *I* composed is my fault, so it must not wear my caller's class.

## .the contract

1. **io logger** (`genIoLoggerMiddleware.onError`): on `request.error`, log `handler.output` with `errorMessage` + `stackTrace` at `warn` when `getIsConstraintError`, else at `error`. where trail has not yet put a `log` on the context (a pre-trail throw, e.g. `genApiGatewayRequestEventNormalizationMiddleware.ts:35`), fall back to `console.warn` / `console.error`, as `genInternalServiceErrorMiddleware.ts:69` already does. the success path and line name stay.
2. **refusal class**: new `LambdaEndpointRefusedError extends MalfunctionError` (F1: one class serves both roads, and the http road has no `LambdaEndpoint` to carry); on the invoke road its metadata keeps `endpoint`, `exid`, `errorType` (the peer's class), `details`, `causeMessage`, and its message names the fix, the opt-in, after the peer's reason and its details (helpful-errors then appends the metadata block). the metadata shape has no `hint` field, so the fix rides the message, as `getParsedResponse.ts:174-177` already does. on the http road the metadata is the road's own: `url`, `status`, `exid`, `correlationId`, `text`, `headers`, plus `errorType`. `getIsConstraintError` reads it false, so every consumer family treats it as a server fault.
3. **hydration** (`getParsedResponse`): takes the class a peer refusal becomes. `askLambdaEndpoint` passes the caller's opt (default the refusal class); `runLambdaEndpoint.onSerialized` passes `ConstraintError`.
4. **http road** (`asErrorFromHttpResponse`): a 4xx follows the same opt, save a 429. a 429 is a throttle, not a refusal (the same bytes succeed after `retry-after`), so it is a `MalfunctionError` under either opt (F8).
5. **opt-in**: `refusal?: { as: 'ConstraintError' | 'LambdaEndpointRefusedError' }` on `askLambdaEndpoint` and `.viaApiGateway` input.

## .mental model

a consumer author says: *"if my downstream says no, that's on me, not my user."* analogy: a waiter whose kitchen rejects the order does not tell the diner "your order is invalid". the waiter owns it.

their words: "the peer rejected it", "downstream 400". ours: a peer **refusal** (same sense as `sqs.record.refused`: an endpoint declined a request as a caller fault).

## .evaluation

- **goal 1** (failure logs loud): met for all four families via one middleware.
- **goal 2** (peer refusal ≠ consumer caller fault): met on both ask roads; opt-in keeps old behavior one key away.
- **pros**: one class on both roads, caught by `instanceof LambdaEndpointRefusedError` or `instanceof MalfunctionError` (never by `instanceof LambdaEndpointError`, which never held a refusal: it was a `ConstraintError` before); no change to `getIsConstraintError`; test harness semantics unchanged.
- **cons**: a contract break for consumers that catch `ConstraintError` from `askLambdaEndpoint` (a version bump; svc-gateway's stopgap catch becomes deletable). a server fault logs two error lines (F5).
- **edge cases**:
  - ancient peer answers `BadRequestError` → same refusal class (inventory case 5)
  - sqs perRecord consumer: a peer refusal now redrives then dead-letters (F6); `invariant.constraint-errors-never-redrive-sqs` `.the bound` gets revised
  - http 404 at the gateway reads as a refusal (F3); a 429 is a throttle, a `MalfunctionError` under either opt, its `retry-after` in metadata (F8)
  - a peer that never answers (timeout, throttle, absent function, network) already throws a server-fault class at every site (`executeLambdaInvocation.ts:63,76`, `executeHttpRequest.ts:27`), so it already reaches `handler.error`; behavior 1 adds its `handler.output` error line (inventory row 12)
  - a peer refusal whose message names a credential cannot be misread as an absent aws credential: `throwIfCredentialsError` is not wired into `askLambdaEndpoint` (`throwIfCredentialsError.ts:85-97`), and its message arm skips any `HelpfulError` (`:60`), which the refusal class is

## .what is awkward

- two error lines per server fault (F5)
- every own caller fault now logs at warn, a routine browser typo included. `sdk-logs` reads warn as "look as soon as reasonably possible" (`genLogMethods.d.ts:13-15`); a busy public endpoint will warn often. the wish names warn for a constraint, so it holds; a consumer that finds it loud filters on `handler.output` + `errorMessage`
- the error branch logs `errorMessage` + `stackTrace` raw; `logTranslate.output` never sees it (`genIoLoggerMiddleware.ts:66-70`). inside lambda sdk-logs defaults to debug (`getRecommendedMinimalLogLevelForEnvironment.js:31-33`), so most services already emit it. a service with `LOG_LEVEL=info` or above now emits a caller fault's raw message for the first time. `handler.error` already does so for server faults, so the exposure matches an extant line; route the error branch through a translate if a consumer needs redaction (out of scope)
- the shared hydration now takes a parameter only to keep the test harness's semantics apart from the consumer's (F4)
- a gateway 404 via http is not a handler's refusal, yet it gets the refusal class (F3)
- the io logger's `request.response` branch stays dead on the error path; this wish does not reorder the chain (`.dream/v2026_09_22.fix.no-cors-or-owasp-headers-on-error-responses.md`)
