# case=9 — fromSqs under forAsk · one bad record — sharp × criti

## .narrative

an author wires `forAsk` with `fromSqs({ payload })` as a live sqs handler. one of 3 bodies is malformed. the whole event is refused as a caller fault; the invoke succeeds, and sqs deletes all three. the warn lists all three ids, so the loss is traceable — and the `fromSqs` doc, read first, says to use `forSqs.perBatch` for a live queue.

## .timeline

```
given forAsk({ schema: { input: asLambdaEventSchema.fromSqs({ payload }), output: z.void() }, invoke })
when an sqs event of 3 records arrives, record 2's body fails the payload schema
then invoke is not called
  and one warn `lambda.event.refused` lists the 3 messageIds
  and the invoke succeeds, so sqs deletes the batch
```

## .the fail-safe

loud, not silent: the warn names every id. the doc names the better path. this is the cost F03 carries.

the seam that makes it loud: `forAsk` reads ids by source name (`getAllLambdaEventIds`, keyed by `LAMBDA_EVENT_SCHEMA_SOURCE_NAMES`). `sqs` joins that list, so the compiler demands an sqs row that reads `Records[].messageId` — without it the warn would carry no ids.
