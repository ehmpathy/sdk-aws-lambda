# case=1 — kinesis.perBatch · a mixed batch — sharp × criti (densest)

## .narrative

kai's click consumer gets 4 records. record 2 is not json — a buggy client. record 3 is valid, yet the warehouse write for it times out. kai's handler writes what it can and names what landed.

the sdk refuses record 2 before kai's code runs: it logs `kinesis.record.refused` at warn with record 2's `sequenceNumber`, and acknowledges it. kai's `invoke` sees records 1, 3, 4. it returns `{ successes: [record1, record4] }`. the sdk answers `{ batchItemFailures: [{ itemIdentifier: seq3 }] }`. lambda checkpoints at seq3 and redelivers 3 and 4; kai's write is idempotent, so 4 lands twice harmlessly. the on-call engineer greps one warn line and finds the bad client.

## .timeline

```
given forKinesis.perBatch({ schema: { input: z.object({ payload: schemaOfClick }) }, invoke })
  and a kinesis event of 4 records, record 2's data = base64('not json')
when the handler runs
  [t0] the sdk decodes each record (base64 → utf8 → json) and validates it
  [t1] record 2 fails: warn `kinesis.record.refused` { id: seq2, eventID: 'shardId-…:seq2', issues }; record 2 is acknowledged
       (`id` is the `sequenceNumber` aws demands as `itemIdentifier`; `eventID` is the range an operator replays, the same id `forAsk`'s `lambda.event.refused` carries for kinesis)
  [t2] invoke receives records = [r1, r3, r4]; records[i] === event.records[j] (a filter, never a copy)
  [t3] invoke returns { successes: [r1, r4] }
then the answer is { batchItemFailures: [{ itemIdentifier: seq3 }] }
  and seq2 is absent from it (a refusal never redrives)
  and lambda checkpoints at seq3, so r3 and r4 are redelivered
```

## .the fail-safe

- a forgotten record is reported failed, never dropped: the answer names successes, so silence fails safe
- the refused record is acknowledged, since the same bytes refuse the same way on every delivery
