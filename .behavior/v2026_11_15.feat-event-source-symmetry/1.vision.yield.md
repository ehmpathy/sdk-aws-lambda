# 1.vision — every event source has both halves, in one shape

## .the outcome world

### before

| source | `genLambdaEndpoint.forX` | `asLambdaEventSchema.fromX` |
|---|---|---|
| sqs | `forSqs.{perRecord, perBatch}` | ⛔ absent, by a stated choice |
| sns | ⛔ absent — authors hand-wire `forAsk` + `fromSns` | `fromSns` |
| kinesis | ⛔ absent — authors hand-wire `forAsk` + `fromKinesis` | `fromKinesis` |

an author who serves sns today reaches for `forAsk`, the direct-invoke family. it carries a caller's
guarantees (dialect, introspection, `schema.output`, a constraint-error response body) that an sns
trigger has no use for. an author who serves kinesis gets one verdict for the whole batch: one bad
record refuses all of them, and kinesis advances past every one.

### after

| source | `genLambdaEndpoint.forX` | `asLambdaEventSchema.fromX` |
|---|---|---|
| sqs | `forSqs.{perRecord, perBatch}` | `fromSqs` ✨ |
| sns | `forSns` ✨ | `fromSns` |
| kinesis | `forKinesis.{perRecord, perBatch}` ✨ | `fromKinesis` |

- each record source speaks one contract: `schema.input` describes one record's `{ headers?, payload }` (kinesis: `{ payload }`, since a kinesis record has no metadata bag), `invoke` gets that record's slots plus the whole `event`
- the symmetry law lives in the repo:
  - a brief, `rule.require.event-source-symmetry`, states it
  - a test reads both family key sets and goes red when a source has one half alone, unless that source is on a declared one-sided list, each entry with its axis

### a day in the life

kai owns a click-stream lambda on kinesis. before, kai wired `forAsk` with `fromKinesis({ payload })`, and a malformed click from one client silently skipped the 99 good clicks beside it. now:

```ts
export const handler = genLambdaEndpoint.forKinesis.perBatch({
  schema: { input: z.object({ payload: schemaOfClick }) },
  invoke: async ({ records }, { log }) => {
    await setClicks({ clicks: records.map((record) => record.payload) });
    return { successes: records };
  },
});
```

the malformed click is logged `kinesis.record.refused` and acknowledged alone. the 99 land.

lena owns an sns notice handler. she writes `genLambdaEndpoint.forSns({ schema, invoke })` — the same shape as her `forSqs.perRecord` handler next door, with `headers` from `MessageAttributes`.

a test author asserts an sqs envelope fixture in a contract test: `asLambdaEventSchema.fromSqs({ payload }).parse(event)`.

### the aha

the tables above have no ⛔ in the record-source rows. a reader who learns one source has learned all three. the clamp test makes the next source arrive with both halves, or say why not.

## .mental model

- "forX builds the lambda that serves source X; fromX is the schema of what X sends"
- analogy: a plug and its socket. each source ships both, and they share one pin layout
- the human says *"the sns handler"*, *"the kinesis consumer"*; we say `forSns`, `forKinesis.perBatch`. `for` = the trigger this handler serves; `from` = the provenance of the event (`define.lambda-event-source`)

## .evaluation

| goal | how it lands |
|---|---|
| both halves for sqs, sns, kinesis | `fromSqs`, `forSns`, `forKinesis` added |
| one shape across sources | `{ schema: { input: { headers?, payload } }, invoke }`; `per*` only where the source batches |
| the law lives in the repo | brief + key-set clamp test |
| one-sided sources said out loud | open questions below, in the pr body |
| tests per new half | unit tests per variant + leaf |

pros:
- an sns or kinesis author gets per-record verdicts and the right guarantees, never `forAsk`'s caller ones
- the symmetry clamp makes drift impossible to merge quietly

cons:
- `fromSqs` reopens the whole-batch refusal that kept it out. mitigated by its doc (which names `forSqs.perBatch` for a live queue) and a test that pins the `lambda.event.refused` warn to list every message id
- the package surface grows by three members
- sns `forSns` is a variant while `forSqs` / `forKinesis` are sub-families; a reader may read that as asymmetry
- the record-source steps (validate each record, filter survivors, check the success refs, log a refusal, build the batch answer) must be shared, never copied per source (`rule.forbid.parallel-codepaths`). that lifts source-agnostic leaves out of `forSqs/` to the family root, a refactor of extant code; each source keeps only its decode, its record id, and its log name

edge cases and the pit of success:
- kinesis partial failure: lambda retries from the lowest failed sequence number, so a success after a failure is re-delivered. the doc says so; handlers must be idempotent (they already must be)
- kinesis `perRecord` under `batchSize > 1`: refused loud, fix named, like `forSqs.perRecord`
- empty kinesis batch: accepted, invoke sees `records: []` at `perBatch`; `perRecord` refuses (count ≠ 1)
- kinesis tumble windows are out of scope: a windowed handler must carry `state` in and out (`KinesisStreamStateResponse`), and `forKinesis` answers `batchItemFailures` alone. a windowed author keeps `forAsk` + `fromKinesis()`; the `forKinesis` doc says so
- a refused kinesis record that sits after a failed one is redelivered with it (the checkpoint precedes it), so its warn may repeat. harmless, and the doc says so
- binary kinesis data: the envelope-only `fromKinesis()` or `deserialize: { payload: false }` with a text schema

## .open questions & assumptions

assumptions, each settled:
- [answered] sns delivers one record per invoke — aws docs. `forSns` still refuses any other count loud
- [answered] kinesis `itemIdentifier` = `sequenceNumber`; checkpoint at the lowest failed — aws docs
- [answered] the new families read the trail from the `{ event, trail }` wrapper, as `forSqs` does; the `MessageAttributes` lift stays unbuilt (`domain.terms/trail.md:74`, F04)
- [answered] tumble windows are out of scope; `forKinesis` answers `batchItemFailures` alone

questions:
1. [wisher] **apiGateway stays one-sided** — `forApiGateway` with no `fromApiGateway`. lean: keep. `forApiGateway` validates its own reconciled v1/v2 input, so a `fromApiGateway` would be a second, unreconciled path. only the commander can widen "super symmetric" past the record sources
2. [answered, reported] **ask stays one-sided** — a direct invoke has no envelope, so `fromAsk(x)` would equal `x`; the construct side already declares "deliberately no `fromAsk`" (`index.test.ts:51-55`). settled by logic; still named in the pr body, as the wish asks of every one-sided source
3. [answered, reported] **forSns as a variant, not `forSns.perRecord`** — settled by `domain.terms/genLambdaEndpoint.md` ("a `for*` object with one leaf is a variant with an extra hop"). named in the pr body, since the commander may weigh call-form parity over the rule (F01, clean rework)
4. [answered, reported] **depth: full record-source families, not sugar over `forAsk`** — the wish's own "one consistent shape across sources" settles it: sugar over `forAsk` demands `schema.output` and carries a dialect, while `forSqs`, the extant record-source shape, has neither. so a sugar `forSns` would differ in shape from `forSqs`. named in the pr body, since the commander named members, not depth (F05)
5. [answered] **s3** — neither half today (only `asLambdaEvent.fromS3`, the construct direction). symmetric as is; no change
6. [answered] **do the extant `asLambdaEvent.fromSns` / `fromKinesis` fixtures carry every key the new decoders read?** yes: `fromSns.ts:57-59` sets `MessageId` and `MessageAttributes: {}`; `fromKinesis.ts:50-64` sets a distinct `sequenceNumber` per record and `eventID` = `shardId-…:${sequenceNumber}`. a headers test sets attributes on the fixture, since the default bag is empty

## .groundwork

### external research

- sns → lambda: "Amazon SNS invokes your function asynchronously with an event that contains a message and metadata"; lambda queues the message and retries a failed invoke. the async retry count sits on the async-invocation page; unchecked, and no claim here rests on it — https://docs.aws.amazon.com/lambda/latest/dg/with-sns.html
- kinesis partial batch response: `itemIdentifier` = `sequenceNumber`; lambda checkpoints at the lowest failed sequence number and retries every record from it; an empty `batchItemFailures` is complete success, an empty or null `itemIdentifier` complete failure — https://docs.aws.amazon.com/lambda/latest/dg/services-kinesis-batchfailurereporting.html
- types: `SNSEvent`, `KinesisStreamEvent`, `SQSEvent` in `@types/aws-lambda@8.10.161` (already a dep); `KinesisStreamBatchResponse` / `KinesisStreamBatchItemFailure` at `trigger/kinesis-stream.d.ts:50-54`

### internal research

- `src/domain.operations/genLambdaEndpoint/genLambdaEndpoint.ts` — the family object; `forSqs` is a sub-family because the trigger forces a cardinality choice
- `src/domain.operations/genLambdaEndpoint/genLambdaEndpoint.forSqs/*` — the record-source pattern to mirror: decode → per-record validate → invoke → acknowledge a caller fault, redrive a server fault; `genSqsEndpointMiddlewares` (no constraint-error, no introspection middleware)
- `src/domain.operations/asLambdaEventSchema/asLambdaEventSchema.ts` — documents "no `fromSqs`, deliberately"; `fromSns` / `fromKinesis` share `asLambdaEventPayloadSchema`
- `src/domain.objects/LambdaEventSchemaSource.ts` — `LAMBDA_EVENT_SCHEMA_SOURCE_NAMES` keys `forAsk`'s refusal table; `sqs` joins it
- `src/index.test.ts:57-64` — the key-set clamp that holds "no `fromSqs`"; it inverts. `:51-55` already declares "deliberately no `fromAsk`" on the construct side, the precedent for open question 2
- `.agent/repo=.this/role=any/briefs/rule.require.consistent-variant-contracts.md` — the audit table an integration test parses; new variants add rows
- `.agent/repo=.this/role=any/briefs/domain.terms/genLambdaEndpoint.md` — "a `for*` object with one leaf is a variant with an extra hop"
- vocab reused: `records`, `headers`, `payload`, `event`, `successes`, `*.record.refused`

## .what is awkward

- `fromSqs` exists to satisfy symmetry while its best use is a test fixture check; for a live handler, `forSqs` is better. the doc has to say so plainly, which reads like a member that argues against itself
- `forSns` vs `forSqs.perRecord`: same contract, different hop count. symmetric by rule, not by eye
- the trail does not cross sns or kinesis either; three record sources with a fresh `exid` per invoke
