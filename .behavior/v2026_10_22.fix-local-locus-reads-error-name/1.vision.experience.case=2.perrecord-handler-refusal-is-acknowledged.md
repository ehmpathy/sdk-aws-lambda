# case=2 — a perRecord handler that refuses a message with ConstraintError is acknowledged

**cell**: perRecord × handler × caller · sharp × criti · the svc-quotes case
**seat**: the svc-quotes endpoint author, who wrote the refusal and its test

from that seat: before, they threw a `ConstraintError` to kill the request, watched it pass locally, then watched prep retry it and dead-letter it. after, the throw does what they meant — the message is gone, once — and the local test and the cloud agree.

## narrative

a `forSqs.perRecord` endpoint in svc-quotes reads a message that it judges it can never serve — say, one that names a quote request already withdrawn — so the handler throws `new ConstraintError('quote request withdrawn', { quoteRequestUuid })`. (the handler and the cause are illustrative; the wish cites the svc-quotes run, not the handler.)

before: the family rethrows every fault, so the throw fails the invoke. sqs retries the message until it dead-letters. worse, the local test gate read the throw as a caller fault while the cloud read `Error`, so the gate stayed green over a red prep.

after: the endpoint catches the throw in-process (`getIsConstraintError` — `instanceof`, the error's own `.name`, then the prototype chain). the error carries no `.name` on helpful-errors 1.7.3, and a subclass such as `QuoteWithdrawnError extends ConstraintError` is caught the same way, since the check never reads the wire label. the throw must be a real `Error`: a bare `{ name }` bag redrives, and so does the invoke freeze's own `ConstraintError`, a handler defect. the endpoint logs `sqs.record.refused` and the invoke succeeds. sqs deletes the message once. there is no retry, no dead-letter entry, and no page — exactly as `simple-lambda-handlers`' `badRequestErrorMiddleware` did.

```ts
given('[case2] a forSqs.perRecord endpoint whose handler refuses with ConstraintError', () => {
  when('[t0] the handler throws ConstraintError', () => {

    then('sqs.record.refused is logged at warn, with the id, the class, and the message', ...);

  when('[t1] the handler throws a subclass of ConstraintError', () => {
    then('the invoke succeeds, the same way', ...);
  });
  when('[t1b] the handler throws a bare BadRequestError — the legacy peer class', () => {
    then('the invoke succeeds; getIsConstraintError detects it by instanceof, .name, and the prototype chain alike', ...);
  });
  when('[t2] a test invokes the endpoint via runLambdaEndpoint, at the local locus and the cloud', () => {
    then('both loci answer success — no error envelope on either', ...);
  });
});
```

## the densest walk

`[t2]` is the walk svc-quotes' test took: test → `runLambdaEndpoint` → (local in-process call | cloud invoke) → handler throw → in-process class check → acknowledged → success back to the test. five boundaries. before, the two loci disagreed on the label of a throw neither should have let escape; after, no throw escapes, so both loci answer the same success and the question of the label never arises.
