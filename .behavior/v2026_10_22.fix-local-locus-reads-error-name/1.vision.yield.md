# 1.vision — the local locus serializes a thrown error the way the aws runtime does

## the outcome world

### before

a `forSqs.perRecord` handler refuses a poison pill with `ConstraintError`. the family rethrows it on purpose — sqs must redrive, then dead-letter (`genSqsEndpointMiddlewares.ts`, "why no constraint-error middleware").

| locus | who serializes the throw | `errorType` | caller reads |
|---|---|---|---|
| local | `asWireFunctionErrorPayload` — `error.constructor?.name` | `ConstraintError` | caller fault ✅ |
| cloud | aws runtime `toRapidResponse` — `error.name` | `Error` (helpful-errors 1.7.3 never sets `.name`) | `LambdaEndpointError` ❌ |

the pr gate runs local and stays green. prep runs cloud and goes red (svc-quotes run 38852404042: 4 refusals read as server faults; sqs retried them).

### after

two changes, one per half of the defect:

1. **the local locus conforms.** `asWireFunctionErrorPayload` reads `error.name`, as `toRapidResponse` does — and `typeof error` for a non-error throw, as `toRapidResponse` does too. a local run now shows what the cloud wire shows — so a defect of this class goes red at the pr gate.
2. **the endpoint names its throw.** `genLambdaEndpoint` gains one `onError` middleware, on every family: when an error escapes with the default `.name === 'Error'` and a more specific `constructor.name`, it sets `.name` from the class (non-enumerable, so serialized errors gain no field). the throw then reaches the runtime already named. the guard sits LAST in each middleware array, so its `onError` runs FIRST: middy 4.7.0 runs `onError` in reverse array order and aborts the chain when one throws (`@middy/core/index.js:100,143-148`), and `genInternalServiceErrorMiddleware` throws from its `onError` when `asOutputAfter: false`. a guard placed before it in run order would never fire on a server fault. a first-run guard also hands every later hook (the io logger, the error builders) the named error.

| locus | `errorType` | caller reads |
|---|---|---|
| local | `ConstraintError` (from `.name`, set by the guard) | caller fault ✅ |
| cloud | `ConstraintError` (from `.name`, set by the guard) | caller fault ✅ |

### the aha

change 1 alone turns the local locus RED for every helpful-errors throw — and that red is the truth: it is what prep already sees. change 2 then makes both loci green, for the right reason. no pin to an unreleased helpful-errors is needed. once helpful-errors sets `.name` itself (helpful-errors#45), the guard becomes a no-op for those classes and stays useful for any class that still lacks `.name`.

### day in the life

svc-quotes deletes its in-repo `withErrorNameFromClass` wrap on the bump. a mechanic who writes a new sqs endpoint never learns that `.name` matters: the endpoint handles it, and if it ever did not, the local acceptance run would say so.

## mental model

- to a friend: *"local tests now name an error the same way lambda does — by `.name`. and endpoints built with the sdk stamp `.name` from the class, so a ConstraintError stays a ConstraintError over the wire."*
- analogy: a parcel label. the cloud reads the label (`.name`); the local locus used to read the box shape (`constructor.name`). now both read the label, and the sdk writes the label before the parcel ships.
- their terms: "error name", "error type". ours: `errorType` on the wire, `.name` on the error, `constructor.name` for the class.

## evaluation

- goals: done #1 and #2 both met; done #3 is moot — the guard makes the clamps pass on helpful-errors 1.7.3, so no pin.
- pros: local = cloud by construction; the pr gate catches this class of defect; callers need no change; forward-compatible with helpful-errors#45.
- cons: the guard mutates the thrown error (one non-enumerable own `name`). a raw handler (not via genLambdaEndpoint) on the local locus now sees `Error` for a helpful-errors throw — correct, since cloud does too, but it is a visible change for tests that relied on the old read.
- pit of success: the default path (build with `genLambdaEndpoint`) is named for free; the off-path (raw handler) is now honest instead of falsely green.

## open questions & assumptions

- **assumed** (fulcrum F1): the guard runs on every family, not only sqs. forApiGateway never lets a throw escape, so there it is a no-op; one array shape across families beats a per-family exception (`rule.forbid.parallel-codepaths`).
- **assumed** (fulcrum F2): the guard sets `.name` only when it is the inherited default `'Error'`; an explicit `.name` wins. matches the extant `asErrorLabel` read in `runLambdaEndpoint.onSerialized.integration.test.ts:1335`.
- **assumed** (fulcrum F3): no pin of helpful-errors — the guard satisfies clamp 2 on 1.7.3.
- **[answered]** does a ConstraintError subclass reach the caller as a caller fault? no, on both loci alike — the wire carries one name string, and the caller knows only `ConstraintError` / `BadRequestError`. this PR mirrors helpful-errors#45 (name = own class) and does not widen the caller; a subclass that wants the caller-fault wire may set `name = 'ConstraintError'`, which the guard respects (F2). flagged in the PR body for the commander.
- **[answered]** does the guard run on a server fault, given the internal middleware throws from `onError`? only if it runs first — so it sits last in each array (see "after", change 2). the case=2 clamp proves it.
- **[research]** the runtime names the stack field `trace`; the local locus and the caller use `stackTrace`. whether the Invoke api renames it needs a live cloud invoke — caught as a dream (`dreams/2026_10_22.fix-local-locus-stack-field-trace-vs-stacktrace.dream.md`), out of this wish's scope.
- **[wisher]** none — the commander asked for best-guess on every fork; F1–F3 hold the guesses.

## what is awkward?

- the guard mutates an error the handler owns. a cleaner fix lives in helpful-errors (#45); the guard is a belt for classes that lack `.name`.
- local test suites of raw handlers that asserted `errorType: 'ConstraintError'` now see `'Error'`. honest, but a visible ripple.
- a subclass of ConstraintError is named after the subclass and so reads as a server fault on both loci — consistent, yet a surprise; flagged, not solved here.
