# 1.vision — sqs never redrives a caller fault, and the local locus labels a throw as the cloud does

the requirement is the wish as amended by the human's verdict (`0.wish.verdict.v1.by_human.md`): outcome 1 and done #1 are kept; done #2 is replaced; the optional `.name` guard is dropped.

## the outcome world

### before

a `forSqs.perRecord` endpoint meets a message it can never serve, and throws a `ConstraintError`. the family rethrows every fault, a caller fault included (`genSqsEndpointMiddlewares.ts:26-32`, "why no constraint-error middleware"). so the invoke fails, sqs redrives the message `maxReceiveCount` times, and it lands in the dead-letter queue. the queue's alarm pages the consumer team for a message that was the producer's fault.

`simple-lambda-handlers` — the predecessor — never did this. its `badRequestErrorMiddleware` caught a `BadRequestError` by class and returned, so "this invocation will not be retried by any retry mechanisms (e.g., sqs, kinesis, etc)". the sqs family of this sdk lost that: a regression.

the local test gate hid it. the local locus labelled the escaped throw by `constructor.name` (`ConstraintError`), while the aws runtime labels it by `.name` (`Error` on helpful-errors 1.7.3). a test that asserted a caller fault passed locally and failed in prep (svc-quotes run 38852404042).

### after

1. **a caller fault on sqs is acknowledged.** the endpoint catches a `ConstraintError` / `BadRequestError` by class, in its own process — a schema refusal and a handler throw alike. it logs `sqs.record.refused` at warn, with the message id, the class, and the cause, and tells sqs the message is done: `perRecord`'s invoke succeeds; `perBatch` leaves the refused id out of `batchItemFailures`. the rule binds per message: a `perBatch` handler throw names no record, so it is forwarded and the batch redrives as today (F8). sqs deletes it. no retry, no dead-letter entry (`invariant.constraint-errors-never-redrive-sqs`).
2. **a server fault still redrives**, as today. the catch allowlists caller faults only.
3. **the local locus labels a throw as the cloud does.** `asWireFunctionErrorPayload` reads `error.name` for a value that passes the runtime's `_isError`, else `typeof error` — exactly `toRapidResponse`'s rule. a local run now shows what the cloud shows.

### the aha

the label was never the lever. sqs never reads `errorType`; it reads only whether the invoke failed, or which ids are in `batchItemFailures`. the decision "do not retry this" must be made where the class is still in hand — in the endpoint, before any throw leaves it. made there, it holds for an error with no `.name`, for a subclass, and in a minified bundle with one copy of helpful-errors, and it needs no change to helpful-errors. a class the check cannot see (two minified copies, or a refusal wrapped in a server-fault class) reads as a server fault and redrives — the miss fails toward a retry, never a silent delete.

### day in the life

a producer ships a bad message. the consumer's lambda logs one `sqs.record.refused` warn that names the field at fault, and moves on. the dead-letter queue holds only messages this service failed to serve, so its alarm means an outage of ours again.

## mental model

- to a friend: *"if a queue message is bad, the lambda logs it and drops it — it never retries it or dumps it in the dead-letter queue. real errors still retry. and local tests now name errors the way lambda does."*
- analogy: a mail room. a letter with no address is returned to sender with a note (the log) — not re-sorted forever, and not filed with the parcels damaged in our own van (the dead-letter queue).
- their terms: "bad message", "poison pill", "don't retry". ours: caller fault, `ConstraintError`, acknowledged, `sqs.record.refused`.

## evaluation

- goals: the human's verdict is met — no retry, no dead-letter for a caller fault — and done #1 is met by the serde fix. done #3 (a helpful-errors pin) is moot: no clamp reads `.name` on sqs any more.
- pros: matches the predecessor; quiets false alarms; detection by class holds for an unset `.name`, a subclass, and a one-copy minified bundle, and a miss fails toward a retry; no new config; the change lives in two variant files and one log helper.
- cons: a malformed message is now deleted, so its bytes are gone once logged (F9); a team that inspected malformed messages in the dead-letter queue reads the log instead. it reverses the extant design note against "swallow a validation failure into a success" (F7).
- pit of success: the default path is right — a handler that throws `ConstraintError` gets the correct sqs disposition with no extra code, and a fault of ours still retries.

## open questions & assumptions

- **[answered — human]** is a `ConstraintError` on sqs retried? no, never, and never dead-lettered (`0.wish.verdict.v1.by_human.md`).
- **[answered — human]** is the label guard kept? no. no production reader consumes the label on sqs.
- **[answered — logic]** (F7) is a schema refusal a caller fault? yes: the same bytes fail the same schema on every receive, so a redrive cannot help; the log names the field, so a bad deploy of the schema stays visible.
- **[answered — human]** (F8) does a `perBatch` handler that throws a caller fault acknowledge the whole batch? no: "batch level throws must not acknowledge every record cause we dont know which ones do succeeded or failed … forBatch, we should forward the throw". a per-record refusal is acknowledged via `successes`.
- **[answered — the verdict]** (F9) is the warn log the one trace? yes: the human said "logged and killed the request"; a "refused" queue is infrastructure no one asked for.
- **[answered — logic]** is the svc-quotes endpoint `perRecord`? not known, and moot: both variants are fixed, so no conclusion rests on it.
- **[research]** does sqs delete a message when a `perRecord` invoke returns no body, and does it read no `errorType`? sourced from this repo's own docs and the extant suites, not from aws docs. fetch the aws sqs event source doc in the research stone and cite it.
- **[research]** the runtime names the stack field `trace`; local and caller use `stackTrace`. caught as a dream, out of scope.
- **[answered — human]** (F10) `fix` or `break`? a patch: "its gonna be a patch still". the PR body names the behavior change (case=6) in its first lines.
- **note — the lesson behind the rewind**: the wish's done #2 named a mechanism (a caller-fault label on the wire) with no consumer that acts on it — sqs never reads it. the motive behind it, found by "what does the reader do differently?", was "do not retry a refused message". a done criterion owes a named consumer and the behavior it changes.

## groundwork

### external research

- aws runtime `toRapidResponse` (`aws/aws-lambda-nodejs-runtime-interface-client`, `src/Errors.js`): `errorType: error.name` when `isNativeError(error) || _isError(error)`, else `typeof error`. fetched 2026-10-22.
- sqs retry semantics: a failed invoke redrives the batch; with `ReportBatchItemFailures`, only the ids in `batchItemFailures` redrive, and sqs reads no `errorType`. fetched 2026-10-22 from aws, "handling errors for an sqs event source in lambda" (`docs.aws.amazon.com/lambda/latest/dg/services-sqs-errorhandling.html`): "When your Lambda Event Function encounters an error while processing a batch, all messages in that batch become visible in the queue again by default"; "If your function throws an exception, the entire batch is considered a complete failure"; "Lambda treats a batch as a complete success if your function returns … An empty `batchItemFailures` list … A null `EventResponse`". the doc keys failure on a thrown exception or the listed ids, never on the error's type or message. this repo's contract docs state the same (`perBatch.ts:107-110`, `genSqsEndpointMiddlewares.ts:26-32`). the execution clamps assert the disposition this sdk returns; the redrive itself is aws's, and a deploy-level check would need a live queue.
- `ehmpathy/simple-lambda-handlers` (`src/logic/middlewares/badRequestErrorMiddleware.ts`, `src/contract/createStandardHandler.ts`, origin/main): catches a `BadRequestError` by `instanceof`, `constructor.name`, and the prototype chain; sets the response and returns, so the invoke succeeds and no retry runs. registered in `createStandardHandler`, which served sqs.

### internal research

- `genSqsEndpointMiddlewares.ts:26-32` — the extant note: no constraint-error middleware in the sqs family, by design. reversed here.
- `genSqsEndpointMiddlewares.ts:82` — `genInternalServiceErrorMiddleware({ asOutputAfter: false })`: a server fault rethrows; unchanged.
- `genLambdaEndpoint.forSqs.perRecord.ts:175-228` — batch-size refusal, then validate, freeze, invoke. the catch wraps validate and invoke, never the batch-size refusal.
- `genLambdaEndpoint.forSqs.perBatch.ts:139-151` — validation refusals are logged `sqs.record.invalid` and retried; `:218-229` — `batchItemFailures` from every id not in `successes`.
- `setSqsRecordValidated.ts` → `getValidatedInput` throws a `ConstraintError` on refusal.
- `middleware/getIsConstraintError.ts` — class detection: `instanceof`, `.name`, prototype chain; reused as is.
- `domain.terms/headers.md:112-113` — states a validation failure redrives and dead-letters; updated with the change.
- `runLambdaEndpoint/serde/asWireFunctionErrorPayload.ts` — the local serializer; `constructor.name` read on main (the label defect).

## what is awkward?

- the sqs family's own doc argued against this exact change, on `rule.forbid.failhide` grounds. the answer — the discard is logged, and a caller fault is not a fault of ours — holds, but the reversal is real and the PR body must say so.
- a refused message's bytes are gone after the log (F9).
- "never redrive a caller fault" has one edge where it does not apply: a `perBatch` handler throw redrives the batch, a `ConstraintError` included, since the throw names no record (F8). the brief states it as the bound, so the rule reads per message.
- the per-record lever in `perBatch` is `successes` — a refused record is acknowledged under the name of a success. it works, but the name says "served".
- the PR's first two commits carry the dropped guard; execution reverts it, so the history shows a path abandoned.
