# experience dimensions

two behaviors ride this route, and each has its own space:

- **S — the sqs disposition**: what sqs does with a message once the endpoint has met a fault
- **L — the local label**: what `errorType` the local locus writes for a throw that escapes, against what the aws runtime writes

they share no axis: S is decided in the endpoint's own process, by class, before any throw leaves it; L is the serializer a throw meets after it leaves. so they are walked apart.

## S — axes

| axis | values | why orthogonal |
|---|---|---|
| S.A variant | **perRecord** — one message per invoke · **perBatch** — a batch, with a partial-failure answer | how sqs learns the verdict: the invoke's success (perRecord) or `batchItemFailures` (perBatch) |
| S.B fault origin | **schema** — `schema.input` refuses the message, before the handler runs · **handler** — the handler's `invoke` throws · **deploy** — the trigger is misconfigured (perRecord's batch-size refusal) | where the fault arises. schema and handler are independent of S.C — each can be a caller or a server fault. **deploy is not**: it exists only under perRecord and is always a server fault, a correlation recorded below rather than hidden |
| S.C fault kind | **caller** — a real `Error` that `getIsConstraintError` accepts: a `ConstraintError` / `BadRequestError` by `instanceof`, a subclass by the prototype chain, or any `Error` whose own in-process `.name` is one of the two · **server** — any other throw: a bare `{ name: 'ConstraintError' }` bag (not an `Error`), and the invoke freeze's own `ConstraintError` (a handler defect that wears the class, excluded by `getIsFrozenMutatorRefusal`) | read in-process, never off the wire label. a subclass, an unnamed 1.7.3 error, and an `Error` renamed to `'ConstraintError'` are one value here. the two server exceptions are the boundary: the value must be an `Error`, and the freeze refusal is carved out |

## S — impossible and forbidden

- **rare, not impossible** — schema × server: a refusal is always a `ConstraintError` (`getValidatedInput.ts:24` → `getValidationError.ts:137`, via `safeParse`), but a schema whose own `.transform()` or `.refine()` callback throws propagates that throw raw. it is a server fault, and redrives like any other
- **impossible (nature)** — deploy × caller: the batch-size refusal is a `MalfunctionError` by declaration (`perRecord.ts:141`). deploy × perBatch: perBatch takes any batch size, and the sdk makes no other deploy check in either variant, so "deploy" names exactly one precondition — perRecord's batch size. it is kept as a value, not folded into server, so the inventory shows that the catch never wraps it
- **the latent axis behind deploy, named** — *precondition check*: a gate the variant runs before any message is read. perRecord has one (batch size), perBatch has none, and it can only refuse as a server fault. it is not a separate axis here, since it has one real cell; it rides S.B as `deploy` so the inventory shows the catch never wraps it
- **runtime cancellation, folded** — a timeout, an out-of-memory kill, or an unhandled rejection is not a throw the endpoint sees, so no catch runs. it folds into handler × server: the invoke fails and sqs redrives, as case=4 shows
- **correlation, surfaced** — S.B = deploy forces S.A = perRecord and S.C = server. the 12-cell product holds 4 deploy cells; 1 is real (perRecord × deploy × server), 3 impossible (perRecord × deploy × caller; perBatch × deploy × caller and perBatch × deploy × server, folded as one row)
- **forbidden (nurture)** — caller × redrive, on the paths that name a message (schema refusals in both variants, perRecord handler throws): such a caller fault never fails the invoke, and never lands in `batchItemFailures`. a perBatch handler throw names no message, so it is outside this invariant and redrives (F8, case=7) (`invariant.constraint-errors-never-redrive-sqs`). the redrive is attemptable — it is today's behavior — and the sdk now rejects it

## S — the grain of a handler refusal

**perBatch × handler × caller**: a `perBatch` handler throw is forwarded whatever its class, so the batch redrives as today. the throw carries no per-record verdict — some records may have been served — so to acknowledge all would delete records of unknown outcome. the invariant binds per message: a handler that refuses one record acknowledges it by name in `successes`. ruled by the human, fulcrum F8.

## L — axes

| axis | values | why orthogonal |
|---|---|---|
| L.A locus | local · cloud | who serializes the escaped throw: `asWireFunctionErrorPayload`, or the aws runtime's `toRapidResponse` |
| L.B thrown value | **error, own name** — passes `_isError`, `.name` ≠ `'Error'` · **error, inherited name** — passes `_isError`, `.name` = `'Error'` (a plain `Error`, or a helpful-errors 1.7.3 subclass; the serializer reads them alike, so they are one value, listed as two inventory rows only to show the false green) · **not an error** — fails `_isError`: a primitive, or an object or function that lacks a non-empty string `name`, `message`, or `stack` (an empty string is falsy, and `_isError` reads truthiness) · **unreadable** — a value the runtime's own reads throw on: a native error with no `stack`, an object with no `toString` (a null prototype), or one whose `toString` throws. a `null` or `undefined` throw never reaches the reads: `CallbackContext.fail` swaps it for the string `'handled'`, so it lands in **not an error** as `'string'` | the three branches the serializer reads: `_isError` passes → `.name`; fails → `typeof error`; a read throws → `'handled'`, with the runtime's fixed message and no trace. a value that passes `_isError` with no `.name` is impossible: `_isError` requires a string `name` |

## L — the collapse

after the fix, the local serializer answers the same `errorType` as the runtime for every L.B value, so L.A collapses: each cell holds "local = cloud", proven by the serde clamps rather than walked twice. the stack field is the one known divergence (`trace` against `stackTrace`), itemized off-grid.

## lifecycle — off-grid, and why

the upgrade (an extant consumer whose test asserted the old redrive) varies the author's experience, but not S or L: the disposition after the upgrade is the same S cell as for a fresh endpoint. what differs is the author's prior expectation, a fact about their test, not about the sdk. so lifecycle is walked as one off-grid row (case=6) rather than a third axis, which would double every S cell with an identical outcome.

## concurrency / time — inert, and why

the disposition is decided per invoke, from the class of one throw. the receive count, a concurrent invoke on another record, and the time since the message was sent do not enter the decision — the same bytes and the same handler give the same verdict on every receive. that is the whole argument for the change: a redrive cannot alter the outcome. so neither is an axis.

## actor — inert, and why

the endpoint author, the producer who sends a message, and the operator who reads the logs and the dead-letter queue all observe one quantity per space: the disposition (S) or the label (L). the actor changes who reads it, never what it is, so each case names its actor in the narrative instead of an axis.
