# case=7 — a perBatch handler throw is forwarded, whatever its class

**cell**: perBatch × handler × caller · sharp × criti · fulcrum F8 (ruled by the human)
**seat**: the batch endpoint author, who chooses between a throw and a `successes` list

from that seat: a throw from a batch handler means "i do not know which of these i served" — so the sdk forwards it and sqs redrives the batch, the same as before this change. to drop one bad record and keep the rest, the author leaves the throw for real faults and acknowledges that record by name in `successes`.

## narrative

a `forSqs.perBatch` endpoint receives three messages. midway through the loop, after it has written the first record, the handler throws `new ConstraintError('tenant absent', { tenantUuid })`.

before and after alike: the throw is forwarded. every id lands in `batchItemFailures`, and sqs redrives all three. no `sqs.record.refused` is logged, since the throw names no record.

why not acknowledge the batch: the handler served record one and may or may not have served records two and three. a throw carries no per-record verdict, so an acknowledgement would delete records whose outcome is unknown. the redrive is the safe answer; idempotent handlers absorb the replay of record one.

## sketch

```ts
given('[case7] a perBatch handler that throws a ConstraintError mid-batch', () => {
  when('[t0] a batch of three records is served', () => {
    then('the throw is forwarded — every id lands in batchItemFailures', ...);
    then('no sqs.record.refused is logged', ...);
  });
  when('[t1] the handler instead acknowledges the bad record in successes and returns', () => {
    then('only the unacknowledged ids land in batchItemFailures', ...);
  });
});
```

## care

critipath: the one edge where "never redrive a caller fault" must not apply. a catch here would be a silent delete of unknown work (`rule.forbid.failhide`).
