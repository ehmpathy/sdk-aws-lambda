## findings

### F1 — the `x-domain-object` pragma survives `z.toJSONSchema()`  [FACT]

converges across **[3], [6], [7]**: `.meta()` fields (which is how
`domain-objects@0.32.0` `.contract` stamps `x-domain-object`) **"get copied into
the resulting JSON Schema"** [3]. and per **[5]** the `x-` prefix is a
first-class annotation convention — validators "collect" it, never strip it. so
a consumer that reads the introspected json-schema **can** see `x-domain-object`
and recover name + primary/unique/alias/nested.

- caveat **[6][7]**: `.meta()` can clobber *core* keys (`type`) if misused. our
  pragma uses a **distinct `x-` key**, so no collision with `type`/`properties`.
  low risk, but the blueprint should assert the pragma never reuses core keys.

### F2 — we do NOT need round-trip soundness  [FACT / reframes assumption D]

**[6]**: "no guarantees of 1:1 round-trip soundness" for
`toJSONSchema → fromJSONSchema`. this *sounds* like a risk but **does not apply to
us**: the wish's resources carry **no re-declared validation schema** (wisher
decision — consumers don't re-validate). so we never need to reconstruct a
*runtime zod schema* from json-schema. we only need:
  (a) **TS types** for the mechanism signatures, and
  (b) the **`x-domain-object` metadata** for the resource classes
    (`primary`/`unique`/`alias`/`nested` — plain data, not schema logic).
both survive; the lossy parts of round-trip (refinements, `.transform()`, brands)
are exactly the runtime-validation bits we deliberately drop.

### F3 — for TS types, `json-schema-to-typescript` is the mature choice  [OPIN, well-supported]

**[1][2][8]**: ~1.6M weekly downloads, actively maintained, purpose-built
JSON-Schema→TS. handles `$ref`/`$defs`, `oneOf`(as `anyOf`), and — critically —
the **`tsType` override** for "non-standard JSON schema extensions" [1], i.e. it
won't choke on our `x-domain-object` key (we can map/ignore it). known limits
**[1]** (`format`, `pattern`, numeric bounds "not expressible in TypeScript") are
irrelevant — those are validation constraints, and TS types can't encode them
anyway; they don't affect the shape.

### F4 — `json-schema-to-zod` is the wrong tool here  [FACT]

**[4]**: "output… not meant to be used at runtime" (emits code strings),
`oneOf` "only partially supported. Here be dragons," and — decisive —
**"As of March 2026, this project will no longer be actively maintained."** since
we don't reconstruct runtime zod anyway (F2), there's no reason to adopt a
deprecated tool. **avoid.**

### F5 — quicktype is a viable alternative, but heavier  [OPIN]

**[9]**: quicktype does JSON-Schema→TS *and* runtime validators "in one pass,"
more stars but ~10× fewer downloads than [1] **[8]**. its extra output (runtime
validators, converters) is surplus for us. a reasonable fallback if [1] proves
too limited; not the default.

## conflict & convergence log

- **convergence (3+):** F1 (pragma survives) affirmed by **[3][5][6][7]**.
  F3 (json-schema-to-typescript maturity) by **[1][2][8]**.
- **conflict:** none direct. the *apparent* tension — "[6] round-trip is lossy"
  vs "the wish wants to reproduce schemas" — is **decided by scope** (F2): we
  reproduce *types + metadata*, not *validation schemas*, so the lossy path is
  never walked.
- **caveat flagged:** `.meta()`-clobbers-core-key bug **[6][7]** — mitigated by
  use of a dedicated `x-` key (which [5] blesses).

## recommendation → for the blueprint

| need | tool | why |
|------|------|-----|
| mechanism arg/return **types** | `json-schema-to-typescript` **[1]** | mature, `tsType` handles our `x-` key, limits are irrelevant validation-only |
| resource **identity + metadata** | read `x-domain-object` pragma directly | it's plain annotation data [3][5]; no schema tool needed |
| runtime zod reconstruction | **none** — out of scope | consumers don't re-validate (F2); avoid deprecated json-schema-to-zod [4] |

**net:** the one flagged research risk (lossy reverse-transform) is **not a risk
for this wish** — because we intentionally carry types + metadata, not validation
schemas. `json-schema-to-typescript` covers the type half; the `x-domain-object`
pragma (verified shipped in domain-objects@0.32.0) covers the metadata half.
