# 1.vision — sdk codegen from lambda contract introspection

> illustrate the world implied by the wish: codegen the cross-service sdk
> (`src/access/svcs/svc*`) from `getAllLambdaContracts`, capturing each
> originator service's domain-objects — with `.primary` / `.unique` / `.alias`
> / `.nested` metadata intact — under a namespaced prefix.

---

## the outcome world

### day-in-the-life

a mechanic on `svc-gateway` needs to call `svc-jobs` to read a `Job`.

today they open `src/data/clients/svcJobs.ts` — a **1207-line hand-maintained
file** (verified: `ahbode/svc-gateway:src/data/clients/svcJobs.ts`, 1207 lines)
— and, if the endpoint or domain-object they need isn't there yet, they
hand-transcribe it: copy the `Job` interface from svc-jobs, rename it
`SvcJobsJob`, hand-write a `getJobByUuid` wrapper around `invokeLambdaFunction`,
and hope the shape still matches what svc-jobs actually returns.

after this wish, they run one command:

```sh
npx sdk-aws-lambda gen --for svc-jobs --into src/access/svcs/
```

(no `rhx` dependency — the consumer already depends on `sdk-aws-lambda`, so the
codegen ships as a `bin` in that package and runs via `npx`.)

and get three files, fully typed, guaranteed to match svc-jobs' live contract:

```
src/access/svcs/
├── svcJobs.ts              # barrel
├── svcJobs.mechanisms.ts   # the endpoint asks (getJobByUuid, getProspects, ...)
└── svcJobs.resources.ts    # the domain objects (SvcJobsJob, SvcJobsJobLead, ...)
```

```ts
// src/access/svcs/svcJobs.ts  (generated)
export { svcJobs } from './svcJobs.mechanisms';
export * from './svcJobs.resources';
```

### before / after

| dimension          | before (hand-maintained `data/clients/svcJobs.ts`) | after (generated `access/svcs/svcJobs.*`) |
| ------------------ | -------------------------------------------------- | ----------------------------------------- |
| source of truth    | a human's memory of svc-jobs' shapes               | svc-jobs' live `{ introspect: 'schema' }` |
| drift              | silent — types lie when svc-jobs changes           | caught — re-codegen diffs in a PR          |
| domain-obj fidelity| interfaces only; `.primary`/`.unique` lost         | metadata propagated end-to-end            |
| effort per endpoint| ~15 lines hand-written                             | 0 — generated                             |
| namespacing        | manual `SvcJobs` prefix, easy to forget            | enforced by the generator                 |

### the "aha"

> "the `SvcJobsJob` in my gateway is not a copy of svc-jobs' `Job` — it **is**
> svc-jobs' `Job`, schema and keys and all, reconstructed from what svc-jobs
> told me about itself. when they add a field, my next codegen shows the diff."

the contract stops being documentation and becomes the build input.

## user experience

### usecases / goals

1. **adopt a new upstream** — gateway starts calling svc-sandbar: codegen
   `svcSandbar.*`, import `svcSandbar.getSurfboard` + `SvcSandbarSurfboard`.
2. **stay in sync** — upstream shipped new fields: re-run codegen, review the
   diff, commit.
3. **override a shape** — gateway wants its own `Job` that translates the
   upstream one: it owns the unqualified `Job` namespace, and references the
   generated `SvcJobsJob` to cast from. (the prefix is what makes this safe.)

### contract inputs & outputs

**input** — the codegen consumes the already-built introspection contract:

```ts
// extant, verified: src/domain.operations/getAllLambdaContracts/getAllLambdaContracts.ts:28
getAllLambdaContracts(
  { which: { service: 'svc-jobs' } },
  { env: { access: 'prep' }, ...log },
): Promise<Record<string, LambdaEndpointSchema>>
// LambdaEndpointSchema = { input: JSONSchema; output: JSONSchema }
//   (verified: src/domain.objects/LambdaEndpointSchema.ts:7)
```

**output** — generated files. testdrive of the proposed shapes:

```ts
// svcJobs.mechanisms.ts  (generated) — each ask wraps askLambdaEndpoint
export const svcJobs = {
  getJobByUuid: (event: { uuid: string }, context: ContextAwsLambdaCaller) =>
    askLambdaEndpoint<{ uuid: string }, { job: SvcJobsJob }>(
      { which: { service: 'svc-jobs', function: 'getJobByUuid' }, event },
      context,
    ),
  // ...one per endpoint discovered in the contract
};
```

```ts
// svcJobs.resources.ts  (generated) — domain objects, prefixed, metadata intact
export interface SvcJobsJob {
  uuid?: string;
  title: string;
  // ...reconstructed from the introspected schema
}
export class SvcJobsJob
  extends DomainEntity<SvcJobsJob>
  implements SvcJobsJob
{
  public static primary = ['uuid'] as const;        // propagated from svc-jobs
  public static unique = ['title', 'customerUuid'] as const; // propagated
  public static alias = { singular: 'job', plural: 'jobs' }; // propagated
  // no `static schema` — consumers don't re-validate; the originator does
}
```

### timeline

```
mechanic                    codegen                       svc-jobs (prep)
```

## mental model

- **how a user describes it to a friend**: "it's like `openapi-generator` or
  `prisma generate`, but for our lambda-to-lambda calls — point it at a service
  and it writes you a typed client."
- **analogy**: a **passport stamp**. the upstream service's domain-objects
  travel across the border into your repo, but they keep their origin stamped on
  them (`SvcJobs` prefix) so everyone knows where they came from and you can't
  confuse them with your own citizens.
- **terms** — ours vs theirs:

  | we say (ubiqlang)      | they might say        |
  | ---------------------- | --------------------- |
  | mechanisms             | the methods / the api |
  | resources              | the types / models    |
  | LambdaEndpoint / ask   | endpoint / call       |
  | originator service     | upstream / the source |
  | introspect             | reflect / describe    |

## evaluation

### how well it solves the goals

- **codegen the sdks from introspection** — direct: the input is exactly
  `getAllLambdaContracts`, which already works and is tested (commit `71136ae`).
- **`mechanisms` + `resources` split** — mirrors the proven hand-written shape
  (`svcJobs = { createJob, getJobByUuid, ... }` + `SvcJobs*` interfaces).
- **end-to-end domain-object capture w/ prefix** — achievable **iff** the
  metadata (`.primary`/`.unique`/`.alias`/`.nested`) is carried across the wire.
  this is the load-bearing open question (below).

### pros

- single source of truth; drift becomes a reviewable diff, not a silent bug.
- zero hand-transcription; namespacing enforced, not remembered.
- reuses the entire extant introspection spine — small new surface.

### cons / costs

- **the metadata gap is now CLOSED (was the keystone risk).** it needed (a) a
  getter that stamps identity + `{ primary, unique, alias, nested }` onto the
  schema, and (b) that stamp to survive `z.toJSONSchema()`. both **shipped** in
  `domain-objects@0.32.0` (installed) as `DomainObject.contract` → the
  `x-domain-object` pragma (verified `DomainObject.d.ts:64-79`). one residual
  author dependency remains — `.contract` throws `ConstraintError` unless the
  dobj declares a `static schema` (see awkward #5).
- json-schema → domain-object reconstruction is lossy in general (unions,
  branded types, refinements). the prefix/override escape-hatch mitigates but
  doesn't erase this.
- introspection is gated to `access === 'prep'` (verified:
  `genIntrospectionMiddleware.ts:49`). codegen must run against prep creds.

### edgecases & pit-of-success

| edgecase                                   | how the contract keeps you safe                          |
| ------------------------------------------ | -------------------------------------------------------- |
| upstream renames a field                   | re-codegen → diff in PR, not a runtime surprise          |
| upstream not deployed / wrong access       | `getAllLambdaContracts` already throws loud, named errors |
| two services both export `Job`             | prefix (`SvcJobsJob` vs `SvcQuotesJob`) — no collision    |
| gateway needs its own `Job`                | gateway owns unqualified `Job`; casts from `SvcJobsJob`   |
| endpoint lacks introspection support       | all-or-none: whole batch fails loud (verified behavior)   |
| hand-edits to generated files              | (open) need a "generated, do not edit" guard / re-gen     |

## open questions & assumptions

### assumptions made

1. the new sdk's `askLambdaEndpoint` (not the legacy
   `simple-lambda-client.invokeLambdaFunction`) is the intended call primitive
   for generated mechanisms. **the legacy `svcJobs.ts` uses the old client +
   `stage`; we assume new codegen targets the new `env.access` contract.**
2. codegen output lives in the *consumer* repo (svc-gateway), committed and
   reviewed — not published from the *originator*.
3. "reproduce the schemas" means reconstruct usable TS types + domain-object
   classes (incl. zod `schema`), not byte-identical source.

### open questions (triaged)

each tagged: **[answered]** resolved now · **[research]** for the research phase ·
**[wisher]** needs wisher input before blueprint.

1. **[answered] invocation primitive** — generated mechanisms wrap
   `askLambdaEndpoint` (verified `askLambdaEndpoint.ts:24`); it is the new
   `env.access` call contract and supersedes the legacy
   `simple-lambda-client.invokeLambdaFunction` + `stage`.
2. **[answered] `.alias` is the dobj name-carrier** — `static alias?` exists
   (`DomainObject.d.ts:50`, `string | { plural?; singular? }`); its doc says it's
   "for code generators to use this colloquial alias in contracts." so `.alias`
   is the name/de-dupe carrier that req 3 (prefix) + req 5 (discover) require.
3. **[answered] pragma round-trip** — SHIPPED in `domain-objects@0.32.0`. the
   stamp rides through `z.toJSONSchema()` via the `x-domain-object` pragma
   (verified `DomainObject.d.ts:64-79`). no separate `.meta()` proof needed.
4. **[research] json-schema → TS/zod reverse-transform** — which tool
   (`json-schema-to-typescript` / `json-schema-to-zod`) and how lossy for
   `anyOf` unions, brands, `.transform()` (ties to assumption D).
5. **[answered → SHIPPED] metadata-pragma** — landed in `domain-objects@0.32.0`
   (installed). the api is **`DomainObject.contract`** (a getter, *not* `.schema`
   as the wish's example wrote): `static get contract(): ZodSchema` returns the
   `static schema` stamped with `{ name, primary, unique, alias, nested }` as an
   `x-domain-object` pragma; usage is `z.object({ x: SomeDobj.contract })`; throws
   `ConstraintError` if `static schema` is absent/non-zod. also ships a
   `MARK_AS_DOMAIN_OBJECT` symbol for cross-version dobj detection. (verified
   `DomainObject.d.ts:64-79,34-39`.)
6. **[answered] reconstruction target** — full `DomainEntity`/`DomainLiteral`
   **classes** with metadata (`primary`/`unique`/`alias`/`nested`) — but
   **without the zod `schema`**. consumers do not re-validate; the originator
   service runtime-typechecks. so resources carry identity + keys, not a
   duplicated validation schema.
7. **[answered] delivery surface** — a `bin` shipped by *this* package, run as
   `npx sdk-aws-lambda gen --for <svc> --into <dir>/`. no `rhx` dependency in
   consumer repos (they already depend on `sdk-aws-lambda`). note: package
   `name` is `sdk-aws-lambda` (✓ `npx` resolves), but **no `bin` field exists
   today** (verified: `package.json` has no `bin`; no `bin/` dir) — to add one
   (compiled into `dist`, e.g. `src/contract/cli/gen`) is in-scope for this wish.
8. **[answered] per-endpoint arg ergonomics** — `(event, context)` for each
   generated mechanism.
9. **[answered] no phase split** — metadata ships from the start; the shipped
   `domain-objects@0.32.0` `.contract` getter provides the stamp (+ identity
   marker), so resources include `primary`/`unique`/`alias`/`nested` immediately.
   the dependency has landed; the wish is unblocked.
10. **[answered] discover-channel** — codegen detects dobjs by the
    `x-domain-object` **pragma** that `SomeDobj.contract` stamps onto the
    json-schema (name + primary/unique/alias/nested). not a separate manifest
    endpoint, and not a blind guess from anonymous shapes.
11. **[answered] hand-edit protection** — emit a `// ⚠️ generated by <tool> — do
    not edit; re-run to update` banner atop each file; re-gen overwrites. (the
    *residual* — add a CI drift-check / checksum so stale generated files fail
    the build — is **[wisher]**.) closes the `(open)` edgecase row above.

## what is awkward?

1. **two wishes, now resolved.** the codegen lives here; the metadata-pragma
   (`DomainObject.contract` getter that stamps identity +
   primary/unique/alias/nested as `x-domain-object`) was a **dependency wish** in
   `domain-objects` — SHIPPED in `0.32.0`, installed. this wish is unblocked.
2. **`mechanisms` vs the `svcJobs` export name.** the wish says
   `export { svcSandbar } from './svcSandbar.mechanisms.ts'` — so the file is
   `.mechanisms` but the export is the bare service name. slightly surprising
   (file says mechanisms, symbol says svcSandbar). worth a naming confirm.
3. **legacy vs new call contract.** the reference pattern (`svcJobs.ts`) rides
   `simple-lambda-client` + `stage`; the new world rides `askLambdaEndpoint` +
   `env.access`. generating against the *new* primitive means the output won't be
   a drop-in for places still on the legacy client — a migration seam.
4. **lossy reconstruction.** "reuse the schemas to reproduce them" reads clean,
   but json-schema can't perfectly round-trip every zod construct. the honest
   framing is "good-enough typed reconstruction + an override escape hatch," not
   "perfect fidelity."
5. **capture leans on authors that declare `static schema`.** shipped confirms
   this: `.contract` throws `ConstraintError` unless the dobj has a `static
   schema` (a domain-object with none — like `LambdaEndpoint` itself — cannot be
   captured). so "capture all domain-objects" depends on every upstream dobj to
   declare its zod schema — today optional, not guaranteed. a real limit to note
   in the blueprint (and possibly a lint on the upstream side).
