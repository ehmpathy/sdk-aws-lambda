# case=3 — an sns message fails the payload schema

care: critipath · feel: sharp · inventory: c2, c7, c20

## .narrative

ses ships a new `notificationType: 'DeliveryDelay'`. kai's enum lacks it. the message reaches the
handler; the schema refuses it before `invoke` runs. the refusal is a caller fault, so `forAsk`
answers an error body and the invoke **succeeds** — lambda's async queue retries only a failed
invoke, so bytes that fail the same way every time are not retried
(`invariant.badrequesterror-not-lambda-error`).

kai's prod logs run at info. the next day a warn line is there: the error class, the message, and
the issue path `Records.0.Sns.Message.notificationType` with the value it got (F9). kai reads it,
widens the enum, and deploys. no page fired, no dead-letter noise, and the dropped notice is named.

## .bdd sketch

```
given an sns handler wired with a payload schema whose enum lacks 'DeliveryDelay'
  when [t0] aws delivers an sns event whose Message has notificationType 'DeliveryDelay'
    then invoke is not called
    then the response is the caller-fault body (errorType BadRequestError, ancient dialect)
    then a warn line is logged with the error class and the issue path
      Records.0.Sns.Message.notificationType
    then the lambda invoke succeeds, so the async queue does not retry it
  when [t1] aws delivers an sns event whose Message is not json
    then invoke is not called
    then the issue is a refusal at Records.0.Sns.Message, never a JSON.parse throw
    then the same warn line is logged
```
