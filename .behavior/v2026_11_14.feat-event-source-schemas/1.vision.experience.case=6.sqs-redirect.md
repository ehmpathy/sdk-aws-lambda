# case=6 — the author reaches for an sqs schema

care: alterpath · feel: sharp · inventory: c6

## .narrative

jo read issue #13 and owns `executeTaskTranscribeVoiceCall`, an sqs consumer wired via `forAsk` with
`z.ZodType<SQSEvent>`. jo types `asLambdaEventSchema.fromSqs`. autocomplete offers `fromSns` and
`fromKinesis` only. jo opens the family's doc and reads its source table: sqs is served by
`genLambdaEndpoint.forSqs.perRecord` / `perBatch`, which validate each record's body and acknowledge a
refused message one at a time, where a `forAsk` schema would refuse the batch.

jo switches to `forSqs.perRecord({ schema: { input: z.object({ payload }) }, … })`. the outcome is
better than the one jo asked for.

this is not hypothetical: two of the four handlers issue #13 cites are sqs consumers wired via
`forAsk` with `z.ZodType<SQSEvent>` (`ahbode/svc-notifications`, `executeTaskRhelayVoiceReceivedEvent`,
`executeTaskTranscribeVoiceCall`). each one is a `forSqs.perRecord` migration.

(F1: the wisher may still want `fromSqs`. the demo shows the experience if not.)

