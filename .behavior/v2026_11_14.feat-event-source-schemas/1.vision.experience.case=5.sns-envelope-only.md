# case=5 — envelope only, the rubber-stamp retired (sns and kinesis)

care: critipath · feel: happy, with a sharp turn (c9 at t1) · inventory: c5, c29, c9, c10

## .narrative

a handler forwards the raw sns message elsewhere and never reads its body. its author wants an honest
schema but has no message shape to declare. `asLambdaEventSchema.fromSns()` with no `payload`
validates every envelope field aws documents, keeps `Message` a string, and types the output as
exactly `SNSEvent`.

an sqs event misrouted to this handler is now refused (`Records.0.Sns` absent), where the
`Records`-array guard let it through to fail deep in the handler. a field aws adds next year passes
through untouched (F4).

mara meets the same form on kinesis. her clickstream is of mixed quality, so case=4 steered her off a
`payload` schema: one bad record there would skip the whole batch. she wires
`asLambdaEventSchema.fromKinesis()` with no `payload`. the envelope is validated, `data` stays the
base64 string aws sent (q11), and she decodes and checks each record in her handler, where one bad
record costs only itself.

## .bdd sketch

```
given kai's sns handler wired with asLambdaEventSchema.fromSns()
  when [t0] aws delivers a valid sns event
    then invoke's payload is typed SNSEvent, Message a string
  when [t1] an sqs event arrives at it
    then it is refused; the issue names Records.0.Sns
  when [t2] an sns event arrives with a key the schema does not declare
    then the key is kept in payload, not stripped, not refused
given mara's kinesis handler wired with asLambdaEventSchema.fromKinesis()
  when [t3] aws delivers a batch of 3 valid records, one of them malformed inside its data
    then invoke's payload is typed KinesisStreamEvent
    then each Records[i].kinesis.data is the base64 string aws sent
    then all 3 reach invoke, so mara's handler can refuse the one record and keep the two
```
