### external research

**zod `4.4.3`** (`package.json:77`) and **`domain-objects@0.33.0`** (`package.json:71`) — both
verified by execution against the installed versions, not by docs.

#### g.1 — `output: z.any()` degrades the generated sdk to `Promise<unknown>`

ran a real `genLambdaEndpoint` with `output: z.any()`, sent `{ introspect: 'schema' }`,
fed the result to this repo's own emitter:

```
output json-schema : { "$schema": "https://json-schema.org/draft/2020-12/schema" }   // i.e. {}
output as typescript: "unknown"
```

`z.any()` → `{}` → `getTypescriptFromJsonSchema` returns `'unknown'`
(`src/domain.operations/genServiceSdk/gen.mechanism/getTypescriptFromJsonSchema.ts:80`,
the "no recognizable shape" branch). **the rubber-stamp crosses the service boundary.**

#### g.2 — `X.contract` stamps identity, and it survives `z.toJSONSchema()`

```json
"x-domain-object": { "name": "Agent", "kind": "entity", "primary": ["uuid"], "unique": ["exid"] }
```

confirms the mechanism this repo's codegen already reads
(`src/domain.operations/genServiceSdk/gen.resource/getAllDomainObjectsFromContracts.ts:47`).

#### g.3 — `.transform()` hydration **breaks introspection at runtime**

the obvious "no sdk change needed" idea — `Agent.contract.transform(p => new Agent(p))` —
does hydrate correctly on parse (`isAgent: true`). but through the real handler:

```
{ introspect: 'schema' } → THREW: Error | Transforms cannot be represented in JSON Schema
    at getJsonSchemaFromZod (…/genIntrospectionMiddleware.getJsonSchemaFromZod.ts:11)
```

a bare `Error`, not a `HelpfulError`, and it takes down `getAllLambdaContracts` for the
**whole service**. so hydration-in-the-schema is not merely unsupported — it is actively
hostile to the introspection + codegen features shipped in `#8` / `#10`.

`getJsonSchemaFromZod` calls `z.toJSONSchema(schema)` with default `io` (= `'output'`);
transforms are unrepresentable in that direction.

#### g.9 — transform-bearing input schemas are a SHIPPED feature, and they are already broken

> **⚠️ out of bound for this pr — seeded as `ehmpathy/sdk-aws-lambda#17`.** in scope for the
> **repo**, not for this deliverable (`rule.require.one-pr-per-worktree`: one deliverable, one
> pr). kept here so the record outlives this session, and written self-contained so `#17` can
> lift it verbatim. **do not widen this bound to chase it** — see [q.7](#q7--the-research-surfaced-a-live-defect-the-wish-did-not-ask-about-fix-it-here-or-report-it-answered--ruled-by-the-wisher).

`g.3` is not about a hypothetical. `.transform()` in an input schema is a **deliberately tested
feature of this repo**:

```ts
// genLambdaEndpoint.forAskEndpoint.test.ts:194-232
given('[case6] schema with transforms', () => {
  const schema = {
    input: z.object({ email: z.string().transform((val) => val.toLowerCase()) }),
    output: z.object({ email: z.string() }),
  };
  …
  then('input is lowercased before handler', () => { expect(capturedEmail).toBe('alice@example.com'); });
```

and `case7`, the introspection test, uses a **different, transform-free** schema:

```ts
// genLambdaEndpoint.forAskEndpoint.test.ts:234-238
given('[case7] introspection request in prep env', () => {
  const schema = {
    input: z.object({ customerId: z.string() }),   // <-- no transform
    output: z.object({ name: z.string(), balance: z.number() }),
  };
```

the two features are each tested in isolation and **never crossed**, so their incompatibility is
untested and invisible.

> **the live defect:** any consumer who uses the tested `.transform()` input feature and
> deploys to `prep` crashes `getAllLambdaContracts` for their **whole service**, with a bare
> `Error: Transforms cannot be represented in JSON Schema` — not even a `HelpfulError`.

**the crash path**, proven end-to-end through the real handler in [g.3](#g3-transform-hydration-breaks-introspection-at-runtime):

```
{ introspect: 'schema' }
  → genIntrospectionMiddleware.ts:58                        getJsonSchemaFromZod(opts.schema.input)
  → genIntrospectionMiddleware.getJsonSchemaFromZod.ts:11   z.toJSONSchema(schema)
  → zod/v4/core/json-schema-processors.cjs:271              transformProcessor
  → Error: Transforms cannot be represented in JSON Schema
```

**root cause:** `getJsonSchemaFromZod` calls `z.toJSONSchema(schema)` with zod's default
`io: 'output'`, and a transform is unrepresentable in that direction.

**the fix, and its proven cost:** serialize with `io: 'input'` — the wire face, which is what
crosses at **both** borders ([g.18](#g18--io-names-the-side-of-the-contract-never-the-border-of-the-endpoint); this issue was first written for the input schema alone,
before `io` was recognized as a side word rather than a border word). [g.4](#g4-io-input-vs-io-output-is-codegen-neutral)
proves this is **codegen-neutral** — the emitter produced byte-identical typescript
(`sameTs: true`), and the only json-schema delta is a dropped `additionalProperties: false`,
which appears in **no** src logic and in exactly four snapshot lines
(`genLambdaEndpoint.forAskEndpoint.test.ts.snap:76,89`;
`genLambdaEndpoint.forApiGateway.test.ts.snap:89,102`).

**the clamp it needs:** a test that crosses the two cases — a transform in the input schema
**plus** an `{ introspect: 'schema' }` request — which must go **red** against today's code
(`rule.require.clamp-edge-cases`). that clamp belongs to the issue, not to this pr.

**this is a defect in the repo today, independent of this wish.** the wish did not ask about it;
this vision's research surfaced it. → surfaced to the wisher as a finding, not folded silently
into scope.

#### g.4 — `io: 'input'` vs `io: 'output'` is codegen-neutral

`z.toJSONSchema(s, { io: 'input' })` **does** serialize a transform. the only delta vs
default for a plain schema is a dropped `additionalProperties: false`:

```
sameTs: true   // both directions emit the identical typescript
```

and `additionalProperties` appears **nowhere in src logic** — only in two snapshot files
(`genLambdaEndpoint.forAskEndpoint.test.ts.snap:76,89`,
`genLambdaEndpoint.forApiGateway.test.ts.snap:89,102`).

**this is not insurance against a hypothetical — it is the fix for the live defect in [g.9](#g9-transform-bearing-input-schemas-are-a-shipped-feature-and-they-are-already-broken).**
`io: 'input'` makes transform-bearing schemas introspectable, and this finding proves that fix
costs **zero** change to generated types and two snapshot updates. it also keeps a schema-side
hydration approach open if one is ever wanted — see [f.2](#f2-what-shape-does-hydrate-take).

> **on the parenthetical this once carried.** an earlier version added *"the output schema stays
> `io: 'output'`, which is the correct direction for what a caller receives."* that is wrong —
> `io` names the **side** of the contract, not the **border**, and the wire face crosses at both
> ([g.18](#g18--io-names-the-side-of-the-contract-never-the-border-of-the-endpoint)). the measurement above is unaffected; only the scope of the fix widened.

issue `#16` proposes `schema: { input }` with `output` absent. run today:

#### g.6 — hydration cannot be inferred — `domain-objects` carries no name→class registry

`getContract.js:9-11` states it outright: *"the contract carries nested identity by name,
never the constructor objects (name-only per vision)"*. and the package's full export list
(44 symbols, enumerated at runtime) has **no** `getContract`, no registry, no name→class
lookup. further, `.meta()` on a transformed schema returns `null`.

**therefore the sdk cannot auto-hydrate from the schema alone.** the consumer must name the
classes. this is a hard constraint, not a preference, and it rules out every "just infer it"
shape in [f.2](#f2-what-shape-does-hydrate-take).

**note the exact bound of the constraint: it binds IDENTITY, not POSITION.** the schema cannot
supply a *constructor*, but it can and does supply a *name* — the `x-domain-object` pragma
([g.2](#g2--xcontract-stamps-identity-and-it-survives-ztojsonschema)). so the consumer owes a class list, not a positional map; see [g.13](#g13--stamp-_dobj-from-the-schema-pragma-then-deserialize--it-works-and-it-reaches-arrays).

#### g.7 — nested hydration already ships in `domain-objects@0.33.0`

`dist/instantiation/hydrate/hydrateNestedDomainObjects.d.ts`:

> *"hydrates each declared nested prop into its DomainObject instance… so callers can pass
> plain (e.g. deserialized) objects and still receive typed instances"*

verified: `new Assignment({ agent: {…}, note: 'x' })` with `static nested = { agent: Agent }`
yields `agent instanceof Agent === true`. it even ships
`NestedDomainObjectHydrationError extends ConstraintError` (exit 2, http 400) for the
failure path.

**but this is conditional, and the condition matters.** `.nested` reaches everything below a
**dobj**. it does not apply at all to a dobj under a **plain** wrapper — and re-reading the
wish's evidence (`0.wish.md:57-67`), that is exactly what it has: `assignment` is spread into a
plain object literal (`{ ...event.assignment, agent: new Agent(…) }`), and only `agent` gets a
constructor. had `Assignment` been a dobj, the author would have written `new Assignment(…)`.

so nested hydration is reached **two ways**, and the design needs both:

| shape | reached by |
|---|---|
| a dobj under a dobj | free — `.nested`, no sdk work |
| a dobj under a **plain** wrapper (the wish's evidence) | the sdk must descend to it ([g.13](#g13--stamp-_dobj-from-the-schema-pragma-then-deserialize--it-works-and-it-reaches-arrays)) |

a top-level-only design would leave the evidence's `Agent` hand-rolled — precisely the outcome
the wisher pre-emptively rejected in acceptance bullet 4. this is the finding that killed the
flat map, and it is the reason the second row must be solved by the sdk rather than declared
away by the consumer.

#### g.8 — a dobj that refuses a validated input surfaces today, but with an inconsistent error shape

with a looser input schema than the dobj's own (`exid: string | number` vs `exid: string`):

```jsonc
// hydration failure — reaches the caller, but shapeless
{ "errorMessage": "✋ HelpfulZodValidationError: …\n\nProps Provided:\n{…}", "errorType": "BadRequestError" }

// input-validation failure — the established shape
{ "errorMessage": "✋ ConstraintError: validation failed: agent.exid: …",
  "errorType": "BadRequestError",
  "details": { "issues": [{ "path": "agent.exid", "message": "…", "code": "invalid_type" }] } }
```

it does fail loud (good — **acceptance bullet 5 already holds today**, so that bullet is a
"do not regress", not a "build"), but with **no `details.issues`** and a raw prop-dump message.

**normalizing that shape is opportunistic, NOT a requirement.** the wish asks only that a
failed construction fail loud and never reach `handle` half-built — which already happens. a
reviewer may cut the normalization without cutting any acceptance criterion. it is listed here
because a first-class `hydrate` step is the natural place to do it cheaply, not because the
wish demands it.

#### g.10 — `safeParse` does NOT contain a throw from inside a transform

> **counter-intuitive. recorded explicitly so the next reader does not assume what i assumed.**

the name and the entire prior say `safeParse` never throws — that is the whole point of the
`safe` prefix, and every reasonable reader (this one included) expects a `{ success: false }`
result for any failure. **that expectation is wrong when the failure comes from inside a
transform.** run against zod `4.4.3`:

```ts
const loose = z
  .object({ exid: z.union([z.string(), z.number()]), name: z.string() })
  .transform((p) => new Agent(p as Agent));   // the ctor throws on exid: number

loose.safeParse({ exid: 123, name: 'kai' });
// → { kind: 'threw', ctor: 'HelpfulZodValidationError' }   NOT { success: false }
```

zod catches **its own** validation issues and reports them in the result; a throw raised by
**user code inside a transform** propagates straight out of `safeParse`.

**why it matters here.** the input validation middleware is written against the result shape —
`if (!result.success) throw getValidationError(...)`
(`genZodEventValidationMiddleware.ts:16-18`). so a hydration failure folded into the schema
would **bypass that branch entirely** and escape as a raw throw, never reaching the
`ConstraintError` conversion that gives callers the `{ issues }` shape ([g.8](#g8-a-dobj-that-refuses-a-validated-input-surfaces-today-but-with-an-inconsistent-error-shape)).

this is a **third** independent argument for hydration as its own step, alongside [g.3](#g3-transform-hydration-breaks-introspection-at-runtime)
(introspection) and [a.7](#assumptions-surfaced--and-questioned) (the published wire shape): a separate step can catch and convert
its own failures, where a transform's throw would slip past the middleware's only error path.

#### g.11 — raw `deserialize` on a plain payload is a SILENT no-op

`domain-objects` ships a `deserialize` that recurses arrays and plain wrappers — exactly the
two shapes the `hydrate` map has to walk by hand. so the obvious question is whether it can
BE the hydration mechanism. run it against a plain external payload:

```ts
deserialize(JSON.stringify({ assignment: { agent: { exid: 'a1', name: 'kai' }, note: 'x' } }),
            { with: [Agent, Assignment] });
// → { assignmentIsAssignment: false, agentIsAgent: false }   and NO error raised
```

it keys off a `_dobj` discriminator **in the data** (`deserialize.js:78`). an external caller
sends plain json, so `_dobj` is absent, so every node falls through the plain-object branch
(`:92-98`) and is copied verbatim. **it does not throw. it returns plain objects that look
hydrated to the type system and are not.** that is `rule.forbid.failhide` by construction, so
raw `deserialize` is unusable as-is.

#### g.12 — the caller-path `serialize` route is closed, twice over

the natural repair for [g.11](#g11--raw-deserialize-on-a-plain-payload-is-a-silent-no-op) is to make the caller send `_dobj` — i.e. have
`askLambdaEndpoint` call `serialize` instead of a plain object. two independent facts close it:

1. **zod strips the discriminator before hydration could run.** a schema drops unknown keys by
   default, so `_dobj` does not survive validation:
   ```
   beforeZod: { agent: { _dobj: 'Agent', exid: 'a1', name: 'kai' } }
   afterZod : { agent: {            exid: 'a1', name: 'kai' } }   dobjSurvived: false
   ```
   `.passthrough()` preserves it, but that would demand every consumer loosen their input
   schema to keep an internal marker — the opposite of a pit of success.
2. **the default `serialize` is LOSSY for nested dobjs.** with `lossless: false` (the default)
   a non-root dobj is replaced by `getUniqueIdentifier(obj)` (`serialize.js:83-89`), so the
   nested `Agent` arrives as `{ exid }` alone — `name` is gone. the wish's own usecase breaks.
   `{ lossless: true, orderless: false }` is required, which is a footgun a caller must
   remember at every call site.

and it would change the wire format for every caller, ancient and contemp alike. closed.

#### g.13 — stamp `_dobj` from the schema pragma, then `deserialize` — it works, and it reaches arrays

the third reframe: the endpoint **already knows** where dobjs live, because
[g.2](#g2--xcontract-stamps-identity-and-it-survives-ztojsonschema) proves `X.contract` stamps an `x-domain-object` pragma that survives
`z.toJSONSchema()`. so the sdk can walk its own json-schema and synthesize the discriminator
`deserialize` wants, rather than demand the caller send it. verified end-to-end on a PLAIN
external payload with no `_dobj` anywhere:

```ts
const jsonSchema = z.toJSONSchema(wishSchema, { io: 'input' });
const stamped    = stampDobj({ value: plainEvent, schema: jsonSchema }); // walk + stamp
deserialize(JSON.stringify(stamped), { with: [Agent] });
// → agentIsAgent: true,  noteSurvived: 'x'
```

and the same path reaches **arrays** of dobjs — the one gap the nested map could not close:

```ts
z.object({ agents: z.array(Agent.contract) })  →  allAgents: true, count: 2
```

the walk unwraps `anyOf` / `oneOf` (which is how a nullable renders), recurses `items` for
arrays and `properties` for objects, and stamps `_dobj` wherever the pragma names a class.

**what the consumer still owes.** [g.6](#g6-hydration-cannot-be-inferred--domain-objects-carries-no-nameclass-registry) is unmoved — there is no name→class registry, so
the classes must still be named. but they collapse from a **positional nested map** to a
**flat list**: `with: [Agent]` rather than `{ assignment: { agent: Agent } }`. position is
derived from the schema; only identity is declared.

**the cost, stated plainly.** this binds hydration to `X.contract` — a consumer whose input
schema is a hand-written `z.object` carries no pragma, so no node is stamped and no hydration
happens. [a.5](#assumptions-surfaced--and-questioned) said `.contract` was NOT a prerequisite; under this mechanism it becomes one.
see [f.2](#f2-what-shape-does-hydrate-take), where that tradeoff is weighed rather than waved past.

#### g.14 — `X.contract` is typed `ZodSchema<any>`, so it erases the position it stamps

> **this one cuts against my own prior draft, and it is not a mechanism choice — it is upstream.**

`getContract.d.ts:16-18`, read first-hand:

```ts
export type DomainObjectContract = ZodSchema<any> & {
    ref: (by: DomainObjectRefBy) => ZodSchema<any>;
};
```

so `z.infer<typeof Agent.contract>` is **`any`** — not `Agent`, and not the plain shape either.
any input schema that embeds `X.contract` therefore yields `any` at that position, and
`handle(event)` compiles **whatever** hydration does or fails to do at runtime.

**why this matters more than it first looks.** the probe that verified type narrowing
(`hydrate: { assignment: { agent: Agent } }` → `Agent | null | undefined`) was written against a
**hand-written** `agentSchema`, not against `Agent.contract`. so that narrowing is real, but it
holds only for the schema style that does **not** carry a pragma. flip to `X.contract` — which
every use case in this vision does, which the codegen wants, and which
[f.2](#f2-what-shape-does-hydrate-take)'s mechanism now requires — and the position is `any`
regardless of which hydration mechanism sits underneath it.

**the honest consequence:** the type-level half of "no `as` cast" is weaker than the wish's
acceptance implies. today an author writes `event as Agent` and a reviewer sees the cast; under
`X.contract` the same unsoundness arrives silently as `any`, with no cast to grep for. that is
strictly better than a hand-rolled graph rebuild (the wish's actual complaint) and strictly
worse than a narrowed type.

> ### ⚠️ CORRECTED by [g.15](#g15--xcontractcoerce-beats-the-hydrate-key-on-every-axis-and-it-does-not-exist) — this `any` IS fixable, and not only upstream
>
> i first wrote that the erasure was upstream and unclosable by any mechanism here. **that was
> wrong.** a `.transform()` at the position re-types it: `z.infer` yields `Surfer`, verified
> unaided under `--strict` with a negative control ([g.15](#g15--xcontractcoerce-beats-the-hydrate-key-on-every-axis-and-it-does-not-exist)). the erasure survives only
> when `.contract` is used **bare**.
>
> the claim below stands **only for the bare-contract case** — which is what the `hydrate`
> design uses, and precisely why `.coerce()` beats it. left in place rather than deleted,
> because the bare case is still today's status quo and the reasoning is still what a reader
> needs to understand the contrast (`rule.require.timeless-comments`).

**a second, deeper fix exists upstream — and the wisher named its mechanism.** the erasure is not
a lax declaration; it is a **typescript constraint**. a static **getter** has no type-parameter
position and no `this` to propagate, so `ZodSchema<any>` is the only type it can carry. a static
**method** can use polymorphic `this` — which is why the accessor becomes `Surfer.contract()`, and
why `.ref` moves with it to `Surfer.contract().ref(by)`. **that closes the bare case too**, which
no transform can reach. a `domain-objects` change, outside this bound
(`rule.require.one-pr-per-worktree`) — see [q.18](#q18--one-declaration-two-usecases-which-does-this-pr-fix-answered--one-of-them).

#### g.15 — `X.contract().coerce()` beats the `hydrate` key on every axis, and it does NOT exist

> **this result invalidates the mechanism g.13 proposed. it is recorded in full because it also
> overturns [g.14](#g14--xcontract-is-typed-zodschemaany-so-it-erases-the-position-it-stamps)'s "upstream, unfixable" verdict.**

the question: rather than a separate `hydrate` key, could hydration ride **on the contract** —
`Surfer.contract().coerce()` — so a consumer never has to remember it?

**first, the literal answer: no such method exists.** enumerated at runtime, `.contract` carries
only zod's own surface plus `ref`:

```
hasRef: 'function'      hasCoerce: 'undefined'
```

so the real question is "should it exist?". a `.coerce()` would be
`contract.transform((p) => new Klass(p))`. tested end-to-end:

| what | result |
|---|---|
| hydrates on parse | ✅ `isSurfer: true` |
| **the `x-domain-object` pragma survives, under `io:'input'`** | ✅ `pragmaSurvivesCoerced: true` |
| the published input schema stays the **plain wire shape** | ✅ — [a.7](#assumptions-surfaced--and-questioned) satisfied, with the pragma intact |
| a dobj under a plain wrapper | ✅ `isSurfer: true`, `nullStaysNull: true` |
| arrays of dobjs | ✅ `all: true` |
| the dobj's own `.nested` still fires | ✅ `nestedIsSpot: true` |

#### g.16 — the codec verdict is right for ONE position, and a failhide for the other

> ### ⚠️ SUPERSEDED by [g.18](#g18--io-names-the-side-of-the-contract-never-the-border-of-the-endpoint)
>
> the measurements below are correct and stand. **the verdict drawn from them was wrong**, because
> it rested on an unstated premise: that the response border publishes whatever
> `getValidatedOutput`'s `safeParse` yields. it does not — `JSON.stringify` is the real encoder,
> and it always emits side A. [g.18](#g18--io-names-the-side-of-the-contract-never-the-border-of-the-endpoint) measures that directly and reverses the output-schema
> verdict to `{ io: 'input' }` at **both** borders.
>
> kept whole rather than deleted: the one-way-transform counter-case is still real, and g.18
> re-classifies it rather than dismisses it (`rule.require.timeless-comments`).

> **prompted by the upstream `.coerce()` drive**, which ruled for a **codec** (their f9) and
> concluded: *"under a codec, the wire shape is side A for both directions — so `{ io: 'input' }`
> is the correct emit for an input schema **and** for an output schema. one rule, both positions,
> rather than the split the transform form forced."*
>
> that would **overturn this bound's `#17` verdict**, which keeps the output schema at
> `io: 'output'`. so it is the claim most worth a probe (`rule.require.trust-but-verify`), and it
> was executed rather than accepted.

**their codec results reproduce exactly** (zod `4.4.3`, `z.codec` confirmed present):

| | result |
|---|---|
| codec under `io: 'input'` | ✅ the **plain wire shape**, pragma-compatible |
| codec under `io: 'output'` | ✖ `Error \| Custom types cannot be represented in JSON Schema` |
| codec parses to a real instance | ✅ `true` |

so their g26 holds, and their conclusion holds **for the input schema** — which this bound
already ruled.

**but the generalization to the output schema does not hold.** the counter-case is a **plain
one-way transform** in an output schema — `z.string().transform((s) => s.length)`, i.e. the
handler yields a string and the caller receives a number:

```
io: 'output' → Error | Transforms cannot be represented in JSON Schema     ← crashes, LOUD
io: 'input'  → { "size": { "type": "string" } }  →  ts: "{ size: string; }" ← publishes a LIE
```

the caller receives a **number**. `io: 'input'` publishes **string**, confidently, with no error —
and that wrong type crosses the service boundary into every generated sdk.

**that is the same harm as [g.1](#g1-output-zany-degrades-the-generated-sdk-to-promiseunknown), and worse.** `z.any()` degrades a caller to
`Promise<unknown>` — useless, but honest. this publishes a **specific, confident, wrong** type.
today's crash is loud; the swap would trade a crash for a silent lie
(`rule.forbid.failhide`).

**why the two positions genuinely differ**, stated once so the split is not read as inconsistency:

| schema | publishes | so the right face is |
|---|---|---|
| **input** | what a caller must **send** | side A — the wire. `io: 'input'`, always |
| **output** | what a caller will **receive** | the *post*-handler face — which for a codec is `encode`'s result (side A), but for a one-way transform is the transform's result (side B) |

for a codec the two coincide, which is exactly why their rule looked universal. for a one-way
transform they diverge, and zod's single `io` flag cannot tell the cases apart at the call site.

**the verdict that survives:**

- **input schema → `{ io: 'input' }`** — unchanged, and now doubly grounded
- **output schema → stays `io: 'output'`** — unchanged
- **a coerced/codec output schema is a real gap**, and its answer is **not** a blind flag swap.
  the honest fix is to make the crash name its own repair: `getJsonSchemaFromZod`, on an output
  schema it cannot serialize, should refuse with *"an output schema cannot carry a transform;
  declare the wire shape, or use a codec and emit its encode face"* rather than a bare zod
  `Error` (`rule.require.errors-name-the-fix`). that is a **flag** for `#17`'s execution stone,
  not a new capability.

**the clamp this owes:** an output schema that carries a one-way transform must **not** silently
publish its pre-transform shape. the test has to assert the **refusal**, because the failure mode
is a confident wrong answer rather than an error — a naive "does it emit?" test passes vacuously.

#### g.18 — `io` names the SIDE of the contract, never the BORDER of the endpoint

> **prompted by the wisher, who named the conflation directly** — and it is the conflation
> [g.16](#g16--the-codec-verdict-is-right-for-one-position-and-a-failhide-for-the-other) made:
>
> | the word | scope | values |
> |---|---|---|
> | **border** | the **endpoint** — which way a message travels | request (input) / response (output) |
> | **side** | the **contract** — which face of the codec | wire (in) / instance (out) |
>
> g.16 read `io` as a border word and split the verdict by position. it is a **side** word, and
> the side that crosses is the **wire** — at both borders, because the wire is json in both
> directions.

**the measurement that settles it.** what actually reaches a caller is not what `safeParse`
returns — it is what `JSON.stringify` emits:

```
stringify({ surfer: instance })  →  {"surfer":{"uuid":"u1","name":"kai"}}      ← side A
```

so the response border publishes **side A**, whatever `getValidatedOutput` does internally.
`{ io: 'input' }` is the correct emit for the output schema, exactly as for the input schema. one
rule, both borders — the upstream verdict holds in full, and g.16's split falls.

**and zod agrees, out loud.** `z.encode` — the direction the response border actually travels —
refuses a unidirectional transform by name:

```
encode(codec,  instance)  → {"surfer":{"uuid":"u1","name":"kai"}}            ← side A, clean
encode(oneWay, instance)  → THREW | $ZodEncodeError |
                              Encountered unidirectional transform during encode: ZodTransform
```

**so g.16's counter-case is re-classified, not dismissed.** `z.string().transform(s => s.length)`
in an output schema does put side B on the wire today — but only because `getValidatedOutput`
runs `safeParse` (a **decode**) on a value that travels the **encode** direction. read as a
contract, that schema is not a wire contract at all; it is a post-processor in a contract's
clothes, and zod names it as such. the repair is to declare the shape the endpoint hands back
(`z.number()`) and let the handler produce it.

**the two are distinguishable at runtime**, which is what makes the refusal implementable rather
than aspirational:

```
codec  reverseTransform : function      def.type : pipe
oneWay reverseTransform : undefined     def.type : pipe
```

**four more results from the same run**, each closing a gap left open earlier:

| | result |
|---|---|
| a codec in the **output** position, `io:'input'` | ✅ plain wire shape — `{uuid, name}`, `required` intact |
| the `x-domain-object` pragma on that emit | ✅ survives — `{"name":"Surfer","kind":"entity"}` |
| the round trip zod codecs promise, for a dobj-shaped codec | ✅ `encode(decode(wire))` is byte-equal to `wire` |
| today's `getValidatedOutput` against a coercing output schema | ✅ `safeParse(instance)` succeeds and yields an instance — **by accident**, because a domain instance is structurally its own wire shape. it would not survive a codec whose sides differ structurally (an iso string ⇄ `Date`). |

that last row is worth its own line: the current response path is decode-shaped, and it only
looks correct for domain objects. it is a latent seam, not a defect this bound repairs.

**the verdict that replaces g.16's:**

- **input schema → `{ io: 'input' }`** — unchanged
- **output schema → `{ io: 'input' }`** — **changed**; the wisher's rule holds at both borders
- **a one-way transform in an output schema is a declaration defect**, not a case `io` must
  accommodate. `getJsonSchemaFromZod` should refuse it and name the repair
  (`rule.require.errors-name-the-fix`), and `reverseTransform` is the discriminator that lets it.

**the clamp this owes** — replaces g.16's, and is strictly easier to write because the failure is
now an error rather than a confident wrong answer:

- a **codec**-bearing output schema emits the plain wire shape with its pragma intact, and its
  emitted typescript matches the bare-contract case
- a **one-way**-transform-bearing output schema is **refused**, with a message that names the fix

#### g.19 — why zod shipped codecs, and why `.contract()` is one

read first-hand: `node_modules/zod/src/v4/classic/tests/codec-examples.test.ts`. every shipped
example is the same shape — **a serialized form ⇄ its rich runtime form** — and every test
asserts a round trip:

```ts
const roundTrip = z.encode(codec, z.decode(codec, original));
expect(roundTrip).toBe(original);
```

the examples: `stringToNumber`, `stringToInt`, `stringToBigInt`, `numberToBigInt`,
`isoDatetimeToDate`, `epochSecondsToDate`, `epochMillisToDate`, `jsonCodec`, `utf8ToBytes`,
`bytesToUtf8`.

**`X.contract().coerce()` is that exact shape** — wire json ⇄ domain instance is the same

`toJSONSchema` limitation; it is the case zod built codecs for. that is the strongest available
argument for the upstream form, and it is why [g.18](#g18--io-names-the-side-of-the-contract-never-the-border-of-the-endpoint)'s "one rule, both borders" reads as a
property of codecs rather than a convenience.

**the obligation it carries:** a codec owes the round trip, so `.coerce()` owes it too —

**the one structural change that reaches us**: `schema.output` no longer describes a body. their
`asApiGatewayResponseSchema({ body })` lifts it into a `{ status?, headers?, body? }` envelope.

**r.1 — our `#17` premise HOLDS, unchanged.** the crash still reproduces, and `{ io: 'input' }`


**r.2 — 🔴 the crash surface GREW, and this strengthens the case.** a transform nested in the

pre-merge, an output transform crashed only where the output schema **was** the transform. now

**r.4 — 🟡 a NEW seam their merge opened, which is ours to raise and theirs to own.** the
generated cross-service sdk now publishes the **envelope** as the return type:

a caller of a generated sdk wants the **body**. it now receives an http envelope with every

## open questions & assumptions

### assumptions surfaced — and questioned

**a.1 — "the wisher wants ONE change, not two." [VINDICATED — and it is what made the cut cheap]**
*inferred, not stated.* the wish says explicitly: *"whether this is one change or two is
yours… that is not evidence they share a seam."* → **held as: two independent seams.** `none`
touched output validation + introspection; `hydrate` touches input validation. neither depended
on the other.

**that call is the reason [q.9](#q9--the-wisher-challenged-the-none-premise-itself-does-none-survive-ruled-drop-none) could be answered without a redesign.** had the two been
fused — the natural fusion is `hydrate` folded into the schema — a cut to one half would have
torn the other, and the objection would have had to be argued down rather than acted on. that
fusion was independently ruled out anyway ([g.3](#g3-transform-hydration-breaks-introspection-at-runtime), [g.10](#g10--safeparse-does-not-contain-a-throw-from-inside-a-transform), [a.7](#assumptions-surfaced--and-questioned)), so the
evidence and the ergonomics agreed.

**a.2 — "`none` should be a symbol." [moot]**
*assumed; never settled.* closed with the rest of the `none` argument — see
[the questions the call closed](#the-questions-the-call-closed).

**a.3 — "hydration belongs in middleware, after validation." [answered — deferred to execution]**
*an open question, triaged, not an unexamined assumption.* it could equally live in the `logic`
fn just before `invoke`. **both placements satisfy every acceptance bullet**, and the choice is
observable only to this repo's maintainers, never to a consumer — so it is an execution-stone
call. best-guess: middleware, for symmetry with validation.

**a.4 — "`forApiGateway` must get the same treatment." [INVERTED by the ruling]**
*was verified true for `none`; is false for `hydrate`.* the sharing between the two surfaces is
entirely output-side — `getValidatedOutput` (`:163-166`) and `genIntrospectionMiddleware`
(`:198-202`). **input** validation is the one part they do not share: `forApiGateway` runs its
own `genZodBodyValidationMiddleware` (`:203`) against `event.body`.

so `none` would have reached `forApiGateway` whether we aimed at it or not; `hydrate` reaches it
only if we put it there. **the question flips from "can we avoid it?" to "should we bother?"** →
[q.5](#q5--does-hydrate-land-in-forapigateway-too-wisher--best-guess-yes), re-derived rather than carried over.

**a.5 — "consumers write `X.contract` in their input schemas." [REVERSED by the evidence]**
*assumed NOT required; the trial proved it required.* the first draft said hydration works
against any input schema, pragma or not — true of a hand-declared positional map, false of the
mechanism the evidence now favors. [g.13](#g13--stamp-_dobj-from-the-schema-pragma-then-deserialize--it-works-and-it-reaches-arrays) reads position **from** the pragma, so a hand-written
`z.object` yields no hydration at all.

**recorded as a reversal rather than quietly amended**, because it changes what a consumer must
do, not merely how the sdk does it. the mitigation is not "it is fine" — it is that the mismatch
must be a loud construction-time refusal ([f.2](#f2-what-shape-does-hydrate-take)), so a consumer learns it at deploy rather
than by a silent no-op in prod.

**a.6 — "the double-validation cost is acceptable."**
*assumed, then answered.* see [q.2](#q2-hydration-double-validates-is-that-acceptable-answered).

**a.7 — "introspection publishes the PRE-hydration wire shape."**
*hidden until the assumption review surfaced it, and load-bearing.* the schema published to
codegen describes what a caller must **send**; `invoke` sees the **post**-hydration shape. so
the published shape ≠ the shape `invoke` receives, by design. *what if the opposite were true?* generated
callers would be typed against domain **classes** they cannot construct across a service
boundary — the wire carries json, not instances — and the generated sdk would be unusable.

**this is a second, independent argument for hydration OUTSIDE the schema.** even if
`.transform()` did not break `z.toJSONSchema` ([g.3](#g3-transform-hydration-breaks-introspection-at-runtime)), hydration folded into the schema
would still corrupt what introspection publishes. so the design does not rest solely on a zod
limitation that a future zod release could remove.

### requirements questioned

**"input-only must be explicit and greppable"** — *who said, and does it hold?* the wisher, in
acceptance bullet 1. **it holds as a goal and fails as a REQUIREMENT** — the goal was already
met, because `z.void()` is explicit and greppable and needed no sdk change
([q.9](#q9--the-wisher-challenged-the-none-premise-itself-does-none-survive-ruled-drop-none)).

**this is the one requirement i questioned too gently, and it cost most of a draft.** i argued
about *how* to satisfy it (a mode vs an absent key) rather than *whether* it was unmet — and
the sub-question "is this already possible?" is the cheapest one available. the wisher asked it
in a single sentence and it dissolved the requirement.

**"hydration must reach nested"** — *is the scope too large?* it looked like the expensive
half, and [g.7](#g7-nested-hydration-already-ships-in-domain-objects033) shows part of it is free. but the trial found the **other** part is not: the
evidence's dobj sits under a *plain* wrapper, which `.nested` does not reach, so the sdk must
descend to it. **scope is right-sized — but a top-level-only design would have failed this
bullet**, exactly as the wisher warned.

**"input must arrive as domain instances"** — *simpler way?* one alternative deserves an answer
because every reader will ask it: **just widen `handle` to accept the plain shape and hydrate
inside it** — zero sdk change. rejected, because `handle` is a pre-existing domain operation
whose contract is set by the domain, not by the transport; to widen it lets a lambda payload
format dictate a domain contract, and it pushes the same hand-rebuild one file deeper instead
of removing it. `rhachet-roles-ehmpathy#537` steers to **boundary** hydration for this reason.

**"the `{ input, output }` path stays unchanged"** — *what if we didn't?* every extant
consumer breaks. non-negotiable — and with the output half cut, `schema` is now **byte-identical**
to today's, so this holds by construction rather than by care.

**"a failed dobj construction fails loud"** — *is it already true?* yes ([g.8](#g8-a-dobj-that-refuses-a-validated-input-surfaces-today-but-with-an-inconsistent-error-shape)) — it throws and
reaches the caller. so this bullet is **not new behavior to build**; it is behavior to
*preserve* while normalizing the error shape. worth telling the wisher, since it reframes
that bullet from "build" to "don't regress".

### questions, triaged

#### q.1 — is input-only a mode, or the absence of a config key? **[moot — q.9 cut the premise]**

asked *how* to spell input-only; [q.9](#q9--the-wisher-challenged-the-none-premise-itself-does-none-survive-ruled-drop-none) answered *whether* the sdk should spell it at all —
it should not, `z.void()` already does. the argument is archived in
[the questions the call closed](#the-questions-the-call-closed).

one durable scrap survives the moot: [g.5](#g5-an-absent-output-key-is-not-a-weak-signal--it-is-a-raw-typeerror) proves an absent `output` key is *currently
unhandled* (a raw `TypeError` in three places), which is a defect **regardless** of this
question's answer. that is why it is seeded rather than dropped with the rest.

#### q.2 — hydration double-validates. is that acceptable? **[answered — then CORRECTED]**

> **⚠️ the answer below is too generous to itself. see [q.14](#q14--hydration-has-a-root-primitive-upstream-too-and-it-is-not-new-ruled-adhere).** i argued no pass is
> redundant; that holds only when the schema diverges from `X.contract`. when the schema position
> **is** the contract, the two passes run the *same* schema and the second is provably redundant —
> and `domain-objects` already ships the opt-out (`skip.schema`), which i did not go look for. the
> argument below is otherwise sound and is kept for the divergent case.

**yes, and neither pass is redundant — they check different things.**

- zod validates **the wire shape** — what a caller is permitted to send.
- the dobj constructor validates **the domain invariant** — what the class permits to exist,
  plus `.nested` reconstruction ([g.7](#g7-nested-hydration-already-ships-in-domain-objects033)).

when the input schema *is* `X.contract`, the two are the same schema and the second pass is a
cheap no-op on already-clean data. when they diverge, the divergence is exactly the signal you
want — and it surfaces loudly ([g.8](#g8-a-dobj-that-refuses-a-validated-input-surfaces-today-but-with-an-inconsistent-error-shape)).

**neither is "authoritative" and they should not reconcile.** to make one authoritative you
would have to either skip zod (losing the wire contract that introspection publishes) or skip
the constructor (yielding a half-built object — violating acceptance bullet 5 and
`rule.require.failfast`). the cost is one extra parse per hydrated key per invocation, on an
object that already passed. accepted.

#### q.3 — does this bind `#13` (input schema generators)? **[answered]**

**no — and the two barely touch.** `#13` produces input schemas for event sources (sns, sqs);
this consumes an input schema to locate dobjs in it. an aws event schema carries no
`x-domain-object` pragma, so a `#13` handler simply omits `hydrate` and takes no new code path.

the one leftover: `#13`'s own evidence writes `output: z.any()`, which
[q.9](#q9--the-wisher-challenged-the-none-premise-itself-does-none-survive-ruled-drop-none) reclassifies as a steer defect. its examples should say `z.void()`. → a doc note
for `#13`, not a design constraint here.

#### q.4 — should `output: z.any()` become illegal? **[answered]**

not a wisher question — **the wisher explicitly delegated it**, in `.acceptance`:

> *"whether it stays legal is **yours**; that it stops being FORCED is the outcome"*

**answer: keep it legal.** `z.any()` is a valid zod schema; to forbid it would break anyone who
uses it deliberately.

**[q.9](#q9--the-wisher-challenged-the-none-premise-itself-does-none-survive-ruled-drop-none) shifts what this question is FOR.** with `none` cut, `z.any()` is the last way left
to say "knowable but undeclared" — so the entire remedy on the output side is a nudge toward

#### q.9 — the wisher challenged the `none` premise itself. does `none` survive? **[ruled: drop `none`]**

> *"why would we ever allow input only validation? if they want to say that the endpoint returns
> null, why wouldn't the output just be `z.null()`?"* — the wisher, mid-drive

**this is the sharpest question asked of this vision, and my answer is that it lands.** it is
recorded here rather than absorbed, because it does not merely reshape the design — it
questions whether half of it should exist.

**first, the steelman for `none`.** `z.null()` asserts the response *is* `null`, and a handler
that returns `undefined` (or anything else) would then fail **output** validation and turn a
working invocation into a `MalfunctionError` 500. so `z.null()` is not a drop-in for "do not
check the output" — it is a stricter claim than the author may be able to honor.

**but that steelman only defends "not `z.null()` specifically", not `none`.** walk every real
case and zod already has an honest word for each:

| what the author actually means | honest declaration today | what `none` adds |
|---|---|---|
| "returns no meaningful value" (the `#13` sqs case) | `z.void()` | not one thing |
| "returns null" | `z.null()` | not one thing |
| "the shape is genuinely unknowable" (a proxy/passthrough) | `z.unknown()` | not one thing |
| "the shape is knowable and i declare it" | the real schema | not one thing |
| "the shape is knowable and i decline to declare it" | — | **sanctions the evasion** |

only the last row needs `none`, and that row is the very lie the wish set out to remove. so
`none` does not replace `z.any()` — it **renames** it, and gives the rename an official blessing.

**and the wish's premise does not survive the check.** the wish says the consumer *"is forced to
write it anyway, because the sdk demands an output schema."* the sdk demands a **ZodSchema** —
and `z.void()` / `z.unknown()` are ZodSchemas. **no rule forces `z.any()` today.** what is true,
and what the wish correctly felt, is that `z.any()` is *tempting* and *undistinguished*. that is
a smaller defect with a smaller fix.

**one capability is genuinely absent, and `none` is not it.** a team may want the output schema
**declared** (so codegen emits a real type) but **not enforced** (so a schema drift degrades a
field rather than 500s a live endpoint). neither `z.any()` nor `none` expresses that — both
throw the type away. an explicit enforcement opt-out does, and it is strictly better than
`none` on the wish's own terms, because the generated caller keeps its real type
([g.1](#g1-output-zany-degrades-the-generated-sdk-to-promiseunknown)'s degradation never happens):

```ts
schema: { input, output: SurfLesson.contract },
enforce: { output: false },   // declared, deliberately unenforced — greppable, and typed
```

**best-guess was: drop `none`; keep `hydrate`.** the two halves were never one seam
([a.1](#assumptions-surfaced--and-questioned)), so the hydration work is untouched by the call.

it went to the wisher rather than my desk because it is **not** a clean rework: acceptance
bullets 1–2 are written in terms of a new way to declare input-only, so to drop it re-scopes the
deliverable; and once consumers write `output: none` in their handlers, its removal breaks every
downstream service.

> [three seeded findings](#what-the-wisher-gets-back-instead-of-the-output-half) and one flagged,
> unbuilt capability.

#### q.13 — the input seam has no root primitive; the output seam does **[ruled: extract one]**

> *"it's gotta structurally operate everywhere the same way, through the same root primitive."*
> — the wisher

**the asymmetry is real, and it is why q.4 was a question at all.** the directory says it:

| seam | root primitive | who calls it |
|---|---|---|
| **output** | `middleware/getValidatedOutput.ts` | both surfaces |
| **input** | **absent** | each surface hand-rolls its own |

the two input middlewares are the **same three steps**, differ only in which field they touch:

```ts
// forAskEndpoint/middleware/genZodEventValidationMiddleware.ts:16-21
const result = input.schema.safeParse(request.event);
if (!result.success) throw getValidationError({ error: result.error });
request.event = result.data;

// forApiGateway/middleware/genZodBodyValidationMiddleware.ts:18-23
const result = input.schema.safeParse(event.body);
if (!result.success) throw getValidationError({ error: result.error });
event.body = result.data as unknown as typeof event.body;
```

they already share `getValidationError`. what they do **not** share is the parse-and-return step
— so "does hydration reach both surfaces?" had to be answered by two parallel end-to-end proofs
that we then hope agree. **that is an empirical guarantee where a structural one is available.**

**the extraction** — mirror `getValidatedOutput` exactly, same directory, same shape, and the
fault attribution the input seam already uses (`ConstraintError`, caller fault — vs the output
seam's `MalfunctionError`, server fault):

```ts
// middleware/getValidatedInput.ts  ← the root primitive
export const getValidatedInput = <TInput>(input: {
  value: unknown;
  schema: ZodType<TInput>;
}): TInput => { … };
```

each surface's middleware then reduces to *pick the field, call the primitive, put it back*:

```ts
request.event = getValidatedInput({ value: request.event, schema: input.schema });
event.body    = getValidatedInput({ value: event.body,    schema: input.schema }) as …;
```

**what this buys, and it is the whole point:** hydration behavior is no longer a per-surface
property to be verified twice. it is a property of **one** function, clamped once. the per-surface
clamp shrinks to a much weaker claim — *this surface reads and writes the right field* — which is
cheap and stays honest. `rule.prefer.most-common-denominator`: the operation is reused by two
sibling surfaces, so it lifts to their common ancestor. it should have lived there already; the
output side proves the pattern was known.

**where it lands: phase 1.** it is a pure refactor — no behavior change, no new surface — and it
is **ungated**, so it does not wait on `domain-objects`. that placement matters for the escape
hatch: if phase 1 splits out and merges alone, the input seam is unified whether or not
`.coerce()` ever ships.

**the honest tension, since this is a third thing in one pr.** [q.7](#q7--the-research-surfaced-a-live-defect-the-wish-did-not-ask-about-fix-it-here-or-report-it-answered--ruled-by-the-wisher) forbade an *incidental*
find chased into scope. this is not that: it is the structural precondition for the deliverable's
own guarantee — without it, "works the same everywhere" is a claim two test files make, not a
fact one function enforces. still, it is extant-code churn a reviewer did not ask for, so it wants
its **own commit** in the pr, revertable on its own, with the byte-identical behavior stated in
the message.

#### q.14 — hydration has a root primitive upstream too, and it is not `new` **[ruled: adhere]**

> *"we gotta adhere to their vision — of deserialize. prepare for it."* — the wisher

[q.13](#q13--the-input-seam-has-no-root-primitive-the-output-seam-does-ruled-extract-one) applies the same-root-primitive rule to **this repo's** input seam. this applies it one
layer down, to **`domain-objects`' own** hydration seam — and there the primitive already exists.
read first-hand at `src/manipulation/serde/deserialize.ts:114`:

```ts
return DomainObjectConstructor.build(obj, { skip: context.skip });
```

**`.build`, not `new`.** every probe in [g.15](#g15--xcontractcoerce-beats-the-hydrate-key-on-every-axis-and-it-does-not-exist) ran `new Klass(p)`, and the first draft of the
handoff asked for the same. that was a divergence from their vision, corrected. the two are not
interchangeable — `.build` additionally:

- applies **`withImmute`**, so a coerced instance is immutable like a deserialized one
- cascades **`.nested`** with `.clone()` (`deserialize.ts:112-113`)
- accepts **`DomainObjectInstantiationOptions`**, the plumb for `skip`

**the payoff, and it is exactly what the wisher asked for:** an instance from
`X.contract().coerce()` becomes **indistinguishable** from one that came out of `deserialize`. one
hydration primitive, one behavior, whichever door a caller enters through. under `new`, the repo
would ship two kinds of domain object — immutable from serde, mutable from schema parse — and the
difference stays invisible until it bites.

**it also resolves [q.2](#q2-hydration-double-validates-is-that-acceptable-answered).** i answered the double-validation objection by
argument ("neither pass is redundant"). that answer was too generous to itself: when the schema
position **is** `X.contract`, the two passes run the *same* schema and the second is provably
redundant. **`domain-objects` already ships the opt-out** —
`DomainObjectInstantiationOptions.skip.schema` (`DomainObject.ts:19-27`, honored at `:47`). so the
handoff now asks that `.coerce()` accept those options and make `skip` reachable, rather than
have a consumer accept a pass they can prove is unnecessary.

**and the boundary that keeps them distinct.** `.coerce()` must **not** become `deserialize`.
`deserialize` revives a string `serialize` produced and keys off the `_dobj` tag `serialize`
stamps (`:98-100`); `.coerce()` handles an **untagged external payload** that never passed
through `serialize`. they share the primitive (`.build`) and no more than that — which is also the
retroactive verdict on [what is awkward #3](#what-is-awkward): the cut `hydrate` design synthesized a `_dobj` tag
onto a caller's payload, and that was a violation of this vision, not merely inelegant.

**what this changes here — "prepare for it":**

| where | the change |
|---|---|
| the handoff | asks for `Klass.build(props, options)`, names the `skip.schema` opt-out, and states the `.coerce()`-is-not-`deserialize` boundary — **already written; needs to reach the dispatched issue** |
| phase 2 clamps | one more: a coerced instance **equals** a deserialized one — same class, same immute, same `.nested` cascade. that is the clamp that makes "same everywhere" a fact rather than a hope |
| [g.15](#g15--xcontractcoerce-beats-the-hydrate-key-on-every-axis-and-it-does-not-exist) | its results stand — the stand-in's `new` vs `.build` does not move any of them (both throw alike, both hydrate, the pragma is untouched). recorded so a reader does not re-derive the probes to check. |

##### c.1 — `deserialize` names two different things, and one contains the other 🔴

| whose | what it means |

#### q.16 — the upstream codec verdict wants `io:'input'` on BOTH schemas. do we take it? **[ruled: yes — in full]**

the `.coerce()` drive ruled for a **codec** and concluded *"one rule, both positions"* — that
`{ io: 'input' }` is right for the input schema **and** the output schema. that directly overturns
this bound's first `#17` design, so it was probed rather than accepted.

**it was probed twice, and the two probes disagreed. the second one is right.**

| round | probe | verdict |
|---|---|---|
| 1 | [g.16](#g16--the-codec-verdict-is-right-for-one-position-and-a-failhide-for-the-other) | **half** — took it for the input schema, declined it for the output schema |
| 2 | [g.18](#g18--io-names-the-side-of-the-contract-never-the-border-of-the-endpoint) | **in full** — one rule, both borders |

**what round 1 got wrong, and why it took the wisher to see it.** g.16 read `io` as a **border**
word — a property of which schema you hold — and so it split the verdict by position. `io` is a
**side** word: it names which face of the contract you emit, wire or instance. and the face that
crosses is the **wire**, at both borders, because the wire is json in both directions:

| the word | scope | values |
|---|---|---|
| **border** | the **endpoint** — which way a message travels | request / response |
| **side** | the **contract** — which face of the codec | wire (in) / instance (out) |

g.16 never stated the premise its split depended on: that the response border publishes whatever
`getValidatedOutput`'s `safeParse` yields. **`JSON.stringify` is the real encoder**, and it emits
side A regardless ([g.18](#g18--io-names-the-side-of-the-contract-never-the-border-of-the-endpoint)). one measurement, and the split falls.

**the counter-case is re-classified, not dismissed.** a one-way transform in an output schema does
put side B on the wire — because the response path decodes a value that travels the encode
direction. `z.encode` refuses that outright (`$ZodEncodeError | Encountered unidirectional
transform during encode`), which names it correctly: that schema is a post-processor, not a wire
contract. so it is a **declaration defect**, and `reverseTransform` distinguishes it at runtime.

**what this bound takes:**

- **takes the rule in full** — `{ io: 'input' }` at both borders
- **takes** the confirmation that `#17` is load-bearing under a codec too — the sequence
  constraint in the handoff is stronger than first written, not weaker
- **keeps the legible-refusal change**, with a better reason than g.16 gave it: not *"we cannot
  serialize this"* but *"an output schema must be a wire contract; a unidirectional transform makes
  it a post-processor"* (`rule.require.errors-name-the-fix`)

**one correction still travels upstream** — not to their `io` rule, which stands, but to the
round-trip obligation a codec carries. `.coerce()` owes `encode(decode(wire)) === wire` for a
**real** dobj, where `.nested` and `withImmute` are the risk points; [g.18](#g18--io-names-the-side-of-the-contract-never-the-border-of-the-endpoint) verified it for a
flat stand-in only ([g.19](#g19--why-zod-shipped-codecs-and-why-contract-is-one)).

##### the accessor is a CALL — `contract()`, not `contract`

ruled by the wisher. today it is a **static getter** (`DomainObject.ts:114`,
`public static get contract()`), so this is a **break** in the accessor on top of the additive
`.coerce()`. three consequences, recorded rather than absorbed:

- **conformance line 6 is revised.** it no longer reads "bare `X.contract` unchanged"; it reads
  **`X.contract()` returns what the removed getter returned** — same pragma, same
  memoized-per-class instance, `.ref` reachable at `X.contract().ref(by)`. the shape survives; the
  accessor does not.
- **the bump becomes major for us**, not additive. our exposure is three call sites, all in test
  assets: `createCapturableHandlers.ts:39,53,69`. cheap here — but every consumer pays the rename.
- **memoization needs a restated contract.** per-class memoization
  (`getContract.ts:57,72-73,122`) is unambiguous for a getter; as a call it must be said out loud
  whether `contract()` is memoized per class or per call. our clamp assumes **per class** — two
  `Surfer.contract()` calls should be `===`, because the codegen de-dupes dobjs by identity.

all three are written into the handoff.

##### and the REASON for the call form — it is the fix for [g.14](#g14--xcontract-is-typed-zodschemaany-so-it-erases-the-position-it-stamps), not a style choice

> *"`Surfer.contract` propagates `any` as the type; `Surfer.contract()` propagates the full type.
> …it becomes `Surfer.contract().ref(...)` too. this is a typescript constraint."* — the wisher

**this corrects my read of it twice over.** i logged the call form as an accessor break with a
cost and no stated benefit, and asked whether it was worth a major bump. it is — and the benefit
is the defect [g.14](#g14--xcontract-is-typed-zodschemaany-so-it-erases-the-position-it-stamps) recorded and [q.8](#q8--the-type-level-half-of-no-as-cast-rests-on-an-upstream-any-report-it-answered) called upstream-and-unclosable:

| form | status | `z.infer` at that position |
|---|---|---|
| `Surfer.contract` | ⛔ **removed** — the getter does not survive | *(was `any`)* |
| `Surfer.contract()` | the only accessor | the real shape |
| `Surfer.contract().coerce()` | | the `Surfer` **instance** |

**the getter is replaced, not joined.** it cannot be kept beside the method — one name cannot be
both a property and a callable, so there is no deprecation window and no both-forms-work release.
every `X.contract` call site in every consumer becomes `X.contract()` at the bump.

**why it must go: a static getter cannot be generic.** it has no type-parameter position and no
`this` to propagate, so `DomainObjectContract = ZodSchema<any>` (`getContract.ts:25-27`) is not a
lax declaration — it is the only type a getter can carry. a static **method** can use polymorphic
`this`, so the return type names the class it came from. the accessor change is not cosmetic:
**it is the mechanism by which the type survives at all.**

**this widens the fix past `.coerce()`.** [g.15](#g15--xcontractcoerce-beats-the-hydrate-key-on-every-axis-and-it-does-not-exist) showed a `.transform()` recovers the type at a
**coerced** position. the call form recovers it at **every** position — a bare `contract()` and a
`contract().ref(by)` too, neither of which involves a transform. so
[q.8](#q8--the-type-level-half-of-no-as-cast-rests-on-an-upstream-any-report-it-answered)'s "report, do not chase" verdict was right about the **repo** (it is upstream work) and
wrong about the **scope** — i wrote that only a coerced position could recover, and every
position can.

**`.ref` moves with it: `Surfer.contract().ref(by)`.** that changes conformance line 6 again —
the shape to preserve across the accessor break now includes `.ref`'s new home, and the
`.ref`-after-`.coerce()` chain-order caveat is stated against the call form throughout.

**written and ready to dispatch** — `refs/handoff.peer-bound.apigateway-wire-response.md`.
self-contained: it carries the executed evidence verbatim, cites their own vision back to them,
proposes the readme sentence, and states its own limit (the two features do not yet exist
together, so the order argument is read from both pipeline diagrams rather than exercised).

> guess.

**it does stop the crash — and that is exactly why it must not land alone.**

executed against `zod@4.4.3` + `domain-objects@0.34.0`:

| the schema | `{ unrepresentable: 'any' }` alone | `{ io: 'input' }` alone |
|---|---|---|
| a `.transform()` | `"id": {}` — **crash gone, schema erased** | `"id": { "type": "string" }` — the true wire shape |
| an `X.contract()` dobj | `"surfer": {}` — **the `x-domain-object` pragma is destroyed** | full shape, pragma intact |
| a `z.custom` | `"id": {}` — correct, it genuinely has no rendition | 💥 still throws |

## 🔴 the hazard: `unrepresentable: 'any'` alone would silently gut the codegen

a `.transform()` and an `X.contract()` **do** have a json-schema rendition — their **input** face.
so a degrade to `{}` is not an honest *"this cannot be rendered"*; it is a lie that says *"this
field is unconstrained"* about a field with a precise wire shape.

the sharpest instance is the dobj row. `genServiceSdk` recognizes a domain object by the
`x-domain-object` pragma (`getAllDomainObjectsFromContracts.ts`). under `unrepresentable: 'any'`
that pragma is **gone** — so every generated cross-service client silently degrades from a typed
resource to `unknown`, with no crash and no tell.

⇒ and this is no longer an edge case: **`domain-objects@0.34.0` made `X.contract()` always
coerce**, and a coerce is a `.transform()`. so on `0.34.0` *every* dobj position in *every* schema
takes this path.

## ⇒ the two fixes are complementary, and the order matters

| | `#17` — `{ io: 'input' }` | `#22` — `{ unrepresentable: 'any' }` |
|---|---|---|
| what it is for | a type that HAS a wire rendition, on its wire face | a type that genuinely has none |
| transform / dobj | **publishes the truth** | erases it to `{}` |
| `z.custom` | still throws | **the only fix** |

both are wanted, and the safe composition is
`z.toJSONSchema(schema, { io: 'input', unrepresentable: 'any' })` — measured: one schema that
carries a transform, a `z.custom`, and a dobj emits cleanly, with the transform's string shape
intact, the dobj's pragma intact, and only the `z.custom` degraded to `{}`.

**so please do not land `#22` before `#17`.** alone it converts a loud crash into a quiet,
service-wide codegen regression — which is strictly worse (`rule.forbid.failhide`).
