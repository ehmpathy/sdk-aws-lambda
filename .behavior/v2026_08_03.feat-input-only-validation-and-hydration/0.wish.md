# wish: an honest input-only contract, and domain objects that arrive already hydrated

## .what

`genLambdaEndpoint` supports two capabilities a consumer today has to FAKE:

1. **input-only validation** — an explicit way to declare "validate the input, do not validate
   the output", with no `output: z.any()` rubber-stamp.
2. **domain-object hydration at the boundary** — the validated input arrives as the domain-class
   instances the `handle` contract wants, rather than the plain objects zod yields.

## .why

**both workarounds produce code that lies, and a reviewer cannot tell the lie from an oversight.**

- `output: z.any()` validates no field at all. a consumer who wants input-only validation is
  forced to write it anyway, because the sdk demands an output schema. so the schema now reads
  as a contract while it enforces naught — and it is **indistinguishable from a schema someone
  forgot to fill in.**
- zod validates to a plain object, but `handle` is typed against a domain class. so the consumer
  either hand-reconstructs the domain graph field by field at every handler, or reaches for an
  `event as ...` cast — the exact anti-pattern `rhachet-roles-ehmpathy#537` forbids.

the sdk should make the recommended path the ergonomic one. today it makes the recommended path
the laborious one, so the cast is what a tired author reaches for.

## .acceptance

- a consumer can declare input-only validation **explicitly and greppably** — a reviewer can
  tell "the author chose not to validate output" apart from "the author forgot", from the
  declaration alone
- **`output: z.any()` is no longer the only way to express that intent.** whether it stays legal
  is yours; that it stops being FORCED is the outcome
- the validated input can arrive as true domain instances, so `invoke` / `handle` receive their
  real contract with **no `as` cast and no per-field hand-reconstruction**
- hydration reaches **nested** domain objects, not only the top level — the evidence below is a
  nested `Agent` inside an `assignment`, and a top-level-only fix would leave that hand-rolled
- a domain object that fails its own construction-time validation **fails loud** at the boundary
  and never reaches `handle` half-built (`rule.require.failfast`)
- the extant `{ input, output }` path still serves consumers who validate both, unchanged

## .ground — verified, NOT instruction

the migrated handler that had to do BOTH workarounds at once — `svc-notifications` branch
`beav/feat-declapract-upgrade`, `src/contract/handlers/configureProxyPhoneNumber.ts`:

```ts
// output: z.any() only to preserve the prior createStandardHandler input-only behavior.
// the invoke hand-hydrates the validated plain `agent` into a real Agent domain instance
// (which re-validates) so `handle` gets its true Agent contract with no cast.
export const handler = genLambdaEndpoint(
  {
    schema: { input: schema, output: z.any() }, // <-- rubber-stamp, not a real contract
    invoke: async ({ event }) =>
      handle({
        ...event,
        assignment: event.assignment
          ? {
              ...event.assignment,
              agent: event.assignment.agent
                ? new Agent(event.assignment.agent) // <-- manual nested hydration
                : null,
            }
          : null,
      }),
  },
  { env: { access: envStatic.access } },
);
```

note what that comment admits out loud: the `z.any()` exists **only** to preserve prior
behavior, and the hand-hydration exists **only** to dodge a cast. two lies, both authored
knowingly, because the sdk offered no honest way to say either one.

## .the HOW is yours — advisory only

per `rule.forbid.prescribe-how-on-dispatch` and `rule.require.wish-outcome-over-proposal`,
`.what` / `.why` / `.acceptance` are authoritative. all else here is ground.

issue **#16** proposes a specific shape — `schema: { input }` with the `output` key absent (or
`output: none`), plus "the input schema (**or** an explicit `hydrate` step)". read it for
context, but note it was authored from OUTSIDE this repo by the consumer who felt the pain:

- **how input-only is declared** is yours. an absent key, a sentinel, a separate entrypoint, or
  a shape this repo already uses — the acceptance asks that the intent be explicit and
  greppable, never that it arrive by a particular syntax. note that an ABSENT key is itself a
  weak signal to a reviewer, and the acceptance demands a strong one.
- **where hydration lives** is yours — folded into the input schema, a distinct `hydrate` step,
  or another home. the issue names both and settles neither.
- **whether this is one change or two** is yours. the two arrived in one issue because one
  handler hit both; that is not evidence they share a seam.

if an in-repo pattern beats the issue's proposal, prefer it and say why in your vision yield.

## .open questions worth a decision (yours to settle)

- **is input-only a mode, or the absence of a config key?** a mode is greppable and reviewable;
  an absent key is neither. a wrong call is awkward to undo once consumers declare against it.
- hydration duplicates validation: zod validates, then a domain-object constructor validates
  again. is the double pass acceptable, is one of them authoritative, or do they reconcile?
- does this pair with **#13** (input schema generators) closely enough that a decision here
  binds that one? they are the two halves of the same input side.
