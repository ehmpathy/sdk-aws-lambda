## .what

`sdk-aws-lambda` ships its own **in-process handler-invoke test util** — the successor to
`simple-lambda-testing-methods`' `invokeHandlerForTesting` — so a repo migrated to
`genLambdaEndpoint` can test its handlers with **no residual dependency on the very
`simple-lambda-*` family the migration replaces**.

done when: a repo whose handlers all use `genLambdaEndpoint` can delete
`simple-lambda-testing-methods` from `package.json` and every handler integration test still
passes.

## .why

the declapract migration wave swaps `simple-lambda-client` / `simple-lambda-handlers` →
`sdk-aws-lambda` (`createStandardHandler` → `genLambdaEndpoint`). the handler **integration
tests** were not part of that swap, so they still import `invokeHandlerForTesting`.

⇒ a **fully migrated** repo keeps `simple-lambda-testing-methods` in `package.json` for one
reason only: to test the handlers that no longer use anything else from that family.

**measured**: `ahbode/svc-notifications@beav/feat-declapract-upgrade` migrated every handler to
`genLambdaEndpoint` and still carries `simple-lambda-testing-methods@0.5.1`, purely for its
handler tests.

so the seam is not cosmetic — it is the last thread that keeps a retired package alive in every
repo the wave touches. one package should own both the handler factory **and** the way you
exercise it in-process.

## 🔴 .the contract it MUST honor — verified against `sdk-aws-lambda@0.3.0`

this is the part most likely to be got wrong, because the obvious behavior is the wrong one.

**`genLambdaEndpoint` does NOT throw on a domain error in-process.** it *catches* the error and
*returns* an error-envelope response (`getErrorResponseBody`) — ancient
`{ errorMessage, errorType, … }` or contemp `{ error: { _serde, class, message, … } }`.

the legacy `invokeHandlerForTesting` is a callback-or-promise bridge that hands back whatever the
handler produced, so the envelope arrives raw. so the util must:

- invoke a `genLambdaEndpoint` handler in-process with a plain `event`, **JSON-stripped the way
  the wire strips it** — the legacy util does `JSON.parse(JSON.stringify(event))` to drop class
  instances, and a util that skips this lets a test pass on an object the wire could never deliver
- hand back the response the handler produced — a success payload OR an error envelope
- ⚠️ **do NOT re-throw domain errors.** that is what the over-the-wire path
  (`askLambdaEndpoint` / `invokeLambdaForTesting`) does. an in-process util must stay faithful to
  what the handler actually returns, or the two paths disagree about the same handler and a test
  proves the wrong one

## .why it is not merely a re-export

`invokeHandlerForTesting` predates `genLambdaEndpoint` and knows naught of it. a util that lives
in this sdk can be **endpoint-aware** — it can know the envelope shape it will get back, which is
what makes an assertion helper possible at all. today a test that wants to check an error message
must hand-`JSON.stringify` the envelope and grep it.

an envelope-aware assertion helper is therefore in scope, if the maintainer judges it earns its
keep.
