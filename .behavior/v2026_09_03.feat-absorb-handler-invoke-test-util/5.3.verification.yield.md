## defect 2 — the root cause of every AWS integration/acceptance failure was the jest env's
credential source, not an IAM policy gap

**this section supersedes the earlier "AWS IAM permission gap" diagnosis and handoff — that
diagnosis was wrong, and the fix was driver-fixable all along.**

every prior failure carried the same `AccessDeniedException`, assumed under
`ahbode-camp-grove-role/i-...` — the AMBIENT grove EC2 instance's OWN base role, never the
chained target-account profile keyrack sets. `jest.integration.env.ts` and
`jest.acceptance.env.ts` called a bare `keyrack.source({ env: 'test', ... })`, which sets only
`AWS_PROFILE`. the `@aws-sdk/client-lambda` (v3) default credential provider then resolved that
profile — `credential_source = Ec2InstanceMetadata` chained via `role_arn` — inconsistently in
this environment, and fell through to the grove's own un-chained instance credentials rather
than the intended cross-account role.

the org's own shared practice (`declapract-typescript-ehmpathy`'s `useKeyrack`) already carries
the fix for exactly this class of gap: splice STATIC credentials (via
`aws configure export-credentials --profile <profile> --format env`) into `process.env`, and
DELETE `AWS_PROFILE`, so the sdk's credential resolution is deterministic rather than chained.
this repo's `jest.*.env.ts` files predated that practice fix.

**fixed**: ported `useKeyrack` (`src/__test_assets__/useKeyrack.ts`) and wired it into both
`jest.integration.env.ts` and `jest.acceptance.env.ts`, replacing the bare `keyrack.source` call.

**result**: 23 previously-failed integration tests → 0 failures. 41 previously-failed
acceptance tests → 0 failures (modulo the prior-infra race below). the wish's own case=9
credential-chain critipath — the cloud-locus `onSerialized` invoke — was OBSERVED GREEN for the
first time in this drive's history:

## defect 3 — the deployed-introspection flake, diagnosed and repaired

with credentials now correct, a SECOND, prior issue became visible for the first time:
`blackbox/deployed.introspection.acceptance.test.ts` intermittently failed under a full
parallel-worker acceptance run (`maxWorkers: '50%'`), two ways — a raw `ResourceConflictException`
from `declastruct-aws`'s `setLambda`, or a schema-mismatch snapshot diff with no thrown error at
all. isolated (path-scoped) runs of that file passed 7/7 every time, which pointed at concurrency
rather than a logic defect in the file itself.

**root cause, both symptoms, one mechanism.** `deployed.introspection.acceptance.test.ts` and
`deployed.awsLambda.acceptance.test.ts` share one IAM role
(`ROLE_NAME = 'sdk-aws-lambda-e2e-seaturtle-role'`), and repeat runs of the suite (or a full
parallel run) can call `setLambda` on the same account while a prior update has not yet finished:

- the **hard** failure: AWS answers a concurrent update with `ResourceConflictException` — the
  file's own `setLambda` had no retry for this error class, only for IAM-role-propagation errors.
- the **soft** failure: `waitUntilFunctionActiveV2` only waits for the lambda's `State` to reach
  `Active`. it does not wait for `LastUpdateStatus` to reach `Successful` — so a lambda can read
  `Active` while its code update from a concurrent run is still `InProgress`, and introspection
  then reads a partial or stale bundle. that is the schema-mismatch flake, with no exception at
  all to catch.

**fixed, in `blackbox/deployed.introspection.acceptance.test.ts` only**:

1. `withRetry`'s `shouldRetry` predicate now also matches `ResourceConflictException` (by
   `error.name` and by message), so the hard failure retries with backoff over a thrown rejection.
2. `waitUntilFunctionUpdatedV2` now runs right after `waitUntilFunctionActiveV2`, so the test
   never introspects a lambda whose code update has not yet finished.

**proof the fix holds — 3 consecutive full-suite runs, `--against cloud --env prep --mode apply`**:

| run | acceptance result |
|---|---|
| 1 | 11 files, 225 passed, 0 failed, 0 skipped (244s) |
| 2 | 11 files, 225 passed, 0 failed, 0 skipped (251s) |
| 3 | 11 files, 225 passed, 0 failed, 0 skipped (320s) |

the flake that previously showed 1-7 failures on `deployed.introspection` did not recur once
across the 3 runs. the earlier caught dream
(`.dream/v2026_09_18.repair.concurrent-declastruct-apply-races-across-deployed-acceptance-files.md`)
is retired — the fix is safe and clean (single file, additive retry + an additional wait, no
change to `jest.acceptance.config.ts` or any other acceptance file), so
`rule.always.fix-forward-under-scouts-honor` calls for the repair over a deferral.
