## .the narrative

maya implements the promotion. `invokeHandlerForTest.ts` imports `createTestContext` from
`./createTestContext`, so she moves that file out of `__test_assets__` alongside it — the whole
file, because that is what a move is.

the suite is green. types pass. lint passes. she opens a PR.

what she cannot see from inside this repo: `createTestContext.ts` has a **second export**.

```ts
// createTestContext.ts:27 — travels along, unnoticed
export const createMockLog = () => ({
  debug: jest.fn(),   // ← jest, at module scope
  …
});
```

inside `sdk-aws-lambda`, `jest` is present — it is a devDependency, and every test runs under it.
so no local signal complains. **the repo is the one environment where this defect is invisible.**

it surfaces in a consumer: someone runs `npm install sdk-aws-lambda`, imports anything from the
barrel, and node evaluates the module graph — reaching `jest.fn()` in a process where `jest` was
never installed.

```
ReferenceError: jest is not defined
    at Object.<anonymous> (node_modules/sdk-aws-lambda/dist/…/createTestContext.js:27:10)
```

**the aha**: the failure is not in the util and not in the consumer's code — it is in a **sibling
export that rode along on a file move**, and it is undetectable from the repo that shipped it. the
green suite is not evidence, because the suite runs in the one context where jest exists.

## .how the edge fails safe

the fail-safe cannot be a runtime check — by the time it could run, the consumer's install is
already broken. it has to bite **before publish**, in this repo:

- **fast** — a build-time or lint guard on the shipped graph: no module reachable from
  `src/index.ts` may reference a jest global. it fails at `npm run build`, not at a consumer's
  `require`.
- **loud** — the guard names the offending file, the symbol, and the import chain that pulled it
  in, so the fix is mechanical rather than a hunt.
- **teaches the fix** — the message states the split: `createTestContext` is portable,
  `createMockLog` is not; jest-bound assets stay in `__test_assets__`.
- **prevents rather than corrects** (`rule.prefer.prevent-over-correct`) — the highest rung
  available here is to **not move the file**. extract the pure `createTestContext` into its own
  module and leave `createMockLog` behind, so the hazardous symbol is never in the shipped graph to
  begin with. the guard is the backstop for the next contributor, not the primary defense.

## .the bdd sketch

```
given [case6] the util is exported from the root barrel

  when [t0] the shipped module graph is walked from src/index.ts
    then not one reachable module references a jest global
    then createMockLog is NOT reachable
    then createInProcessLambdaHarness is NOT reachable

  when [t1] a contributor adds `import { jest } from '@jest/globals'`
            to a module the barrel reaches
    then the build fails
    then the message names the file, the symbol, and the import chain

  when [t2] the built dist is required in a process with no jest installed
    then it loads with no ReferenceError
    then runLambdaEndpoint.onReferenced is callable

  when [t3] the repo's own suite runs
    then it still passes — jest IS present here
    then so [t3] passing is NOT evidence for [t2]
```

**what the sketch tests that the narrative does not**: `[t2]` and `[t3]`, as a pair.

the narrative shows the defect reaching a consumer, but it cannot show the **reason it got there**:
that the repo's own green suite is structurally incapable of catching it. `[t3]` states that
non-implication out loud — *this test passing is not evidence for that test passing* — which is the
one fact a future contributor most needs and is least likely to derive. `[t2]` is the only
assertion in the whole vision that exercises the built artifact in a **jest-free process**, which
is the actual consumer condition.

## .why it is a critipath

`freq × cost` = high × ∞, worked above. and the failure has a property that makes it worse than its
severity suggests: **it is invisible from the repo that causes it.** every local signal — tests,
types, lint — stays green. so without a deliberate guard there is no feedback loop at all; the
first signal is a consumer's broken install after publish.

no workable fallback exists: a consumer cannot patch around a module-scope `ReferenceError` in a
transitive import.
