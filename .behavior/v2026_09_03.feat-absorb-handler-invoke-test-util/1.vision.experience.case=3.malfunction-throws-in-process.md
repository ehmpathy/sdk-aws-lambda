# case=3 — a malfunction throws in-process, and the util lets it

> cell #9 · sharp · **critipath** · actor: maintainer · density 3
> ⚠️ this demo contradicts a sentence in the wish. see fulcrum **F1**.

## .the narrative

maya maintains `sdk-aws-lambda`. she is writing the util's own test suite, and she starts from the
wish's contract paragraph, which is unambiguous:

> **`genLambdaEndpoint` does NOT throw on a domain error in-process.**

so her first test asserts a returned envelope for a handler that blows up. it fails. the call
rejects.

she goes to the middleware chain, and the reason is plain once seen — the error path is not one
path, it is two:

```ts
// genConstraintErrorMiddleware.ts:40-41,72 — constraint family
const isConstraintError = getIsConstraintError({ error });
if (!isConstraintError) return;          // ← hands off
request.response = body;                  // ← RETURNS an envelope

// genInternalServiceErrorMiddleware.ts:23-24,62 — each other error
const isBadRequest = getIsConstraintError({ error });
if (isBadRequest) return;                 // ← hands off
throw error;                              // ← THROWS
```

the two middlewares split the error space on the same predicate and do **opposite** things with
their halves. and the repo's own suite has said so all along, in one file, twenty lines apart:

- `…forAskEndpoint.test.ts:61-81` — invalid **input** → `await`s the result, asserts on the
  returned envelope
- `…forAskEndpoint.test.ts:103-121` — invalid **output** → wraps in `getError(...)`, asserts on a
  **thrown** error

**the aha**: the wish's rule and the wish's reason point at different implementations, and the
reason is the one that is right. the wish forbids the re-throw so that "the two paths [do not]
disagree about the same handler". a util that caught maya's `MalfunctionError` and returned it as
an envelope would create exactly that disagreement — the real in-process handler raises, and her
util would report a value. the fidelity the wish asks for is a **pass-through**, not a never-throw.

so she deletes the `catch` she had not yet written, and the util gets simpler: it awaits, and it
returns. it makes no claim about `genLambdaEndpoint`'s error taxonomy, so it cannot drift from it.

## .how the edge fails safe

- **fast** — the throw propagates on the same tick the handler raises; the util adds no frame that
  could swallow or delay it.
- **loud** — the original error arrives intact: class, message, `metadata`, `cause`, stack. no part
  is re-wrapped, so `getError(...)` and `expect(...).rejects.toThrow(MalfunctionError)` both work
  on the real thing.
- **teaches the fix** — the message is the handler's own. `…forAskEndpoint.test.ts:113` shows the
  shape: `'output validation failed'` plus the zod issues in `metadata` — it names the field, not
  merely the symptom.
- **the util adds no `catch`** — which is the fail-safe property itself. per
  `rule.forbid.failhide`, a catch here would be the hazard, not the guard. contrast
  `createInProcessLambdaHarness.ts:1-7` which needs a documented rule-exception precisely because
  it *does* convert throws — and earns it only by simulation of the aws runtime, a justification
  this util does not have.

## .the bdd sketch

```
given [case3] a genLambdaEndpoint handler whose invoke raises a MalfunctionError

  when [t0] the util is called with a valid event
    then the call REJECTS — it does not settle to an envelope
    then the thrown value is the handler's own error instance, not a re-wrap
    then error.metadata survives intact

  when [t1] the handler instead returns a shape its output schema rejects
    then the call REJECTS with an output-validation error
    then the message names the offending field

  when [t2] the same handler is asked over the wire via askLambdaEndpoint
    then that call also REJECTS — as a LambdaEndpointError, not a ConstraintError
    then the two paths agree that this was a SERVER fault, in their own vocabularies

  when [t3] the util's source is read
    then it contains no try/catch around the handler call
```

**what the sketch tests that the narrative does not**: `[t2]` and `[t3]`. the narrative is maya's
discovery that the wish was half-wrong — it ends at the insight. `[t2]` checks the thing the
insight *implies but never verifies*: that pass-through fidelity actually keeps the two paths in
agreement about fault attribution (both say server-fault, in different error classes). `[t3]` is
the structural assertion — a future contributor could reintroduce a `catch` and keep `[t0]` green
by a rethrow, so the absent-`catch` property needs its own guard rather than trust.

## .why it is a critipath

it is the contract the wish calls out in red, and the vision's answer differs from the wish's text.
if it is left undemonstrated, the next reader implements the wish literally, writes the `catch`,
and ships a failhide that makes every malfunction in every migrated repo look like a successful
invocation that returned an error object. there is no fallback — a swallowed server fault is
invisible by construction.
