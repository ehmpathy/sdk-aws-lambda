# case=9 — the invoke hangs for ninety seconds

> cell **S3** · sharp · **critipath** · actor: migrant + native · density 3
> D5 = `serialized.cloud` · D2 = `resolution-failure`
> 🔴 **the highest-care cell in the 176-cell product**, on measured evidence

## the narrative

**kai** runs the deployed acceptance suite on his laptop. he is signed in through aws sso, as
every engineer on the team is.

the first invoke takes **ninety seconds**. so does the second.

no error. no retry log. no timeout message. the terminal simply sits there, and then the assertion
passes. a suite of a dozen invokes becomes a twenty-minute wait, and the only signal he has is
that acceptance tests are *"slow"*.

they are not slow. **the credential chain is stuck.** the incumbent reaches aws through
`simple-lambda-client`, which pulls **aws-sdk v2** — and v2 has no SSO-profile support. so it
walks its chain to the end, finds no static credentials, and falls back to the **instance metadata
service**. on an ec2 box IMDS answers in a millisecond. on kai's laptop there is no metadata
service, so it waits for the timeout. every invoke. every time.

the workaround the team found is to export the credentials into env vars before the run, which
skips the chain. it works, and it teaches naught: nobody who hits the hang can tell from the
symptom that credentials are the cause.

> **the hang is not a slow lambda. it is a credential chain that cannot see your sso session.**

⚠️ **this is measured, not inferred** — `ahbode/svc-home-services` PR #30, recorded in radio task
**#20** (2026-08-30). it is the origin story of that task: *"the deployed acceptance grain hung
90s/invoke until creds were exported to env vars."*

and it is exactly the drift the sdk exists to close. `sdk-aws-lambda` already owns a lambda client,
a credential chain, and the function-name computation for the **runtime** invoke. the incumbent
forks all three for the **test** invoke — on an older aws-sdk. so a fix in one does not reach the
other, and the two can disagree about how a lambda is even addressed.

## the bdd

```
given a developer authed via an aws sso profile, with no static credentials in env

when [t0] a deployed lambda is run on the serialized.cloud boundary
  then the invoke completes without a fallback to IMDS
  and it completes in under a second on a warm function

when [t1] no credentials can be sourced at all
  then it REJECTS with a named credential error
  and the error names the fix — not a timeout, not a hang

when [t2] the addressed function is not deployed
  then it REJECTS with a LambdaFunctionNotFoundError naming the slug it looked for

when [t3] the same endpoint is addressed by the runtime path and by the test path
  then both compute the identical function slug
  and neither forks the name computation
```

`[t0]` is the whole case, and it is a **negative** assertion about a fallback — which is why it
needs a demo rather than a note. a util can pass every functional test and still hang, because a
hang is a success with a bad clock.

`[t1]` is the rule this fixes: `rule.require.errors-name-the-fix`. today the failure mode is a
90-second silence, which names no cause at all. the successor must fail **loud and fast**.

`[t3]` guards the drift #20 names — one name computation, shared. a test that addresses a lambda
differently than production does is a test of a lambda that does not exist.

## the boundaries this walk crosses

1. **the run boundary** — serialized (D5)
2. **the locus** — `.cloud`, the only side where a credential chain runs
3. **resolution-failure** — the sixth outcome-state, which exists only on this boundary

**density 3**, and every one of the three is invisible on the referenced half: kai holds no
handler, so there is a lookup, so there is a credential chain, so there is a hang.

## why this is the highest-care cell in the product

`care = freq × cost`, and both terms are extreme:

| term | value |
|---|---|
| **freq** | every deployed-acceptance run, by every engineer, on every laptop — sso is the org default |
| **cost** | 90s × the invoke count, with **no diagnostic signal**; a dozen-invoke suite costs 20 minutes |

⇒ higher than case=5's frame flip (which costs one confused debug session, once) and higher than
case=8's stance flip (which fails loudly and teaches immediately). **this one fails silently, on
every run, forever** — and the symptom points at the wrong thing.

⚠️ **and it was invisible to this drive until the radio was read.** the vision measured 519 call
sites and read the incumbent's source line-by-line, and still had **zero mentions** of aws-sdk v2 —
because the defect lives in a transitive dependency and manifests as latency, so neither a grep nor
a source read of the util surfaces it. it took a task filed by a human who had felt it.

⇒ the lesson the catalog records: **a measured operational defect cannot be found by static
analysis of the artifact.** it is found by the person who waited.
