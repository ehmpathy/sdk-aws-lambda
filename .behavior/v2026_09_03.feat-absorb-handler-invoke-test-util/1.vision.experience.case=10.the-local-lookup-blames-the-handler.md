# case=10 — the local lookup blames the handler

> cell **S2** · sharp · **critipath** · actor: migrant + native · density 3
> D5 = `serialized.local` · D2 = `resolution-failure`

## the narrative

**priya** moves a handler. `src/contract/handlers/getServiceBySlug.ts` becomes
`src/contract/handlers/public/getServiceBySlug.ts` — a tidy-up, one directory deeper.

her unit tests pass. her referenced-boundary integration tests pass; they import the handler
directly, so the move is invisible to them.

her acceptance suite fails with:

```
no file was found at handler.path `/repo/src/contract/handlers/getServiceBySlug`
```

which is **correct and useless in the same breath**. correct, because that path no longer exists.
useless, because it does not say who asked for it. she greps the repo for that string and finds it
in `serverless.yml` — a file she did not think of as a test dependency, because on the referenced
boundary it is not one.

> **on the serialized boundary the handler is not passed — it is looked up.** and every step of
> that lookup is a step that can go stale.

the lookup reads `serverless.yml`, checks the service name matches, finds the function entry, parses
its `handler` string into a path plus an export, imports the file, and reads the export. **six
throw sites, at `invokeLambdaForTestingLocally.ts:23,37,44,51,65,73`** — and every one of them is
the *test author's configuration* at fault, never the handler.

that is what makes it a sixth outcome-state. `malfunction` means the handler ran and broke.
`resolution-failure` means **the handler never ran at all**, and the six ways to get there share an
owner and share a fix shape: a value in the config does not match a value in the tree.

## the bdd

```
given a serverless.yml whose function entry points at a moved handler file

when [t0] the endpoint is run on the serialized.local boundary
  then it REJECTS with a resolution error
  and the error names WHICH config declared the path
  and it names the function entry it read

when [t1] the serverless.yml service name does not match the addressed service
  then it REJECTS and names both the addressed name and the declared one

when [t2] the function entry is absent from serverless.yml
  then it REJECTS and names the function, plus where the entry belongs

when [t3] the handler file exists but does not export the named handler
  then it REJECTS and names the file, the expected export, and what it did export

when [t4] the same handler is run on the referenced boundary
  then it RESOLVES — no lookup occurs, so no resolution failure is reachable
```

`[t0]`'s `and` clauses carry the whole case. the incumbent throws six errors that each name the
**symptom** and none that names the **source** — `rule.require.errors-name-the-fix` graded
blocker. an error that reports *"no file at X"* without *"declared by
serverless.yml#functions.getServiceBySlug.handler"* sends the author to their handler, which is
not the broken part.

`[t4]` is the structural guard: it asserts resolution-failure is **unreachable** on the referenced
boundary. that is a bar, not a behavior — priya hands over the handler, so there is no lookup and
no stale config to trip on.

## the boundaries this walk crosses

1. **the run boundary** — serialized (D5)
2. **the locus** — `.local`, where the lookup is a filesystem + module walk rather than an aws call
3. **resolution-failure** — the sixth outcome-state

**density 3**, and it is the twin of [case=9](1.vision.experience.case=9.the-invoke-hangs-for-ninety-seconds.md):
same state, other locus. together they establish that `resolution-failure` is real on both loci and
that its *causes* are locus-specific while its *shape* is not.

## why this is a critipath

**every repo with an acceptance suite has a `serverless.yml`, and handlers get moved.** a rename,
a reorganization, a directory split — each is a routine refactor that a referenced-boundary suite
will not catch, because it imports the handler and does not care where it lives.

⇒ the serialized boundary makes `serverless.yml` a **test dependency**, and that is a genuinely
new fact for an author who has only run referenced-boundary tests. the error is the only place
they will learn it, so the error has to teach it.

⚠️ **and the incumbent's six errors are the design to improve on, not to port.** they are honest
and they are symptom-only. this is the one place in the wish where the successor should be *better*
than the incumbent rather than faithful to it — the migration swaps an import, so no author's
assertion depends on how an error is phrased.
